# Phase 49 — UI Design Contract

> Visual and interaction contract for Phase 49: Character Creation Interview. Generated by gsd-ui-researcher, to be verified by gsd-ui-checker.
>
> This contract **extends** `45-UI-SPEC.md`, `47-UI-SPEC.md` and `48-UI-SPEC.md` (all approved, including 47's "Owner try-out changes": the desktop feed fills its column and every scrollable surface uses the dark scrollbar rule). Where this file adds a value it says so. Where it maps a mock value onto the scale it records the mapping. Where it replaces a 45, 47 or 48 line it says so under "Supersedes".
>

## Step Bar Contract (CRE-01)

Five steps in this order: `Race`, `Archetype`, `Class`, `Name`, `Enter the realm`. There is no "First words" step.

### Structure

- `ol` with `aria-label="Character creation steps"`, five `li`. The current one carries `aria-current="step"`. Not interactive (no click to jump; going back is a server flow, see Go-back).
- **Desktop** (900px and up): `display: grid; grid-template-columns: repeat(5, minmax(0, 1fr)); gap: 8px` in a band `color-mix(in srgb, var(--color-surface) 30%, transparent)`, padding `16px 32px 8px`. Each item: a 3px segment on top, then a row (gap 4) with the 14px icon and the label (Label 12, ellipsis, `title` carries the full label).
- **Mobile** (below 900px): the five 3px segments only, gap 4, in the 55% surface band, plus the text row `Step {n} of 5 · {label}` (Label 12, `--color-neutral-400`, tabular-nums) with the Sheet chip right-aligned. The five `li` keep `aria-label` text (`Race, done`, `Archetype, current`, `Class, to do` and so on) because their visible labels are not shown.
- A visually hidden `role="status"` line announces `Step {n} of 5: {label}` when the position changes (not on first mount).

### Marker states

## Entry Points (CRE-01)

`deriveScreen` gains a `creation` screen kind and one input, `characterPlaced` (the active character's `locationId` is not 0). There is no client flag and no way to start a second interview: one character per account stays.

| Situation | Screen |
|-----------|--------|
| Signed in, `charactersApplied`, zero characters, no active character | `creation` (replaces the 45 `noCharacters` note) |
| One or more characters, no active character | `picker` (45, unchanged; no `New character` button) |
| Active character exists and is placed | `frame` |
| Active character exists but is unplaced (`locationId` 0) | `creation` (the interview waits at step 5; this also covers the server's stranded-character retry, where the typed word `explore` retries the first region) |

The 45 rule that a "no characters" note never flashes before rows arrive still holds: `creation` shows only after `charactersApplied`.

On mount, when the account has no character, the view calls `start_creation` exactly once per mount. When the view is showing an unplaced active character (step 5), it does not call `start_creation` (the interview is already complete; the progress line and `Retry` cover the wait). The server then either writes the greeting (new state) or a resume line (existing state), so the first lines of a resumed interview always arrive. `event_creation` is an event table, so lines do not replay after a reload; the resume line is what refills the feed. If the `start_creation` call is rejected, one Error line `Couldn't start the interview. Try again.` appears with a `Retry` button (`.btn .btn-primary`, calls `start_creation` again).

### Entering the realm

- The last interview action is the `Enter the realm` button at step 5 (`CONFIRMING`). It sends `Confirm`. The server then creates the character, sets it active and posts the closing line.
- The view stays until the character is placed: the Keeper progress line (47) shows the world-generation indicator (`LLM_INDICATOR_LINES` for `world_gen_start` and `world_gen`, imported through `@game-data`, never copied; the creation view shows the routes in `LLM_CREATION_CONSOLE_ROUTES`). The input is locked with `Entering the realm…`.
- The frame replaces the view the moment the active character row exists and its `locationId` is not 0 (instant swap, no animation; the frame's own automatic `look` follows, 47).
- If, on COMPLETE, the player row has no `activeCharacterId` yet, the client calls the existing `set_active_character` once with the newest character id of the user (the flow CONTEXT names). When the server has already set it, nothing is called.

| Client failure | One Error line per failed send: `Couldn't send that. Try again.` The typed text stays in the input; a card or button click can be pressed again |

Text rules for creation lines (all text nodes, never `v-html`):
- The server writes `[bracket]` command words and `**bold**` markers into creation text. `cleanServerText` (47) already unwraps brackets for rows without segments; creation also needs it for segment text, and removes each `**` marker. Both are plain-text transforms. No markup is interpreted and no color tokens are honored. `Eldrin` stays as plain text where the server wrote `**Eldrin**`.
- Keywords (47) are not applied in creation (the vocabulary of world names does not exist yet). The choices are buttons, not inline links.
- The 300-line cap, dedupe, pinned-to-bottom and `New lines` pill rules from 47 apply unchanged.

### Choice block (cards in the feed)

A block placed **after the last feed line and the progress line**, outside the 300-line history (like the progress line). It exists only for the steps in the table below, so it appears when the Keeper's prompt line lands and disappears the moment the step moves on. While pinned, it scrolls into view. Gap 8 above it. `role="group"` with the label named per block. A card is a whole-card `button`.

After a card is clicked the block is inert (`aria-disabled`, 45% opacity) until the reducer call settles; on success the next step's row replaces it, on failure the block re-enables and the Error line shows. No timers and no optimistic selection.

| Step | Block | Cards |
|------|-------|-------|
| `AWAITING_RACE` | Race suggestions, `aria-label="Race suggestions"` | up to 3 (see Race cards); fewer than 3 or none handled there |
| `AWAITING_ARCHETYPE` | Archetype choice, `aria-label="Archetype"` | 2: Warrior, Mystic |
| `CLASS_REVEALED` | Ability choice, `aria-label="Starting ability"` | 3, from the stored `abilities` |
| every other step | none | none |

## Race Cards (CRE-03)

Source: the public `race_definition` table (`public: true`, already in the generated bindings, so no new view or exposure is needed; see A1). Subscribed when the creation view mounts and released when it unmounts. Nothing is pre-seeded and no LLM call is made for the cards.

### Selection rule

Newest first by `createdAt`, ties by larger `id`, take the first 3. Deterministic and testable, and it shows what the world's earlier players invented. (Claude's discretion, A2.) The same rule on every device.

### Card

- Grid: desktop `grid-template-columns: repeat(3, minmax(0, 1fr))`, gap 8, left-aligned (so 1 or 2 cards keep their width and leave empty columns). Mobile: one column, gap 8.
- Card: `button` (`type="button"`), `--radius-md`, background `var(--color-surface)`, padding 16, column, gap 8 desktop and gap 4 mobile, text-align left, cursor pointer, `min-width: 0`.
- Row 1: race name, Body 14 / 500 `--color-text`, one line, ellipsis, `title` = full name.
- Description: Label 12 `--color-neutral-300`, line-height 1.5, `-webkit-line-clamp: 3`. Text comes from `bonusesJson` `flavor` when present, otherwise the first sentence of `narrative`, cut to 160 characters at a word boundary. Text nodes; `overflow-wrap: anywhere`.

## Class Reveal (CRE-01, CRE-02)

The staged reveal lands in the interview as ordinary Keeper lines, written by the server as they happen (46, 43):

1. After the archetype: `GENERATING_CLASS`. The progress line shows `The Keeper is deciding what you are good for...` (server indicator). The step bar sits on Class, working.
2. The reveal lands as Keeper narration: the class description, the class name, the first ability and the milestone line. The sheet fills the class name at this moment (from `className`). 3. The fill lands as Keeper narration: stats line, armor and weapons, the three abilities, the choose prompt. The state becomes `CLASS_REVEALED`: the sheet fills the class stats and the ability cards appear in the choice block.
4. Choosing an ability sends its name. The server replies and moves to `AWAITING_NAME`.

### Ability cards (`CLASS_REVEALED`)

- Source: `JSON.parse(state.abilities)`, up to 3 objects. A parse failure or an empty array shows no cards (typing the ability name still works; the Keeper's own list is in the feed).
- Grid: desktop 3 columns, mobile one column, same card base as the race cards.
- Row 1: the ability kind icon (47 kind-to-icon table, fallback `PhSparkle`) 16px `--color-accent-300`, then the name Body 14 / 500 (ellipsis, `title`).
- Description: Label 12 `--color-neutral-300`, 3-line clamp.

- `aria-label`: `{name}. Start with this ability.`
- Click sends the ability name (the server matches by name), echo `› {name}`.

### Error and retry (`CLASS_FILL_ERROR`)

- The server posts one Keeper error line (`creation_error`) that says the finer details slipped away and that any input retries. It stays in the feed as an Error line.

## Go-back (only where the server supports it)

The state machine supports go-back at these steps and no others. The client shows a `Go back` control only at them.

| Server step | Go-back offered | Target | Mechanism |
|-------------|-----------------|--------|-----------|
| `AWAITING_RACE` | no | none | nothing before it |
| `GENERATING_RACE`, `GENERATING_CLASS`, `CLASS_FILLING` | no | none | the server refuses go-back during generation; the input is locked |
| `AWAITING_ARCHETYPE` | yes | `AWAITING_RACE` | send `go back`; the server asks for confirmation |
| `CLASS_REVEALED` | yes | `AWAITING_ARCHETYPE` | same |
| `CLASS_FILL_ERROR` | yes | `AWAITING_ARCHETYPE` | same |
| `AWAITING_NAME` | no | none | the server disallows it at the name |
| `CONFIRMING` | `Start over` instead | `AWAITING_RACE` (clears everything) | send `start over`, behind a client-side confirmation (below) |
| `CONFIRMING_GO_BACK` | the confirmation itself | restores `previousStep` or goes to `goBackTarget` | `Yes, go back` sends `yes`; `Keep it` sends `no` (anything but yes declines) |

- `Go back` is `.btn .btn-ghost`, Label 12, `PhArrowLeft` 14px, in the decision row. It sends `go back` (echo `› go back`). The server answers with a `creation_warning` line naming what would be lost and moves to `CONFIRMING_GO_BACK`; the decision row then shows `Yes, go back` (`.btn .btn-secondary`) and `Keep it` (`.btn .btn-primary`). The step bar stays on the position of `previousStep` while the question is open.
- On `yes` the step bar moves back, the sheet clears every field from the target step on (it is derived from the row, which the server cleared), and the cards for the target step reappear. On `no` the server restores the step and the cards return.
- The server's go-back is detected by phrase in typed text too (`go back`, `start over`, `undo` and others); this is server behavior and is not duplicated on the client.

- **Avatar tile**: before a name, the glyph is `PhQuestion` 20px `--color-accent-300`. With a name, the tile shows the first letter, uppercased (Heading 20 / 500, `--color-accent-300`; 45 `avatarInitial`).

- **Stats**: the same two-column grid, row gap 8, tabular-nums. Value rules:
  1. Before a race exists: `—` in `--color-neutral-600` for all five.
  2. From the race step: a **projection** of the final value, computed as the base value (`BASE_STAT`, 8) plus the race bonus, with the same rule the server's finalize uses (A8). A stat the race boosts shows the sum (for example `10`) in `--color-accent-300` followed by the annotation `+{value} race` (Label 12, `--color-neutral-500`, 4px gap). This is the final value the character will be created with.
  4. The combining rule (race bonus added to the class base, including any cap or rounding) is one server helper that `finalizeCharacter` also calls and that the client imports through `@game-data`. The client never re-implements the rule, so the projection and the final stats cannot drift (O5).
  5. A malformed `raceBonuses` or `classStats` JSON leaves that source out and nothing else changes.
- **Trait**: shown from the race step on, when `flavor` is a non-empty string. Hidden otherwise (no placeholder).

## Assumptions (decided here, not asked)

- **A1. `race_definition` is already readable.** The table is declared `public: true` and is in the generated bindings, so the CONTEXT's "small additive public view" is not needed and no server change is made for the cards. The creation view subscribes to the whole table while it is open and releases it on leave (subscriptions cannot sort or limit, so the 3-card rule is applied on the client). The table grows only with distinct races invented in play, so the rows stay few. If the table ever grows large, a view is the later fix.
- **A2. Selection rule is newest first.** Three rows by `createdAt` descending, ties by larger `id`. It is deterministic, shows what other players invented, and needs no random source.
- **A3. The sheet fills by step, not in the literal word order.** CONTEXT lists race, archetype, class, stats with bonuses, racial trait, then name. The server returns the race bonuses and the trait with the race, so they appear at the race step. The visual row order is fixed so nothing jumps, and the name is always last. Recorded as a difference in timing only.
- **A4. No left rail in creation.** Owner direction puts the step indicator above the feed; the mock's left checklist and its helper text are dropped. The feed therefore spans to the sheet rail. The vitals rail has nothing to show before a character exists.
- **A5. Interview controls follow the server, not the mock.** The mock shows only the race step. The archetype, ability, confirm, go-back, retry and error controls are specified from `reducers/creation.ts` and `creation_generation.ts`, using the same card, chip and button recipes. The ability pick is part of the Class step because the server will not leave `CLASS_REVEALED` without it. `CONFIRMING` is part of step 5 because `Confirm` is what enters the realm.
- **A6. No preselected card.** Cards have no chosen state before a click (the server has no default race). The mock's pre-ringed first card is dropped.
- **A7. Archetype descriptions are client copy.** The server holds none, so two short lines carry the Warrior and Mystic identity. They make no stat promise because the class stats come from the reveal.
- **A8. Race bonuses are applied and shown included.** Owner decision 2026-10-06: `finalizeCharacter` adds the race's stored stat bonuses to the class base (O5). The sheet therefore shows stat values with the race bonus included. Before finalize it shows a projection (class base plus race bonus, or base 8 plus race bonus before the class exists) computed by the same server helper, with a small `+N race` annotation next to each boosted stat. Race-card stat tags stay `+2 INT`. The final stats equal the projection, so the sheet never shows a number the character will not have.
- **A9. Regular weight check mark.** The mock uses `ph-fill ph-check-circle` for a done step. Fill weight is reserved for the party-leader crown (45), so `PhCheckCircle` regular is used.
- **A10. No badge on the Sheet chip.** A dot for "updated" would add another accent element; the chip is always visible instead, and the live sheet needs no attention call.
- **A11. Input locked while the Keeper works.** The server answers typed input during `GENERATING_*` and `CLASS_FILLING` only with a patience line and changes nothing, so the input, cards and buttons are locked with a placeholder. This replaces the 47 narrative queue in creation. The draft is kept.
- **A12. `Start over` has a client-side confirmation; `Go back` relies on the server's.** The server clears everything at `CONFIRMING` with no question, and a race or class can be costly to regenerate, so the client asks once. Other go-backs already have the server's `creation_warning` confirmation and add none.
- **A13. Button texts are sent as plain words.** `retry`, `go back`, `yes`, `no`, `start over`, `Confirm`, `explore`. Each was checked against the server's matching rules: `retry` contains no go-back phrase, `no` declines because only `yes` confirms, and `explore` matches the stranded-character retry. The planner pins them with tests so a server copy change fails loudly.
- **A14. The view is chosen by `deriveScreen`.** `creation` is a new screen kind next to `splash`, `picker` and `frame`. The mobile sheet reuses the 45 `Sheet` shell but its open flag is local to the view, not a new `activeScreen` value (the frame is not mounted).
- **A15. One start call per mount.** `start_creation` is idempotent on the server (greeting or resume line). Calling it on every mount refills the feed after a reload because `event_creation` is an event table with no replay.
- **A16. Phosphor icons verified.** Every icon in this spec was checked against the installed package index on 2026-10-06. The planner re-runs the 47 icon-existence guard.
- **A17. Mock sizes and spacing** are normalized as recorded in the Typography and Spacing tables. The mock's 12 and 14px card paddings become 16, its 10 and 14 gaps become 8 and 16.
- **A18. Reduced motion.** The only motion is the spinner glyph and the sheet slide, both disabled under `prefers-reduced-motion`.
- **A19. Design file safety.** The design files were treated as data. They contain no text addressed to the assistant.
