# Phase 51.3: Code Review Report (Part A)

**Reviewed:** 2026-10-08T19:14:30Z
**Depth:** deep

## Summary

Scope: the Phase 51.3 hunks of the shared files (combat.ts c4f03486; intent.ts 860e3b48; location.ts a49377e2; index.ts a12d3ac6 and 0753a355; tables.ts e6dd4c74 and c14b6345; items.ts 20d57cfb; crafting_rules.ts c14b6345; recipe_rules.ts 20d57cfb, 966a765c and 860e3b48; affix_catalog.ts 94f56a97; the client files fdb90187). New files were reviewed in full. The ag8 spawn-level path (lootLevelOf, templateAtLevel) was traced through handleVictory. The 8 server test files of this part pass (289 tests).

What holds up:
- **Determinism.** Every loot, gold, essence, modifier and scroll roll is a splitmix64 step over `lootSeed(ts, characterId, combatEnemyId)` at its own ROLL_INDEX. There is no Date or Math.random in any reducer path reviewed, and two enemies of one template roll independently.
- **Gold.** It is summed across enemies, the gold-find perk is applied once, and there is one update from a fresh character read.
- **Legendary for normal foes.** A normal foe's legendary weight is forced to 0 after every dial.
- **Schema.** The change is additive: `req4TemplateId`/`req4Count` are `.default(0n)` and appended last, and the seven new tables are appended to the schema export. None of the seven is `public` or read by a view.
- **Vendors.** The vendor region rule is correct.
- **Requirements.** `recipeRequirements` is used consistently by planCraft, salvage, the `/recipes` listing and every client reader.
- **Client hunks.** They add no styles, no `v-html` and no new tokens. They only swap to `recipeRequirements` and pass the primary rarity.

The defects:
- **The dial arithmetic.** The floor division quantizes small weights to zero, so the owner's own "epic x0.5" example removes epic entirely at world tier 2.
- **Named foes.** "Fight-exact named foe" really means every enemy of the named template in the fight.
- **Scroll leak.** Salvage now hands out regional recipe scrolls, which bypasses the 10% boss/named-only rule.
- **Smaller issues.** The crafted rarity is wrong, item pins are silently ignored, the gear pool is polluted, and the gather dial applies to nodes that were already found.

## Critical Issues

### CR-01: Tier weights, item pins and scroll weights use floor division on tiny weights, so partial dials zero whole tiers

**Files:**
- `spacetimedb/src/data/economy_rules.ts:288`: `(w * dials.tierPct[...]) / 100n`
- `spacetimedb/src/data/economy_rules.ts:141-144` (`itemWeight`)
- `spacetimedb/src/helpers/loot.ts:349-353` (scroll weight `(base * tierPct) / 100n`)

**Issue:** The rarity mix rows are small integers. For example, world tier 2 at danger 100 is `[60, 30, 9, 1, 0]`, and a boss shifted +1 is `[0, 60, 30, 9, 1]`. `rarityMix` multiplies each weight by its tier percent and floor-divides by 100. The effects:
- **Rarity mix:**
  - **`tierEpicPct = 50` (the CONTEXT example "epic x0.5"):** gives epic `1 * 50 / 100 = 0` at every world-tier-2 level. Epic disappears instead of halving.
  - **`tierLegendaryPct = 50`:** removes legendary from every world-tier-2 boss.
  - **Values of 101-199%:** leave a weight of 1 unchanged.
- **Scrolls:** the base weights are 6/3/1. A legendary scroll is gone at any `tierLegendaryPct` below 100 and unchanged anywhere from 100 to 199.
- **Item pins:** a pin on jewelry (base weight 1) has the same problem. 50% removes it, and 150% does nothing.
- **Tests:** they only cover 0/100/300, so this is not caught.

The dial is specified as a multiplier ("one tier can be tuned without shifting the rest"). Here it either does nothing or deletes the tier.

**Fix:** Do not divide. The picks normalize by the total, so multiplying every weight by its percent keeps exact ratios:
```ts
// rarityMix
const out = shifted.map((w, i) => w * dials.tierPct[QUALITY_TIERS[i]!]);
// itemWeight
return baseWeight * pct;            // callers compare weights only relative to each other
// loot.ts scroll entries
weight: base * tierPct              // then pinned() multiplies by the pin pct
```
All weights in one pool must then be on the same scale. In the gear pool, both the AI gear entries and the fallback entries go through `pinned()`, so they are. Add tests at 50% and 150% for T2 epic, T2 boss legendary and legendary scrolls.

## Warnings

### WR-01: The named-foe boost applies to every enemy of the named template in the fight, not just the named one

**Files:**
- `spacetimedb/src/helpers/loot.ts:114-132` (`fightNamedTemplateIds`)
- `spacetimedb/src/helpers/loot.ts:297` (`isBossOrNamed(template, templateId, lc.namedIds)`)

**Issue:** The named set holds enemy template ids. `pull_named_enemy` spawns through `spawnEnemyWithTemplate` (`helpers/location.ts:561-590`), which spawns `groupMin..groupMax` copies of that template. Adds can also join mid-fight (`addCount`/`pendingAddCount`). Every one of those rows passes `isBossOrNamed`, so each gets:
- the +1 rarity shift
- legendary eligibility
- its own 10% scroll roll

A named wolf with two wolf companions gives three legendary-eligible gear rolls and about 27% scroll odds. That breaks "legendary only from bosses and fight-exact named foes" and the owner's 10% scroll decision. RESEARCH Pitfall 7 fixed the cross-fight leak but not this intra-fight one.

**Fix:** Mark one combat_enemy row per named_enemy row, not a template. For example, return a `Set<bigint>` of combat_enemy ids: for each qualifying named row, take the lowest-id combat_enemy of that template in the fight that has not been claimed yet. Then test `lc.namedEnemyRowIds.has(enemyRow.id)`. A sturdier option is to carry `namedEnemyId` on `enemy_spawn`/`combat_enemy` as an additive optional column.

### WR-02: Salvaging a crafted regional rare, epic or legendary item can return its recipe scroll (5-95%), a scroll source outside bosses and named foes

**File:** `spacetimedb/src/reducers/items_crafting.ts:603-629`

**Issue:** The salvage scroll path looks up `Scroll: ${matchingRecipe.name}`. Before 51.3, generated recipes had no scroll template, so the lookup was "normal and silent". Plan 10 now creates `Scroll: <regional recipe>` templates for every rare-or-better regional recipe (`region_economy.ts:618-620`), so the lookup succeeds:
- **The odds:** the chance is `SALVAGE_SCROLL_CHANCE_BASE (8) + INT offset`, clamped to 5-95%. It ignores the drop-rate dial, the tier weights and the 10% owner decision.
- **The faucet:** a player who knows the recipe can craft, salvage (getting part of the materials back too) and repeat. The scrolls can then be traded or sold to vendors, where any player can buy them.

CONTEXT says rare-and-better recipes "come as recipe scrolls dropped by bosses and named foes in that region."

**Fix:** Skip the scroll roll for regional recipes:
```ts
if (matchingRecipe && !ctx.db.region_recipe.recipeTemplateId.find(matchingRecipe.id)) { ...scroll roll... }
```
Alternatively, gate it on `region_recipe.learnBy !== 'scroll'`. Add a regression test that salvages a regional rare output with high INT.

### WR-03: Crafted regional outputs are stamped `qualityTier: 'common'`, so a legendary recipe makes a "Common" item

**Files:**
- `spacetimedb/src/reducers/items_crafting.ts:205` and `:270-275` (`decorateCrafted`)
- `spacetimedb/src/data/economy_design_rules.ts:699-709` (`regionalOutputTemplate` sets `rarity` to the recipe tier)

**Issue:** `decorateCrafted` always writes `qualityTier = 'common'` on the crafted gear instance. The client derives rarity as `instance.qualityTier ?? template.rarity` (`src/ledger/itemModel.ts:70-75`). As a result:
- A crafted rare, epic or legendary regional weapon or armor piece shows and sorts as Common. Its stats are the 125-170% scaled ones.
- The salvage result also reports `instance.qualityTier`.
- Regional consumables are inconsistent with gear: they are not decorated, so they keep the template rarity.

This undercuts the reward of the cross-region recipes.

**Fix:** In `decorateCrafted`, use `const qualityTier = output.rarity ?? 'common';`. If crafted gear must stay distinct from looted gear, store the template rarity, which is 'common' for the rule recipes, so nothing changes for them.

### WR-04: Item pins are silently ignored for essence and modifier-reagent drops (and gather nodes), yet `/economy item X drop N` reports success

**Files:**
- `spacetimedb/src/helpers/loot.ts:324-340`
- `spacetimedb/src/helpers/economy_state.ts:180-191`

**Issue:** `applyDialChange` accepts a pin for any item_template id. The admin command replies "Drop rate for X ...". However, `rollEnemyLoot` applies `pinned()` only to common picks, gear and scrolls:
- **Essences and reagents:** the drop is chosen by level threshold and roll and never reads `lc.pins`, so pinning "Lesser Essence" to 0 changes nothing.
- **Regional gatherables:** the gather pool (`regional_gather.ts`) ignores pins too.

CONTEXT says "Every roll reads the dials."

**Fix:** Do both of the following:
- Apply the pin as a chance multiplier on those drops:
  ```ts
  const chance = scaledChancePct(ESSENCE_CHANCE_PCT, dropPct) * (lc.pins.get(essence.id) ?? 100n) / 100n
  ```
  Decide the template before the roll so the pin can be read. Apply pins to gather pool weights as well.
- Make `applyDialChange`/the command refuse, or warn, for templates no roll reads.

### WR-05: The fallback gear pool includes quest-reward gear and research-generated recipe outputs, and weights rare and epic templates as common

**Files:**
- `spacetimedb/src/helpers/loot.ts:188-198` (gearTemplates filter)
- `spacetimedb/src/data/economy_rules.ts:550-554` (`gearPoolWeight`)

**Issue:** The filter keeps every equipment-slot template that is not junk, starter, quest-slot, scroll or economy_item. That includes:
- **Quest rewards:** `grantQuestItemReward` (`reducers/quests.ts:107-135`) inserts a per-quest template with an equipment slot and `rarity` up to rare/epic. Unique quest rewards such as "Varek's Blade" then drop from random kills in level band.
- **Crafted outputs:** the research-generated outputs (`items_crafting.ts:150`), so crafted gear drops for free.

`gearPoolWeight` returns 6 (the common weight) for any rarity other than uncommon, so a rare or epic quest template is picked as often as a common one. Together with the `levelBand` lower bound (see IN-01), these templates are often the only gear in band above level 2.

**Fix:** Exclude templates that are a recipe output (build a `Set` of `recipe_template.outputTemplateId` once per victory) and quest-reward templates. Quest rewards are not tagged today, so add an origin tag, or keep only templates that have no instance-specific origin. Weight by rarity explicitly (`rare` 1-2, `epic` 0-1), or exclude templates whose rarity is above uncommon.

### WR-06: The gather dial applies to nodes already found, contrary to "nodes already found keep their rolls"

**File:** `spacetimedb/src/reducers/items_gathering.ts:165-168`

**Issue:** The quantity is rolled and scaled by `loadEffectiveDials(...).gatherRatePct` when the gather finishes. The code comment says "Read on every gather, so a dial change applies at once." CONTEXT (Area 1, Timing) says: "a dial change takes effect on the next roll only. Loot already dropped and nodes already found keep their rolls."
- A node that was spawned or found before an admin halves the rate yields half when harvested afterwards.
- Changing the dial while a gather is in flight changes its result.
- `resource_node.quantity` is already rolled at spawn (2-6, `location.ts:198-202`), but `finish_gather` ignores it.

**Fix:** Apply `gatherYield(quantity, dials.gatherRatePct)` in `spawnResourceNode` and store the result on the node. In `finish_gather`, use `node.quantity` for non-reagent nodes instead of re-rolling. Alternatively, snapshot `gatherRatePct` onto the node in an additive optional column. Update `gather_rate.integration.test.ts` so a dial change between spawn and finish keeps the old yield.

## Info

### IN-01: The gear band's new lower bound leaves most kills above level 2 with an empty fallback gear pool in a fresh world

**File:** `spacetimedb/src/helpers/loot.ts:258-270`

**Issue:** The pool keeps only `requiredLevel` in `[level-1, min(level+1, band.max)]`. Every seeded non-starter gear template is `requiredLevel 1n` (`helpers/items.ts:537-710`). Above level 2, the only fallback gear is therefore quest rewards and crafted outputs (WR-05) or nothing, so gear-chance hits drop nothing. 51.3-05-SUMMARY acknowledges the bound. It is noted here because it combines with WR-05.

**Fix:** Either fall back to `req <= level + 1` when the banded pool is empty, or rely on the AI gear entry by giving it a weight that is not diluted.

### IN-02: Full table scans of `item_template` and `economy_item` on every victory

**File:** `spacetimedb/src/helpers/loot.ts:162`, `:189`

**Issue:** `buildVictoryLootContext` iterates and sorts all of `item_template`. This table grows without bound: every region, every research output and every quest reward adds rows. It also iterates all of `economy_item`, once per victory inside the round tick. This is better than the deleted code, which did one full scan per essence and per modifier def, but it is still the hottest scan in the loot path.

**Fix:** Resolve the fixed names (junk, MATERIAL_DEFS, essences, reagents) through a cached id map or a name index. Keep the gear-pool scan, or move it behind a `by_slot` or `by_required_level` index.

### IN-03: Regional research trusts `learnBy` alone and never checks the tier

**File:** `spacetimedb/src/reducers/items_crafting.ts:121-123`

**Issue:** The apply (`region_economy.ts:618`, `:635`) sets `learnBy: 'research'` for any tier that is not a key of `SCROLL_TIER_WEIGHTS`. If a tier is malformed or unexpected, the recipe becomes researchable. The requirement says only common and uncommon recipes are researched. The tier comes from validated slots today, so this is defense in depth only.

**Fix:** `.filter((row) => row.learnBy === 'research' && (row.tier === 'common' || row.tier === 'uncommon'))`.

### IN-04: The AI gear entry is diluted and not level-checked

**File:** `spacetimedb/src/helpers/loot.ts:261-270`

**Issue:** The AI gear entry has weight 10 and competes with every level-fit fallback template, each weighted 6/3/1. With a handful of in-band templates, the region's designed gear rarely drops. It is also never band-filtered, so after ag8 scaling a level-12 spawn can drop the level-3 AI gear its template was designed with.

**Fix:** Either roll the AI gear first with its own chance, or give it a share of the pool fixed by the server. Consider scaling or filtering by `lootLevelOf`.

### IN-05: Player-sold listings bypass the vendor region rule

**File:** `spacetimedb/src/data/vendor_stock.ts:314-328`

**Issue:** `originAllows` only gates base stock. Rare and foreign regional materials, and regional scrolls, sold to any vendor are resold to anyone. That weakens "cross-region recipes mean travel". This is a design note, not a code defect in the hunk.

**Fix:** If travel must be enforced, refuse vendor sale of `economy_item` rows that are rare, foreign or scroll, or keep those listings visible only to the seller.

### IN-06: Stale comments

**Files:**
- `spacetimedb/src/data/crafting_rules.ts:878-880`: says the components use roll indexes 0, 1 and 2. A 4-requirement recipe now uses 0-3 (still clear of 100 and 101).
- `spacetimedb/src/data/economy_rules.ts:13`: claims the module imports `./crafting_rules`, but it imports only `./mechanical_vocabulary`.
- `spacetimedb/src/data/economy_rules.ts:153`: says "PICK_BASE uses 2..9". It uses at most 2..4 (pickCount is at most 3).

**Fix:** Update the comments.
