# Phase 51.3 (part B): Code Review Report

**Reviewed:** 2026-10-08

## Summary

Part B covers the region_economy route, the reply validator, the idempotent apply, the chain hooks, the executor in-flight limit and `/economy` (admin command and reducers).

**What holds:**
- **Spend safety.** Both enqueues read `economy_dials.aiEnabled` first, and a missing row reads as off. Both enqueue with `budget: 'phase_only'`. That obeys the kill switch and the global ceiling, never touches a player row, and the per-player cap exemption only matters in `player` mode.
  - region_economy is absent from the sweep, smoke and no-auto-retry lists. Transient failures retry up to `LLM_MAX_ATTEMPTS` = 3, with backoff. That is bounded, not a storm.
  - Dedupe plus the once-only `region_economy` row stop repeat region jobs.
  - The background claim limit (`LLM_NARRATION_MAX_IN_FLIGHT`) keeps the last in-flight slot for gameplay.
  - The sweeper's 10-minute pending expiry routes through `applyLlmFailure` to `failRegionEconomy`, so a deferred job cannot leave a row stuck at `pending`.
- **The validator.** It never reads a number from the reply. Every count comes from `regionalRequirementPlan` and every id from the stored input.
  - It reads own properties only, so `__proto__` cannot reach it.
  - Handles are resolved only against the input. Names are cleaned (letters, apostrophes and hyphens), checked against reserved names and made unique. Descriptions are stripped of `[]{}<>` and control characters.
- **The apply.** It is guarded on `pending` and keyed on region plus slotKey and recipe key. Status `complete` is written last. A re-run reuses its own rows because `openBook` leaves them out of the name set. Legendary recipes write req4.
- **The prompt.** `REGION_ECONOMY_BLOCK` and the volatile builders match the APPROVED draft (sections 1, 2a, 2b) word for word. I checked the header, the variant lines, the recipe-rule table wording and the late-creature line, which has no trailing period. Every interpolated value goes through `w()` (`sanitizeWorldData`, single line, angle brackets escaped).
- **Admin gating.** `/economy` refuses any non-admin with one fixed line through `fail()`, before any lookup, so a non-admin learns nothing. The reducers call `requireAdmin` first.
- **Hooks.** Both chain hooks run after the generation write and inside try/catch.
- **Determinism.** No `Math.random` or `Date`; seeds and times come from ids and `ctx.timestamp`. This phase adds no new scheduled reducers.

**Snapshot-filter deviation (51.3-12, deviation 2): safe.**
- `dump()` deletes `economy_dials` only when the table is an empty array, the same rule already used for `llm_admin_state`. Any row the fill or late-enemy path wrote to `economy_dials` would still appear and break the snapshot.
- Any `llm_job`, `llm_dispatch` or `region_economy` row written with the switch off would also still appear, because those tables are not filtered.
- The `.snap` file is unchanged, so the filter hides no behavior change. The one thing it does not prove is that the hooks *read* the switch. `region_economy_chain.test.ts` and `economy_phase_contract.test.ts` cover that.

**Main concern: live evidence from job 8206.** The owner ran `/economy design` on region 1 (job 8206: completed, 32102 micro-USD). Two of its three recipe outputs are items whose slot contradicts their own name and description (WR-01, WR-02). The cause is in the validator and output builder, not the model. The model's reply was reasonable; the server repaired the category and picked the slot but kept the model's name and description.

## Warnings

### WR-01: Recipe category repair keeps the model's name and description, so "Salted Wayfarer Jerky" ships as chest armor

**File:** `spacetimedb/src/helpers/region_economy_validate.ts:249-263, 300-306`; output built at `spacetimedb/src/helpers/region_economy.ts:580-596` via `regionalOutputTemplate` (`spacetimedb/src/data/economy_design_rules.ts:688-750`)

**Issue (traced against live data, read-only SQL on local `uwr`):**

- **Job 8206's reply** for recipe `first`:
  ```json
  {"name":"Salted Wayfarer Jerky","category":"consumable","materials":["G1","D:E1"], "description":"Strips of cured meat rubbed with pan salt..."}
  ```
- **The region's locals:**
  - G1 = item 8195 "Pan Salt Cakes", kind `base`
  - G2 = 8196, kind `cloth`
  - G3 = 8197, kind `trinket`
  - D:E1 = 8198 "Crusted Chitin Plate", kind `hide`
  - No local has kind `edible`.
- **How the validator repairs it:**
  1. Line 253: `primary = listedLocals.find((l) => categoryForKind(l.kind) !== null)`. G1 (`base`) has no category, so the primary becomes D:E1 (`hide`).
  2. Line 255: `consumable` is not a primary category for `hide`, so `category = categoryForKind('hide')` = `armor`.
  3. Line 303 still takes the model's name (`names.take(field(entry, 'name'), 'output', cat)`), and line 305 takes the model's description.
- **The result:** in `region_economy.ts:580` the armor branch of `regionalOutputTemplate` turns it into item 8207 "Salted Wayfarer Jerky".
  - The item: slot `chest`, armorType `leather`, AC 3, with a food description.
  - Its economy_item kind is `armor`.
  - Its recipe 4099 (`region:1:r0`) has recipe_type `armor`.
- **Why it matters:** players get a "jerky" chest piece. Any region without an edible gatherable or drop can never produce a consumable, so every food-themed recipe the model writes gets this treatment.
- The same silent flip happens whenever the model's first usable handle disagrees with its category (for example `weapon` with `G2`=cloth listed first). The approved prompt asks for the main material first, but the validator does not prefer the model's category when choosing the primary.

**Fix:**
1. Prefer the model's category when choosing the primary. Search all locals, not only the listed ones, before flipping the category.
2. Change the category only when no local can serve it.
3. When the category does change, discard the model's name and description, because they describe the wrong thing. Use the rule name and rule description instead.

```ts
// region_economy_validate.ts, validateRecipe: primary and category
const wanted = RECIPE_CATEGORIES.indexOf(modelCategory) !== -1 ? (modelCategory as RecipeCategory) : null;
let primary =
  (wanted !== null ? listedLocals.find((l) => isPrimaryFor(wanted, l.kind)) : undefined) ??
  (wanted !== null ? locals.find((l) => isPrimaryFor(wanted, l.kind)) : undefined);
let category: RecipeCategory | null = primary ? wanted : null;
if (!primary) {
  primary = listedLocals.find((l) => categoryForKind(l.kind) !== null) ?? locals.find((l) => categoryForKind(l.kind) !== null);
  category = primary ? categoryForKind(primary.kind) : null;
}
if (!primary || category === null) return null;
const repaired = wanted !== null && category !== wanted;
// ...
return {
  index, tier,
  // A repaired category gets the rule name and rule description: the model's text described another item.
  name: names.take(repaired ? '' : field(entry, 'name'), 'output', category),
  category,
  description: repaired ? '' : cleanDescription(asText(field(entry, 'description'))),
  requirements: requirements.slice(0, MAX_RECIPE_REQUIREMENTS),
};
```

`regionalOutputTemplate` already falls back to a rule description (`made(...)`) on `''`, and `uniqueItemName('')` falls back to `<Region> Jerkin`, `<Region> Stew` and so on. A consumable with no edible local still cannot exist under this fix. That is correct, because the server cannot make food without an edible material, but the item then reads as what it is. Add a test with this live reply (G1 base, D:E1 hide, category consumable). It should give category `armor`, a rule name and an empty description, or `consumable` when an edible local exists anywhere in the region.

### WR-02: Armor recipe outputs take their slot from the recipe index, not from the item, so "Wickthread Sash" ships as legs

**File:** `spacetimedb/src/data/economy_design_rules.ts` (`regionalOutputTemplate`, armor branch: `const form = ARMOR_FORMS[index % ARMOR_FORMS.length]`); called from `spacetimedb/src/helpers/region_economy.ts:584-594` with `index: recipe.index`

**Issue:**
- Job 8206's recipe `second` was `{"name":"Wickthread Sash","category":"armor","materials":["G2","G1"],"description":"A woven sash of reed fiber, light across the shoulders..."}`.
- The category is valid and kept (G2 is `cloth`).
- The slot then comes from `ARMOR_FORMS[1 % 3]`, which is `legs` (`recipe_rules.ts:170-172`: chest, legs, boots). The result is item 8208, slot `legs`, cloth, AC 1, whose own description says "across the shoulders".
- The reply schema has no recipe slot, so neither the model's name nor its description affects the slot. Any armor recipe in slot index 1 or 2 has this chance of contradicting its own text.
- Item 8207 got `chest` only because it was index 0.
- Gear drops do not have this problem: they take the model's slot (`repairGear`). Recipe outputs do not.

**Fix:**
- **Without a prompt change** (the approved wording stays as is): choose the armor form from the cleaned output name's last word, and fall back to the index only when no word matches:

```ts
// economy_design_rules.ts
const ARMOR_SLOT_WORDS: Readonly<Record<string, string>> = {
  robe: 'chest', vest: 'chest', jerkin: 'chest', tunic: 'chest', cuirass: 'chest', coat: 'chest',
  mantle: 'chest', sash: 'chest', shirt: 'chest', hauberk: 'chest',
  trousers: 'legs', pants: 'legs', leggings: 'legs', greaves: 'legs', breeches: 'legs', kilt: 'legs',
  boots: 'boots', shoes: 'boots', sandals: 'boots', slippers: 'boots', treads: 'boots',
};
function armorSlotFromName(name: string): string | null {
  const words = asText(name).toLowerCase().split(/\s+/).filter(Boolean);
  for (let i = words.length - 1; i >= 0; i--) {
    const w = words[i].replace(/s$/, '');
    const hit = ARMOR_SLOT_WORDS[words[i]] ?? ARMOR_SLOT_WORDS[w];
    if (hit) return hit;
  }
  return null;
}
// armor branch:
const named = armorSlotFromName(input.name);
const form = (named && ARMOR_FORMS.find((f) => f.slot === named)) || ARMOR_FORMS[index % ARMOR_FORMS.length];
```

- **Fallback when the name gives no slot:** use the rule name and description as in WR-01, so the text cannot contradict the slot.
- **With a prompt change:** a stronger fix adds an optional `slot` (chest, legs, boots) to recipe entries in `REGION_ECONOMY_SCHEMA`. That changes the approved contract and wording, so it needs new owner approval, and this review does not propose wording.
- **Test:** add one with the live reply ("Wickthread Sash", index 1) that expects slot `chest`.
- **Existing data:** items 8207 and 8208 in local `uwr` keep their wrong slots. Repair them by hand or clear region 1's economy rows before the golden run, because the apply never rewrites an existing slotKey.

## Info

### IN-01: A caught throw in the fill hook can leave a paid job with no `region_economy` row

**File:** `spacetimedb/src/helpers/llm_apply.ts` (fill hook, `try { startRegionEconomy(...) } catch`); `spacetimedb/src/helpers/region_economy.ts:723-741`

**Issue:**
- A caught exception does not roll back writes already made. `llm_sweeper.ts` states this rule in its header.
- `startRegionEconomy` inserts the `llm_job` and dispatch rows (`enqueueLlmJob`) before `markRegionEconomyPending`. If the mark throws, the catch keeps the job, but no lock row exists.
- `applyRegionEconomyResult` then returns at line 541 (`!statusRow`), so the paid result is thrown away.
- This is unlikely today: the `exists` gate runs first, so the insert should not conflict.

**Fix:** Write the pending row before enqueueing, using a placeholder `jobId: 0n`, then update it with the real job id. On refusal, delete or roll back the row. Alternatively, have the apply accept a missing row when the job id is the region's current job.

### IN-02: The region apply and failure path do not check the job id against `region_economy.jobId`

**File:** `spacetimedb/src/helpers/region_economy.ts:540-541, 820-822`

**Issue:**
- The apply and `failRegionEconomy` act on any region-mode job for the region whenever the row is `pending`.
- Today the executor's stale and expired checks make a late result from an older job impossible. Still, the stored `jobId` is never used, and an older job's failure could mark a newer job's row `failed`.

**Fix:** Add `if (statusRow.jobId !== undefined && job.id !== undefined && statusRow.jobId !== job.id) return;`. This needs `id` added to `EconomyApplyJob` and `toApplyJob`.

### IN-03: The validator does not check the local secondary against SECONDARY_KINDS

**File:** `spacetimedb/src/helpers/region_economy_validate.ts:273`

**Issue:**
- `secondary = listedLocals.find((l) => l.ref !== primaryRef)` accepts any listed local, whatever its kind.
- Live recipes 4099 (hide + `base` salt, armor) and 4100 (cloth + `base` salt, armor) use a `base` secondary. That kind is not in `SECONDARY_KINDS.armor` (hide, cloth, metal).
- The kind fallback at lines 275-279 applies only when no listed local remains.

**Fix:** Prefer a listed local whose kind is in `SECONDARY_KINDS[cat]`, then the existing kind walk, then any listed local.

### IN-04: "No player text reaches this route" holds only loosely: enemy names created by npc_conversation are LLM-laundered player text

**File:** `spacetimedb/src/helpers/llm_apply.ts:888-899` (new enemy from `effect.targetEnemyName`, no length cap), which flows into `buildRegionEconomyVolatile` through `regionEconomyEnemyLines`

**Issue:**
- A player can steer the npc_conversation model into naming a quest enemy with instruction-like text. That name is stored on `enemy_template` and later sent to region_economy as "world data".
- `w()` keeps it to one line with angle brackets escaped, and the block tells the model that the data is never an instruction.
- The damage is limited: every number is server-owned and every output name and description is cleaned. The worst case is odd or offensive item names.

**Fix:** Cap and clean enemy names at creation (`cleanItemName`-style, around 40 characters), or apply a length cap per value in `regionEconomyEnemyLines`.

### IN-05: A late-creature job that fails or returns an unusable reply leaves the enemy on fallback loot with no retry path

**File:** `spacetimedb/src/helpers/region_economy.ts:794-811, 817-819`

**Issue:**
- Enemy mode records no status.
- `/economy design` re-runs only region mode, and only for a `failed` region.
- So the one paid enemy design can be lost for good. The fallback loot still keeps kills from being empty, as intended.
- Also, an apply whose reply leaves out creatures queues one enemy job per omitted enemy (`startLateEnemies`). That is bounded by the region's enemy count, but a lazy reply turns into several paid calls.

**Fix:** Optionally accept `/economy design <region>` on a complete region to run `startEnemyLoot` for its enemies that have no loot. Log the omitted count.

### IN-06: `/economy design` reports "No region by that name." for an existing region with no locations

**File:** `spacetimedb/src/helpers/economy_admin_commands.ts:401`

**Issue:** `no_region` also covers a region that exists but has no locations. That misleads the admin. It is not a leak, because the path is admin-only.

**Fix:** Give a separate line for the no-locations case, for example "That region has no places yet."
