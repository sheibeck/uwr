### Locked Decisions

**Round flow (RND-01, RND-02)**
- A round lasts at most 10 seconds. It resolves either when the deadline passes or as soon as every living player participant has chosen an action. A solo player who acts at once resolves the round immediately; there is no waiting out the timer.
- A player chooses through the existing `use_ability` reducer. While the player is in combat, the reducer records the choice for the current round instead of executing at once. Choosing again replaces the previous choice until the round resolves. The Phase 47 hotbar already calls `use_ability`, so it becomes the round-choice input with no client change.
- A player with no choice when the round resolves auto-attacks their current target. With no valid target, they attack the living enemy with the lowest id.
- Disconnected or AFK players are never waited on beyond the 10-second deadline, and they auto-attack under the same rule.

**Resolution order and timing (RND-03)**
- The order is deterministic. Player actions resolve in ascending character id, then enemy actions in ascending enemy id. Dead actors skip.
- In combat, cooldowns, effects and DoT/HoT count in rounds.
  - Rounds = ceil(seconds / 4), with a minimum of 1. This reuses the existing `EFFECT_ROUND_CONVERSION_MICROS` (4s) constant.
  - Effects and DoT/HoT tick once at the end of each round.
  - Out of combat, the real-time ability cooldowns are unchanged.
- An enemy ability with a cast or wind-up time is announced in round N and lands at the end of round N + ceil(castSeconds / 4), with a minimum of 1 round.
- Once rounds work, the real-time swing scheduling (weapon-speed swing timers, per-second `combat_loop` resolution) is removed, together with any code it leaves dead.
  - The v2.0 round experiment (commits `8a94bf47` and `74137f46`, reverted in quick-348) is a code reference.
  - `ROUND_TIMER_MICROS` and `SOLO_TIMER_MICROS` (30s) become 10s.

**Public round state (RND-04)**
- Add two public tables:
  - `combat_round`: combat id, round number, deadline timestamp, status.
  - `combat_round_choice`: combat id, character id, chosen ability template id or none for auto-attack, chosen-at timestamp.
- Both are keyed for lookup by combat id, so party members can see each other's choices for coordination.
- Schema changes are additive, so a local publish with `--break-clients` needs no `--clear-database`. If a non-additive change ever turns out to be needed, STOP and ask the owner, because clearing wipes the stored Anthropic key.
- Regenerate the client bindings. The Phase 47 client keeps working outside combat. Combat display is Phase 48.

**Narration (RND-05)**
- Big-moment triggers:
  - the first kill of the fight, plus any boss or named-enemy kill
  - a player's first drop below 20% HP in this fight (once per player per fight)
  - a boss or named enemy crossing 50% HP (the phase change)
- The end of the fight (victory or defeat) is also narrated. There is no fixed every-N-rounds summary.
- Per-encounter budget: at most 3 big-moment narrations plus 1 end narration per fight. The existing global narration budget threshold (`NARRATION_BUDGET_THRESHOLD`) still applies, so a refused enqueue is skipped silently, as today.
- Rounds never wait for narration. Narration lands in the feed when ready, tagged with its round number. The existing stale-narration age cut-off stays.
- Voice:
  - Reuse the Phase 46 owner-approved `combat_narration` JSON route, `COMBAT_NARRATION_SCHEMA` and combat route block, with no route-block or Bible change.
  - The per-call user text gains the moment type (`kill`, `near_death`, `phase`, `victory`, `defeat`) and its facts.
  - Collect any new per-call wording in a short `46.1-VOICE-ADDENDUM.md` for the owner's later review. It was auto-approved overnight, and the owner can revise it at the end-of-milestone pass.
- No paid LLM calls in this phase.

## Summary

Combat today is a real-time engine. `startCombatForSpawn` schedules a 1-second `combat_loop_tick`; `combat_loop` (reducers/combat.ts:2717-2819) swings players on weapon-speed timers (`nextAutoAttackAt`), swings enemies on role timers, runs effects and checks victory/defeat. Players act through `use_ability` (reducers/items.ts:778), which executes instantly or via `character_cast`. A v2.0 round experiment was reverted in quick-348, but it left most of the schema behind: `combat_round`, `combat_action`, `combat_narrative` and the scheduled `round_timer_tick` all still exist (tables.ts:2008-2073), `resolve_round_timer` is a registered no-op (reducers/combat.ts:2706), and `clearCombatArtifacts` already deletes round and action rows. The effect, DoT and HoT code already counts `roundsRemaining`. So the phase is mostly a re-wiring job, not a green-field build.

The important findings for planning are these. (1) `combat_round` and `combat_action` already cover RND-04 almost exactly, so the cheapest additive path is to reuse them instead of adding `combat_round_choice`. (2) The official SpacetimeDB automatic-migration rules forbid removing non-empty tables, removing or modifying columns, and adding columns without defaults, so the real-time columns (`nextAutoAttackAt`) must stay, new columns must be defaulted and last, and `combat_loop_tick` may be dropped only if it is empty at publish time. (3) Scheduled reducers are callable by clients in this codebase (the executor guards with `ctx.sender` against `ctx.databaseIdentity`), so the new round tick reducer must carry the same guard. (4) The effect machinery has two real-time leftovers that conflict with rounds: DoT damage fires only when `roundsRemaining % 3 === 0`, and enemy stun stores an expiry time in `magnitude` with `roundsRemaining: 0`, which makes stuns inert today. (5) Narration needs no route change: `buildCombatNarrationVolatile` already branches on `narrativeType`, so the new moment types are a new per-call builder only. The "global narration budget" in CONTEXT is actually enforced by `enqueueLlmJob`'s budget refusal; `NARRATION_BUDGET_THRESHOLD` and `MAX_COMBAT_NARRATIONS` are unused constants.

**Primary recommendation:** Keep one scheduled `round_timer_tick` per combat, resolve early inline inside the choosing reducer (cancel by `scheduledId`, then insert the next tick), reuse `combat_round` and `combat_action` for RND-04, add only defaulted last-position columns for rounds-based cooldowns and wind-ups, add one new private `combat_moment` table for the once-per-fight flags and the 3+1 budget, and make the whole engine testable through a small pure `combat_rounds.ts` module plus a captured-reducer integration test.

### Pattern 1: One tick per combat, cancel and replace
**What:** Exactly one `round_timer_tick` row exists per active combat. Early resolution deletes it by `scheduledId` and the resolver inserts the next one. The tick reducer ignores stale ticks.
**When to use:** Every round boundary.
**Example:**
```typescript
// Source: this repo's own precedent (clearCombatArtifacts deletes by scheduledId; ScheduleAt.time as in helpers/scheduling.ts)
// and the official doc "Scheduled reducers: the row is deleted after execution" [CITED: spacetimedb.com/docs/tables/schedule-tables]
export function scheduleRoundTick(ctx: any, combatId: bigint, roundNumber: bigint): bigint {
  const deadline = ctx.timestamp.microsSinceUnixEpoch + ROUND_TIMER_MICROS;
  ctx.db.round_timer_tick.insert({ scheduledId: 0n, scheduledAt: ScheduleAt.time(deadline), combatId, roundNumber });
  return deadline;
}
export function cancelRoundTick(ctx: any, combatId: bigint, exceptScheduledId?: bigint): void {
  for (const row of [...ctx.db.round_timer_tick.iter()]) {           // or by_combat if the index is added
    if (row.combatId !== combatId) continue;
    if (exceptScheduledId !== undefined && row.scheduledId === exceptScheduledId) continue; // never delete the running row
    ctx.db.round_timer_tick.scheduledId.delete(row.scheduledId);      // PK is scheduledId, never .id
  }
}
```

### Pattern 2: Guarded, stale-proof tick reducer
```typescript
// Guard precedent: reducers/llm_executor.ts:37 and helpers/llm_executor.ts:620
scheduledReducers['resolve_round_timer'] = spacetimedb.reducer(
  'resolve_round_timer', { arg: RoundTimerTick.rowType }, (ctx, { arg }) => {
    if (ctx.sender.toHexString() !== ctx.databaseIdentity.toHexString()) return; // clients can call scheduled reducers
    const combat = ctx.db.combat_encounter.id.find(arg.combatId);
    if (!combat || combat.state !== 'active') return;
    const round = currentRound(ctx, arg.combatId);
    if (!round || round.roundNumber !== arg.roundNumber || round.state !== 'action_select') return; // stale tick
    resolveRound(ctx, arg.combatId, round, { firedScheduledId: arg.scheduledId });
  });
```

### Pattern 3: Choice record, then early resolve inside the reducer
```typescript
const round = currentRound(ctx, combatId);
upsertChoice(ctx, combatId, round.roundNumber, character, abilityTemplateId, targetCharacterId); // replace, never duplicate
if (allActiveChosen(ctx, combatId, round.roundNumber)) {
  cancelRoundTick(ctx, combatId);
  resolveRound(ctx, combatId, round);   // schedules round N+1 unless the fight ended
}
```

### Pattern 4: Moment detection from a before/after snapshot
Snapshot every enemy and player HP at round start, resolve, then diff. This is independent of where damage came from (ability, auto-attack, DoT, pet). Attribute the killing blow by checking enemy HP after each player action in the loop, recording `{killerName, abilityName}` only for the per-call text.

### Anti-Patterns to Avoid
- **`ctx.db.round_timer_tick.id.delete(...)`**: the experiment did exactly this (`timerTable.id.delete(row.scheduledId)`, diff of 74137f46). Scheduled tables key on `scheduledId` (project memory). The strict test mock throws on an unknown accessor.
- **Relying on iteration order**: `filter()` and `iter()` order is not a contract. Sort choices, players and enemies by id (bigint compare) before resolving.
- **Destructuring a late-bound dep at registration**: `registerItemReducers` runs before `registerCombatReducers` (reducers/index.ts). A function assigned in the combat registrar must be read as `deps.submitCombatChoice(...)` at call time.
- **Deleting the currently running schedule row** from inside the tick reducer (skip `firedScheduledId`).
- **Applying the conversion inside `addCharacterEffect`/`addEnemyEffect`**: both already take rounds (`roundsRemaining`) and `combat.test.ts` pins values passed straight through. Convert at the `resolveAbility` call sites that read `ability.effectDuration`.

### 2. The v2.0 round experiment (8a94bf47, 74137f46, reverted by quick-348)

**What survived the revert (reusable now):** tables `combat_round` (id, combatId, roundNumber, state, timerExpiresAtMicros, narrationCount), `combat_action` (id, combatId, characterId, roundNumber, actionType, abilityTemplateId?, targetEnemyId?, targetCharacterId?, submittedAt), `combat_narrative`, scheduled `round_timer_tick` (scheduledId, scheduledAt, combatId, roundNumber); constants; helpers `scheduleRoundTimer`, `createFirstRound`, `convertDurationToRounds` (helpers/combat.ts:1503-1532); `resolve_round_timer` no-op; `clearCombatArtifacts` cleanup of ticks, actions and rounds (:368-381).

**Reusable shape from the reverted `resolveRound`:** state sequence `action_select` to `resolving` to `resolved`; fill auto-attack for missing choices; players then enemies then pets then effect tick then pending adds then retarget then victory/defeat then next round with `narrationCount` carried; per-round effect tick; `submit_combat_action` input shape (`characterId`, `actionType`, `abilityTemplateId?`, `targetEnemyId?`, `targetCharacterId?`).

**Conflicts and defects to NOT copy:**
1. `timerTable.id.delete(row.scheduledId)` wrong accessor (the project-memory bug); use `scheduledId.delete`.
2. Calls `executeAbilityAction({ actorType: 'player', abilityKey: ability.name, ... })`; today's signature is `actorType: 'character'` with `abilityTemplateId` (helpers/combat.ts:1435).
3. Calls `calculateFleeChance(ctx, character)`; the real function takes a danger multiplier (`helpers/combat_perks.ts:259`).
4. Resolves actions in insertion (autoinc) order, with defaulted actions appended last, so the order is not "ascending character id".
5. Early resolution inserted an immediate `round_timer_tick` (async, next transaction) instead of resolving inline.
6. Checks cooldowns against wall-clock micros; 30 s solo and group timers; bosses get two actions (`isBoss ? 2 : 1`), which CONTEXT does not authorise.
7. Executes enemy abilities instantly (no wind-up), and ticks DoT every 3rd round tick.
8. The experiment's `resolve_round_timer` had no caller guard (a client could force a resolution), and its `flee` action path relied on the wrong `calculateFleeChance` signature (item 3).

**Migration rules, from the official doc** [CITED: spacetimedb.com/docs/databases/automatic-migrations]:
- Always allowed: add tables, add indexes, add reducers, private to public.

- Forbidden (needs a workaround, i.e. a clear): remove NON-EMPTY tables, remove or modify existing columns, add columns without defaults, insert columns mid-table, change whether a table is scheduled, add unique or primary-key constraints.

### 4. Scheduling (SpacetimeDB 2.10)

- One-shot scheduled reducers: the row is "deleted after execution, so the row is visible in the schedule table while the reducer runs" [CITED: spacetimedb.com/docs/tables/schedule-tables]. The doc does not describe cancellation; the repo cancels by deleting the row (CLAUDE.md "Cancel a job by deleting the row", `clearCombatArtifacts` does it). Delete by `scheduledId`.
- The doc does not say clients cannot call scheduled reducers, and this repo treats them as forgeable (`llm_run` and `reducers/llm_executor.ts:37` compare `ctx.sender` with `ctx.databaseIdentity`). The current `resolve_round_timer`, `combat_loop` and `resolve_pull` have no guard. The new tick reducer must have one. The mock supports it: `createMockCtx({ sender, databaseIdentity })` (helpers/test-utils.ts:180-186).
- Cancel and replace: the early path deletes the pending tick and inserts the next; the tick path skips its own running row. The stale-tick guard (`arg.roundNumber === round.roundNumber && round.state === 'action_select'`) makes a failed cancel harmless.
- Determinism: use only `ctx.timestamp` and ids for seeds (existing style: `nowMicros + character.id * 37n + target.id`); add `roundNumber * 104729n` to the seed so successive rounds decorrelate when the clock is coarse. No `Date.now`, no `Math.random`, no iteration-order assumptions (sort by id). Early resolution uses the choosing reducer's `ctx.timestamp`; that is fine, the transaction is still deterministic.
- Failure behaviour is unproven: if a scheduled reducer throws, whether SpacetimeDB still removes its row is not documented. Treat "a combat with no tick row" as possible and repair it through `ensureRound` on the next player action `[ASSUMED]`.
- The reducer transaction does all of resolution, victory, loot and the narration enqueue at once. That is the same work `combat_loop` does today, so cost is comparable.

### 5. Converting combat time to rounds

`secondsToRounds(s) = max(1, ceil(s / 4))`, expressed with `EFFECT_ROUND_CONVERSION_MICROS` and `MIN_EFFECT_ROUNDS` (data/combat_constants.ts:10-11). The existing `convertDurationToRounds` truncates (floor); `combat.test.ts:149-152` pins "truncates partial rounds" (10 s gives 2). Change it to ceil (10 s gives 3) and update that test. For the prompt-range values: cooldownSeconds 4-12 gives 1-3 rounds; effectDuration 9-12 gives 3; stun 3 gives 1; default effect durations 3, 4, 5, 9, 30, 180 give 1, 1, 2, 3, 8, 45.

**Where to apply:** at every `ability.effectDuration ?? N` read in `resolveAbility` (helpers/combat.ts:571, 610, 632, 683, 720, 858, 934, 958, 1004, 1014, 1029, 1046), in `executePetAbility`'s hard-coded bleed (:1423), and in `combat_perks.ts:109,237` (those use `ceil(duration / 3)`; switch to the shared helper). Power scaling (`getAbilityMultiplier`, mana cast floor) stays in seconds.

**Prompt text is untouched:** the approved ability prompts say "Combat rounds are 3 seconds ... durations of 9-12 give 3-4 ticks" (data/llm_layers.ts:280, 372, 400). Under ceil(s/4), 9-12 s gives 3 rounds, which the wording still serves; do not edit approved blocks.

**Cooldowns, same table or new column:** use the same `ability_cooldown` row with the new defaulted `roundsRemaining` column.
- In combat the authority is `roundsRemaining`; `use_ability` checks `roundsRemaining > 0` instead of the wall clock. Out of combat nothing changes.
- On use in round N set `roundsRemaining = secondsToRounds(cooldownSeconds) + 1`, and decrement every cooldown row at the end of each round (including round N). Result: a cooldown of C rounds blocks the next C rounds, and the stored number equals "rounds until usable" (what Phase 48 will show). Do not apply the 1.5 s GCD in combat (one action per round already). `[ASSUMED]` the "blocks the next C rounds" meaning; the alternative (usable again in round N+C, so a 4 s cooldown is no cooldown at all) is simpler but makes the minimum-1-round rule meaningless. See Open Question 1.
- Keep the Phase 47 hotbar truthful with no client change: whenever a round writes or rewrites a cooldown row set `startedAtMicros = now` and `durationMicros = roundsRemaining * ROUND_TIMER_MICROS` (an estimate), and delete the row when `roundsRemaining` reaches 0. The client then shows "cooling" exactly while the server refuses, with only the sweep animation approximate.
- Conversion at the boundaries: at combat start convert each participant's live wall-clock cooldown to `ceil(remaining / 4 s)` rounds; at fight end (in `clearCombatArtifacts`, which today only deletes expired rows at :419-424) convert leftover rounds back to `durationMicros = rounds * 4 s` from now, so cooldowns carry across the fight boundary.
- Client fixture risk: adding `roundsRemaining` changes the generated `AbilityCooldown` row type. The two client fixtures that build cooldown rows (src/hotbar/HotbarRow.test.ts:55-62, src/frame/AppFrame.populated.test.ts:150-157) are untyped literals; run `pnpm exec vue-tsc -b` after regeneration and add `roundsRemaining: 0n` to them if it complains (test-only touch).

**Enemy abilities:**
- Cooldown: `combat_enemy_cooldown.readyAtRound = N + secondsToRounds(cooldownSeconds) + 1` (same meaning as players).
- Wind-up: when an enemy picks an ability with `castSeconds > 0`, insert a `combat_enemy_cast` row with `announcedRound = N`, `landsAtRound = N + max(1, ceil(castSeconds / 4))` and the chosen target, log an announcement, and skip all other actions for that enemy until it lands. It lands in the landing phase at the end of round `landsAtRound` (after enemy actions, before effect ticks), re-validating that the enemy is alive and the target is valid (retarget by the ability's `targetRule`, else it fizzles with a log line). Abilities with `castSeconds = 0` resolve at once. World-gen creates caster `Bolt` with `castSeconds: 2n` (helpers/world_gen.ts:847-856), so caster enemies will wind up for one round `[VERIFIED: world_gen.ts]`.
- Stun: store `roundsRemaining = secondsToRounds(effectDuration)` with `magnitude 1n` (drop the expiry-micros representation, helpers/combat.ts:268-290), skip a stunned enemy's whole action, and cancel its pending wind-up. This also repairs today's inert stun. `[ASSUMED]` interrupt-on-stun is the intended counterplay.
- Effect ticks: remove the `% EFFECT_TICK_SECONDS` gate so DoT/HoT fire every round. Keep the immediate first DoT tick on application (`addCharacterEffect`, helpers/combat.ts:239-253).
- Pets: act once per round after all players and before enemies, ascending pet id; ability use when `round % secondsToRounds(abilityCooldownSeconds ?? 10) === 0` (stateless, no schema). `[ASSUMED]`
- Pending adds: arrive at round `N + 2` (`PULL_ADD_DELAY_ROUNDS`) via `arriveAtRound`; update the "arrive in Ns" text to rounds.
- Out-of-combat effects: they only decay inside `tickEffectsForRound` today (the `tick_effects` and `tick_hot` reducers are no-ops), so out-of-combat buffs persist until a fight. Pre-existing; out of scope, mention to the owner.

### Round resolution order (one transaction, inside `resolveRound`)
1. Mark round `resolving`; snapshot HP (players and enemies) and effects count for moment detection.
2. Player actions in ascending character id over `active` participants with HP > 0. A choice row's ability executes through `executeAbilityAction({ actorType: 'character', ... })` inside try/catch; any failure (cooldown, mana, no target, wrong state) logs through `fail(ctx, character, msg, 'combat')` and falls back to `processPlayerAutoAttackForRound`. No choice: auto-attack. Ability target for enemy-targeted abilities is `character.combatTargetEnemyId` at resolution (as `findEnemyTarget` already does); the choice row stores the target for display. Auto-attack target: current target if alive, else lowest living enemy id.
3. Skip the enemy phase and effect ticks if every enemy is already dead; go to victory.
4. Pets, then enemies in ascending enemy id (skip dead, stunned, winding up), then wind-up landings (ascending enemy id).
5. Effects, DoT, HoT, cooldown decrements, pending adds, retarget.
6. Victory check, then defeat check (existing `handleVictory` and `handleDefeat`, unchanged signatures).
7. Moment detection and enqueue (skipped on the final round).
8. Mark resolved, delete this round's `combat_action` rows, insert round N+1, schedule its tick.

Dead actors skip at the moment they would act. A fleeing participant (`status: 'fleeing'`) is neither waited on nor attacked; keep today's flee behaviour but make `flee_combat` call the same early-resolution check (if the fleeing player was the last unchosen one, or no `active` participant remains, resolve now instead of waiting up to 10 s).

## Common Pitfalls

### Pitfall 1: Wrong primary key on scheduled tables
**What goes wrong:** `ctx.db.round_timer_tick.id.delete(...)` throws "Cannot read properties of undefined".
**Why:** scheduled tables key on `scheduledId`. The v2.0 experiment did this.
**Avoid:** `scheduledId.delete`; run tests with `createMockCtx({ strict: true })` so a bad accessor throws.
**Warning sign:** a tick that never cancels, or a TypeError on early resolution.

### Pitfall 2: Persisted-table columns without defaults, or not last
**What goes wrong:** publish refuses the migration and only a clear fixes it (the Anthropic key is wiped).
**Avoid:** every new column on `ability_cooldown`, `combat_enemy_cooldown`, `combat_enemy_cast`, `combat_pending_add`, `combat_round` uses `.default(...)` and is the last column; verify with a recorder test; do not copy the optional-no-default pattern from the event tables.

### Pitfall 3: Dropping or modifying real-time columns
**Avoid:** keep `nextAutoAttackAt` on `combat_participant` and `combat_enemy`; write `0n`.

### Pitfall 4: Dropping `combat_loop_tick` while a fight is active
**Avoid:** pre-publish check that the table is empty (see section 3); never publish with an active fight in the owner's local DB.

### Pitfall 5: Forgeable scheduled reducer
**Avoid:** the module-identity guard and the stale-tick guard; add a forged-call test.

### Pitfall 6: Late-bound deps
`registerItemReducers` runs first. Read `deps.submitCombatChoice` inside the reducer body, never in the destructuring header.

### Pitfall 7: Iteration order and the "ascending id" contract
Sort explicitly. Build the ordered list once per round from a sorted copy of participants, not from `combat_action` row order.

### Pitfall 8: Target validation gap
Today `use_ability` passes `targetCharacterId` straight to `resolveAbility` for any character id (a heal or buff on a stranger or another fight). In combat, require the target to be an `active` participant of the same combat; reject with `fail(ctx, character, msg, 'combat')`.

### Pitfall 9: Mixed units
Out-of-combat cooldowns stay wall-clock; in-combat uses rounds. Convert at combat start and in `clearCombatArtifacts`, and test both directions. A cooldown row with `roundsRemaining > 0` must never be removed by the wall-clock "expired" cleanup (reducers/combat.ts:419-424, 1417-1421).

### Pitfall 10: Narration that blocks or double-fires
Fire-and-forget only. One moment per round, none on the final round, outro always separate; a refused enqueue must not throw (wrap like the outro's try/catch).

### Pitfall 11: Stun and DoT leftovers
Convert stun to rounds and drop the `% 3` gate in the same change as the round conversion, or stuns stay inert and DoTs tick only every third round.

### Pitfall 12: Game balance shifts
One swing per player per round ignores weapon speed (slow weapons with larger hits become strictly better than fast ones), in-combat regen still runs on the 8 s wall clock while early rounds take seconds, and rounds resolve far faster than the old 1 s loop could swing. Not a blocker; list for the owner (Open Question 3).

## Code Examples

### Seconds to rounds (pure, testable)
```typescript
import { EFFECT_ROUND_CONVERSION_MICROS, MIN_EFFECT_ROUNDS } from '../data/combat_constants';
export function secondsToRounds(seconds: bigint): bigint {
  const micros = seconds * 1_000_000n;
  const rounds = (micros + EFFECT_ROUND_CONVERSION_MICROS - 1n) / EFFECT_ROUND_CONVERSION_MICROS; // ceil
  return rounds < MIN_EFFECT_ROUNDS ? MIN_EFFECT_ROUNDS : rounds;
}
export const windupRounds = (castSeconds: bigint): bigint => (castSeconds > 0n ? secondsToRounds(castSeconds) : 0n);
```

## Open Questions

1. **Cooldown meaning (A1).** Recommend "blocks the next C rounds". Decide before the plan fixes the stored value (C + 1 versus C).
2. **Explicit auto-attack and flee as round actions (A8).** The new reducer is recommended. Flee currently never completes (status `fleeing` is never resolved); recommend keeping that behaviour in 46.1 and only making flee trigger the early-resolution check. A real flee roll (`calculateFleeChance(dangerMultiplier)`) is a follow-up.
3. **Balance.** Weapon speed becomes irrelevant, resource regen is still wall-clock, and rounds resolve faster than the old loop. Recommend shipping as specified and reviewing at the milestone-end play pass.
4. **Boss and named detection.** `isBoss` is never set. Recommend the pure `isBossOrNamed` helper now and a follow-up that sets `isBoss` (world gen or quest-invented enemies).
5. **`combat_loop_tick` removal.** Needs an empty table. Recommend the pre-publish check; if not empty, end the fight first.
6. **Naming.** Confirm reuse of `combat_action` for the choice table (A6).

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Client calls the scheduled round reducer to force or skip rounds | Tampering | `ctx.sender` equals `ctx.databaseIdentity` guard plus stale-tick check |

## Project Constraints (from CLAUDE.md)

- Reducers are transactional and deterministic: no filesystem, network, timers or random; read data through tables.
- `ctx.sender` is the authenticated principal; never trust identity arguments.
- Scheduled tables use `scheduledId` as the primary key; delete a scheduled job by deleting its row; the `scheduled:` option takes a function reference.
- Tables take `table(OPTIONS, COLUMNS)`; indexes belong in OPTIONS with `algorithm: 'btree'`; reducer calls use object syntax; use `ctx.db.<camelCase table>`; insert returns the row and auto-inc ids need a `0n` placeholder.
- Do not edit generated bindings; regenerate with `pnpm spacetime:generate`.
- Do not invent SpacetimeDB APIs. Smallest change necessary; do not touch unrelated files.
- Feature checklist: tables, reducers, client subscription, client call, client render. For this backend-only phase the client wiring is deferred to Phases 47 and 48 by decision; confirm the existing `useAbility` call is the only hotbar entry.
- Project memory: prefer `fail()` over `SenderError` where a character is available; the server is the source of truth (never duplicate server constants on the client); greenfield, no compat shims, no backups; never publish to maincloud; local publish only; `--clear-database` only if the schema truly requires it and then only with the owner; unit tests are required for every change; defer UAT to milestone end.
- Local publish command (exact): `spacetime publish uwr -p spacetimedb --server local --break-clients < /dev/null`, then `pnpm spacetime:generate`. (Research did not run it.)
