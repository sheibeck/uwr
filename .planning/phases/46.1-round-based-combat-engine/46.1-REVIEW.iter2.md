# Phase 46.1: Code Review Report

**Reviewed:** 2026-10-06
**Depth:** standard
**Files Reviewed:** 20
**Status:** issues_found

## Summary

The round engine is mostly sound. Everything on the focus list held up under a trace:

- **Lifecycle:** one tick per fight, cancelled and re-armed inside `resolveRound`. A tick is stale by round number and state, so there is no double resolution and no lost round on the normal path.
- **Ordering:** players, then pets, then enemies, in ascending id. Wind-up cleanup happens in the same pass.
- **Round cooldowns:** an ability used in round N is choosable again from round N + C. I traced C = 1, 2 and 3.
- **Flee:** it is a round choice and follows the quick-123 rules.
- **Security:**
  - Ownership goes through `requireCharacterOwnedBy`.
  - `targetCharacterId` and `targetEnemyId` are validated against the same fight, both at submit and again at resolution.
  - `resolve_round_timer`, `combat_loop` and `resolve_pull` are all guarded by the module identity.
  - The narration budget is bounded at 3 moment rows (written before the enqueue) plus 1 outro, and the outro is skipped when nobody is left in the fight.
- **Migration:**
  - Every new persisted column is `.default(0n)` and last.
  - `combat_loop_tick` is retained.
  - Every insert site writes the new columns.
  - The generated bindings contain no surprises beyond the accepted `CombatMoment` type.
- **Tests:** vitest over `src/helpers`, `src/reducers`, `src/schema` and `src/data` gave 3667 passes and 2 failures. Both failures are in `measurement.results.test.ts`, which looks for a missing `.planning/phases/39-*` directory. That is an environmental, pre-existing failure and unrelated to this phase.

The problems found are:

- one security gap in the same class the phase set out to close (adjacent scheduled reducers that remain callable by any client);
- a fault-tolerance gap that can leave a fight permanently unresolvable;
- two correctness defects that the round model makes more visible than the old per-second loop did.

## Critical Issues

### CR-01: Self-rescheduling scheduled reducers stay callable by any client (`regen_health`, `tick_casts`)

**File:** `spacetimedb/src/reducers/combat.ts:1343` (`regen_health`), `:1719` (`tick_casts`); also `:1233` (`respawn_enemy`), `:1586` (`tick_bard_songs`)

**Issue:** CONTEXT scoped the module-identity guard to `resolve_round_timer`, `combat_loop` and `resolve_pull`. Those three are guarded correctly. The sibling scheduled reducers in the same file have no `ctx.sender` check. Clients can call scheduled reducers directly, and the arg is not validated against the table.

- `regen_health` ends with an unconditional `health_regen_tick.insert(... +8s)`.
- `tick_casts` ends with an unconditional `cast_tick.insert(... +200ms)`.

Each forged call therefore forks one more perpetual chain:

- Any authenticated client can multiply the global regen rate. This applies in combat too, and wall-clock regen is the only sustain left outside abilities now that weapon speed no longer paces fights.
- Any authenticated client can grow the 200 ms cast chain without bound, which is a server load amplifier (DoS).

The problem predates the phase, but `tick_casts` was edited in this phase (the "cast interrupted by combat" branch) and this phase made regen the sole wall-clock sustain. `respawn_enemy` lets a client spawn enemies on demand, up to the cap check. `tick_bard_songs` is inert today because `active_bard_song` is never inserted.

**Fix:** add the same guard as `llm_run` at the top of each of these reducers.

```ts
if (ctx.sender.toHexString() !== ctx.databaseIdentity.toHexString()) return;
```

Alternatively, make the reschedule idempotent: before inserting, skip if a pending `health_regen_tick` or `cast_tick` row already exists.

## Warnings

### WR-01: A throw inside `resolveRound` strands the fight; the player cannot even flee

**File:** `spacetimedb/src/reducers/combat.ts:2981-3125`

**Issue:** The enemy turn is wrapped in `try/catch` ("one failing enemy can never roll back the round"). Nothing else in the resolver is:

- `processPlayerAutoAttackForRound`
- `processPetCombat`'s `resolveAttack` call
- `tickEffectsForRound`
- `processPendingAdds`
- the cooldown decrement
- `handleVictory` / `handleDefeat`

`processPendingAdds` calls `addEnemyToCombat`, which throws `SenderError('Enemy template missing')` when a pending add's template is gone. The loot and quest work in `handleVictory` can also throw.

A throw rolls back the whole reducer, which has two consequences:

- **Timer path:** the round never advances. The firing tick is consumed, and no new tick is scheduled. `combat_loop` is retired, so there is no watchdog.
- **Early path:** every player's `use_ability`, `submit_combat_action` and `flee_combat` runs `resolveRound` when it completes the round, and each call is rolled back too. The fight has no way forward, and `end_combat` (admin) is the only way out.

The old per-second loop had the same weakness, but only the tick failed. Player input now fails as well.

**Fix:** wrap the post-player phases (pets, effects, cooldowns, adds, retarget) in per-step `try/catch` with `console.error`, as the enemy loop already does, so the round always reaches the "next round / victory / defeat" decision. For `handleVictory` and `handleDefeat`, catch, log, and still call `clearCombatArtifacts` and mark the encounter `resolved`, so a bad reward path cannot brick the fight. Also consider re-arming a tick in `ensureRound` when a combat has an open round whose deadline passed more than one round ago.

### WR-02: A player killed mid-round by an immediate DoT tick stays `active` and keeps soaking later enemy actions

**File:** `spacetimedb/src/helpers/combat.ts:236-250`, `spacetimedb/src/reducers/combat.ts:3064-3069`, `:2506`, `:821-826`

**Issue:** `addCharacterEffect` applies the first DoT tick immediately and writes `hp: 0n` without marking the participant dead. `resolveRound` builds `activeNow` per enemy from `participant.status === 'active'` only. `markNewlyDeadParticipants` runs once, at step (f).

The rest of the enemy phase can therefore target the dead-but-active player:

- The `lowest_hp` rule sorts a 0-HP character first, so it picks the corpse over every living player.
- `aggro` and `all_allies` can pick that player too.
- `processEnemyAutoAttackForRound` returns early on `character.hp === 0n`, so the enemy loses its whole action.
- `tryEnemyAbilityForRound` has no such guard and may run an ability against a corpse.

In the old loop the window was about 1 second. Now it is the entire enemy phase of the round.

**Fix:** build `activeNow` and `activeParticipants` from living characters.

```ts
const activeNow = allParticipants.filter((x: any) => {
  if (x.status !== 'active') return false;
  const c = ctx.db.character.id.find(x.characterId);
  return !!c && c.hp > 0n;
});
```

Better, call `markParticipantDead` in `addCharacterEffect`'s DoT branch when `nextHp === 0n`.

### WR-03: `markParticipantDead` can resurrect a dying player who has an `hp_bonus` buff (pre-existing, reachable every round)

**File:** `spacetimedb/src/reducers/combat.ts:329-342`, called from `:2560-2565` and `:2602-2605`

**Issue:** Both callers write `hp: 0n` and then pass the stale `character` row, fetched before the damage, to `markParticipantDead`, which passes it to `clearCharacterEffectsOnDeath`. For an `hp_bonus` effect that function writes:

```ts
const nextHp = character.hp > nextMax ? nextMax : character.hp;   // character.hp is the PRE-damage HP
ctx.db.character.id.update({ ...character, maxHp: nextMax, hp: nextHp });
```

The character's HP goes back up to the pre-damage value while the participant row says `dead`. The player stays alive as far as `character.hp` is concerned, but is excluded from the fight, and is still alive for the defeat check's HP read. The code is unchanged from before this phase, but end-of-round DoT and enemy strikes now reach it deterministically.

**Fix:** in `clearCharacterEffectsOnDeath` (or at the top of `markParticipantDead`), re-read the row first.

```ts
const fresh = ctx.db.character.id.find(character.id) ?? character;
// use fresh.hp / fresh.maxHp below
```

### WR-04: Character DoTs tick twice in the round they are applied; enemy DoTs do not

**File:** `spacetimedb/src/helpers/combat.ts:236-250`, `spacetimedb/src/reducers/combat.ts:2596-2607`

**Issue:** Enemy-applied DoTs on a character hit once at application (the "first tick" inside `addCharacterEffect`) and again at the end of the same round in `tickEffectsForRound`. A DoT of D rounds therefore deals D + 1 ticks to a player. DoTs a player puts on an enemy get no immediate tick, so they deal D. The tick block's own comment says the intent is "an effect with 1 round left ticks once". The immediate tick is a leftover of the real-time loop.

**Fix:** drop the immediate tick in `addCharacterEffect` for round combat, or skip the end-of-round tick for an effect applied in the current round. Either way, make the two sides symmetric and update the tests that assert the current counts.

## Info

### IN-01: The first-kill moment is lost whenever another moment outranks it that round

**File:** `spacetimedb/src/helpers/combat_moments.ts:92-93`, `:149-162`

`firstPossible` requires that no enemy started the round dead (`!anyStartedDead`). If round 2 holds the first kill and a boss phase or near-death moment wins the priority, the kill is never narrated. From round 3, `anyStartedDead` is true, so `firstPossible` is false for every later kill. Dropping the `anyStartedDead` condition and relying on the `kill|first` fired-key alone would let it fire in a later round, but it would then be narrated late. Decide whether "first kill" means "first kill if nothing outranks it that round" and document it. At minimum, add a test for this case.

### IN-02: Moment near-death threshold (20%) differs from the summary's `nearDeathNames` threshold (10%)

**File:** `spacetimedb/src/helpers/combat_moments.ts:17`, `spacetimedb/src/helpers/combat_narration.ts:81`

For a `near_death` moment, the subject can be at 15% and absent from `nearDeathNames`. The moment prompt uses `momentSubject`, so it is not wrong today. Reuse `NEAR_DEATH_MOMENT_PERCENT` so the two cannot drift.

### IN-03: `combat_action` is public for every fight

**File:** `spacetimedb/src/schema/tables.ts:2037-2052`

RND-04 asks for party visibility, but a public table shows every fight's choices to every client. This is accepted by the decisions. Note it for the Phase 48 subscription, which should filter by `combatId` client-side and not rely on it being private.

### IN-04: Order-dependent iteration in end-of-round effects

**File:** `spacetimedb/src/reducers/combat.ts:3080-3088`, `:2584`, `:2639`

`tickEffectsForRound`, `processPendingAdds` and the retarget loop iterate `by_combat` index order, not `sortById`/`sortByKey` like the rest of the resolver. It is deterministic in practice. Sorting would make the documented "fixed order" literally true. The `random` target rule also uses `timestamp % n`, so every random-rule enemy picks the same target in a given round.

### IN-05: Dead code and leftovers

**File:** `spacetimedb/src/helpers/combat.ts:1160-1163` (`_oldCodeRemoved` plus a TODO); `spacetimedb/src/reducers/combat.ts:308` (`getEquippedWeaponStats` destructured but unused, since the auto-attack uses `deps.getEquippedWeaponStats`); `:3251` (`if (RoundTimerTick)` guard, always true); `data/combat_constants.ts` (`COMBAT_INTRO_TIMEOUT_MICROS` unused, already noted in the plans). Remove them to keep the next phase's diff small.

### IN-06: Legacy `fleeing` participants from fights in flight at publish are never resolved

**File:** `spacetimedb/src/reducers/combat.ts:2996-3028`

A participant row left in status `fleeing` by the old `flee_combat` is neither waited on nor processed, and nothing converts it. It can only matter for fights live at publish time. If that is possible on the owner's local database, add a one-line normalisation in the `combat_loop` drain path (`fleeing` to `active`).
