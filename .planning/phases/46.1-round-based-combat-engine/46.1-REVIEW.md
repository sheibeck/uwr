### CR-01 (module-identity guards): resolved

**Coverage.** I enumerated every scheduled binding:

- 15 `scheduled:` tables in `schema/tables.ts`.
- 2 `onSchedule` reducers in `reducers/llm_executor.ts`: `llm_run` and `llm_sweep`.

All 17 now start with the guard. The guard is the first statement in each, and a source-pin test enforces that. A last test fails if a new scheduled table appears that is not covered.

**Legitimate callers.** No scheduled reducer is invoked directly from anywhere else:

- A repo-wide grep for each reducer name finds only the definition, the `scheduled:` binding, and comments or inserts into the matching `*_tick` table.
- There are no `scheduledReducers[...]()` call sites.
- There is no client, `scripts/`, or `spacetime call` usage.
- `init`, `clientConnected` and `clientDisconnected` only insert tick rows (`scheduling.ts`, `index.ts:612`, `auth.ts:19`, `characters.ts:62`, `intent.ts:1375`, `combat_rewards.ts:226,242`, `world_events.ts:87`, `items_gathering.ts:117`). The scheduler then calls the reducer with the module identity, which is what the guard allows. This is the same pattern `llm_run` and `resolve_pull` already use.
- The self-rescheduling reducers (`regen_health`, `tick_casts`, `tick_day_night`, `sweep_inactivity`) keep their chain, because the scheduler call passes the guard. The test checks one reschedule for the module and none for a client.

**Verdict.** Nothing legitimate is blocked, and a forged client call can no longer fork a chain, resolve a world event, log out a player, or finish a gather.

### WR-01 (isolateRoundStep): resolved

**Round advancement and re-arm, both paths.**

- Every independent step is isolated, and the code from `(g)` to `(h)` contains no throwing write outside an isolate.
  - `recordBigMoment`, `snapshotForMoments`, `livingHpMap`, `recordKillsBy` and `momentCountOf` have their own try/catch.
  - `clearRoundChoices` and `startRound` are plain inserts.
- Timer path:
  - `cancelRoundTicks` spares the firing row (the scheduler consumes it).
  - `startRound` inserts the next tick, so the chain continues.
- Early path:
  - The player's choice is stored before `resolveRound`, and no step can roll it back.
  - `cancelRoundTicks` clears the old tick.
  - `startRound` arms the next round.
- When `reading the participants` fails, `afterEnemies` is `[]`, so the end-of-round steps do nothing for that round. The round still advances.

**A throwing victory or defeat.**

- `isolateRoundStep('victory'|'defeat')` returns false, and `closeFightAfterFailure` runs `clearCombatArtifacts` and sets the encounter to `resolved`, each in its own isolate.
- That clears the ticks, rounds, choices, participants, enemies and pending adds, and restores the combat state of the characters.
- It is idempotent. If the throw happened after `handleVictory` had already cleared and resolved the fight (in the XP loop), the second pass finds nothing and the state check skips the update.
- The round is then not advanced, which is correct because the fight is over.

**Partial writes of a failed step are kept.** This is the stated design (no savepoints). I found two consequences worth knowing about; neither is a regression compared with the old behaviour, a permanently stuck fight. They are recorded as IN-07 and IN-08.

### WR-02 (no 0-HP targets): resolved

- `livingActiveParticipants` filters at `pickEnemyTarget`, so the `lowest_hp`, `random`, `all_allies` and aggro rules and the fallback all exclude a corpse.
- The same filter is used for `activeNow` per enemy, in `landEnemyCasts`, and for the adds' aggro target.
- A side effect, noted and harmless: the "begins to cast" and "fizzles" lines are no longer posted to a participant who is at 0 HP but not yet marked dead.
- When every participant is at 0 HP, `pickEnemyTarget` returns undefined before the aggro branch is reached, so a pet entry cannot be targeted. Pets of a dead owner are deleted anyway.

### WR-03 (stale death row): resolved

- `clearCharacterEffectsOnDeath` re-reads the character per `hp_bonus` effect.
- Both killing-blow callers write `hp: 0n` before `markParticipantDead`, so the re-read sees 0 and the death sticks.
- The extra `break` after a lethal DoT is correct:
  - `markParticipantDead` deletes the character's effect rows, so updating one of them afterwards would throw, and a throw would now cost the rest of the effect ticks.
  - The `break` applies only when the participant row exists. Otherwise the loop falls through as before.

### WR-04 (DoT symmetry): resolved

- The immediate tick is removed from `addCharacterEffect`.
- A DoT of D rounds now ticks D times on a player, as it already did on an enemy.
- The code removed was partly dead already: an inner `effectType === 'regen'` branch sat inside an `effectType === 'dot'` guard.
- Every `addCharacterEffect` caller with a DoT is an in-combat enemy ability, and `tickEffectsForRound` runs in combat. So no out-of-combat DoT lost its only tick.
- The application line already carries "applies a burning effect". Losing the "You suffer N damage from X" line at application is intended.

**Balance effect (noted, not a defect).** Damage taken from enemy DoTs falls by exactly one tick per application. For the default 3 s duration (1 round), a DoT deals 1 tick instead of 2, which is half. The D = 1 case is where players will see the change most. Balance remains unreviewed, per the known and accepted list.

## Info

### IN-01: The first-kill moment is lost whenever another moment outranks it that round

**File:** `spacetimedb/src/helpers/combat_moments.ts:92-93`, `:149-162`

`firstPossible` requires that no enemy started the round dead (`!anyStartedDead`). If round 2 holds the first kill and a boss phase or near-death moment wins the priority, the kill is never narrated. From round 3, `anyStartedDead` is true, so `firstPossible` is false for every later kill. Dropping the `anyStartedDead` condition and relying on the `kill|first` fired-key alone would let it fire in a later round, but it would then be narrated late. Decide whether "first kill" means "first kill if nothing outranks it that round" and document it. At minimum, add a test for this case.

### IN-02: Moment near-death threshold (20%) differs from the summary's `nearDeathNames` threshold (10%)

**File:** `spacetimedb/src/helpers/combat_moments.ts:17`, `spacetimedb/src/helpers/combat_narration.ts:81`

For a `near_death` moment, the subject can be at 15% and absent from `nearDeathNames`. The moment prompt uses `momentSubject`, so it is not wrong today. Reuse `NEAR_DEATH_MOMENT_PERCENT` so the two cannot drift.

### IN-04: Order-dependent iteration in end-of-round effects

**File:** `spacetimedb/src/reducers/combat.ts:3080-3088`, `:2584`, `:2639`

`tickEffectsForRound`, `processPendingAdds` and the retarget loop iterate `by_combat` index order, not `sortById`/`sortByKey` like the rest of the resolver. It is deterministic in practice. Sorting would make the documented "fixed order" literally true. The `random` target rule also uses `timestamp % n`, so every random-rule enemy picks the same target in a given round.

### IN-06: Legacy `fleeing` participants from fights in flight at publish are never resolved

**File:** `spacetimedb/src/reducers/combat.ts:2996-3028`

A participant row left in status `fleeing` by the old `flee_combat` is neither waited on nor processed, and nothing converts it. It can only matter for fights live at publish time. If that is possible on the owner's local database, add a one-line normalisation in the `combat_loop` drain path (`fleeing` to `active`).

### IN-07: A throwing victory or defeat path closes the fight but skips corpses, penalties and (if it threw early) the spawn release

**File:** `spacetimedb/src/reducers/combat.ts:3040-3048` (`closeFightAfterFailure`), `:1973-2223` (`handleVictory`), `:2227-2275` (`handleDefeat`)

`closeFightAfterFailure` only clears artifacts and marks the encounter `resolved`. Whatever the failed path had not yet done stays undone:

- A throw in the loot or quest code, which is the most likely cause, happens after `resetSpawnAfterCombat` but before `createCorpsesForDead` and `applyDeathPenalties`. A player who died in that fight is left at 0 HP with no corpse and no XP penalty. `respawn_character` still recovers them, so it is a free death and not a stuck state.
- A throw inside `resetSpawnAfterCombat` itself, or before it, leaves the enemy spawns `engaged` and locked to a combat that has been deleted. `clearCombatArtifacts` only releases spawns of pending adds, so those spawns would be lost from the location.

This is a double-fault path and an improvement on a permanently stuck fight. If it is cheap, the close step could run `createCorpsesForDead` in its own isolate. It could also release any `enemy_spawn` whose `lockedCombatId` equals the combat, before the enemy rows are cleared.

### IN-08: `tickEffectsForRound` is one isolated step, so a persistently failing effect row stalls every later effect tick

**File:** `spacetimedb/src/reducers/combat.ts:3165-3166`, `:2619-2679` (character effects), `:2681-2750` (enemy effects)

The player turn and the enemy turn are isolated per entity. The effect tick is isolated as a whole. A character effect row that throws on every round, such as a malformed or legacy row, keeps the characters after it and all enemy effects (DoT damage and the stun countdown) from ticking for the rest of the fight. A stunned enemy would then stay stunned. The round still advances, so the fight is not stuck.

The trigger is hypothetical, because the current rows are well formed. Isolating each participant's effects and each enemy effect would remove it.

### IN-09: `tick_bard_songs` references an undefined `combatId` (pre-existing, inert)

**File:** `spacetimedb/src/reducers/combat.ts:1711`, `:1713`

`bard_requiem_of_ruin` reads `combatId`, but the reducer only declares `bardCombatId`. tsc reports TS2304. It is inert today because `active_bard_song` is never inserted, and it was not touched by this phase (the guard fix only added one line above it). If bard songs are ever wired up, it throws a `ReferenceError`. Rename to `bardCombatId`, or delete the dead reducer with the bard code.
