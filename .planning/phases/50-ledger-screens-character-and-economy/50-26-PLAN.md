### 3. Pricing inputs and the floor

**Pricing inputs.**
- List price: `listPriceFor(vendorValue)` = 2v, or 10 when v is 0 (data/vendor_stock.ts:239-241). The same rule is written inline at vendor_sale.ts:172 and intent.ts:1009.
- Buy: `buyPrice(listPrice, perkDiscountPct, vendorBuyMod)` (vendor_pricing.ts:61-73). The perk discount is capped at 50, then the Charisma factor (1000 - mod)/1000 applies, with a minimum of 1 after each step.
- Sell: `sellPayout(vendorValue, quantity, perkSellPct, vendorSellMod)` (vendor_pricing.ts:43-54). It computes v x q, applies the perk only when above 0, then Charisma only when above 0, rounding down twice.
- Perks:
  - Server: `getPerkBonusByField(ctx, id, 'vendorBuyDiscount' | 'vendorSellBonus', level)` (items.ts:136, vendor_sale.ts:145).
  - Client: `perkBonusByField` (src/vendor/vendorModel.ts:105-111).
- Charisma: vendorBuyMod = max(0, (CHA-10) x 10) and vendorSellMod = max(0, (CHA-10) x 8) (data/combat_scaling.ts:481-486, helpers/character.ts:119).

**The exploit today.**
- With the 5% perk, 2v x 0.95 x (1 - 0.01x) < v x 1.05 x (1 + 0.008x) once x = CHA-10 > 31. So above about CHA 41, a character buys for less than he sells and prints gold.
- Finite stock alone does not stop this, because the player supplies the stock.

**Why a plain "sell of one + 1" floor is not enough.** sellPayout rounds per call, so a stack pays more per unit than a single item. Worked example (each value checked by hand from the current code):
- v = 3, sell perk 5, vendorSellMod 330: sellPayout(3,1) = 3, but sellPayout(3,100) = 418, which is 4.18 per unit.
- A floor of 4 lets a player sell 100 for 418, buy them back one at a time for 400, and repeat for +18 gold per pass.

**The chosen floor** removes this for every stack size:
- unitSellCeiling = floor(v x (100 + applied sell perk) x (1000 + max(0, mod)) / 100000). This is the exact per-unit payout rounded down.
- listingBuyPrice = max(raw discounted price, unitSellCeiling + 1).
- Proof: sellPayout(v, N) <= N x exact rate < N x (unitSellCeiling + 1), and buying N units one at a time costs N x listingBuyPrice.
- In the example: unitSellCeiling = 4, so the floor is 5, and 100 x 5 = 500 > 418.
- unitSellCeiling + 1 is always at least sellPayout(v,1) + 1, so the owner's "sell + 1" rule also holds.

**Where the floor binds.** At normal Charisma the floor never binds (list price = 2v), so existing prices do not move. vendor_pricing_parity fixtures: list price 123n, vendorValue 7n.

### 4. Reducer signature: a new reducer, the old one kept

- The SDK encodes reducer arguments as a positional BSATN product.
  - `ProductType.makeSerializer` (`node_modules/spacetimedb/src/lib/algebraic_type.ts:443-498`) writes each element in order, with no field tags or lengths.

- A client built against three u64 fields sends 24 bytes. A server that expects a fourth field cannot decode them, so every Sell from a client with the old bindings would fail. That includes the owner's open tab and, at the milestone deploy, the old maincloud bundle.
- Therefore:

  - Keep `sell_item` with its exact signature, routed through the same helper.

- **What the kept sell_item sells (Claude's discretion).** It sells the whole instance, which is what it does today.
  - For every non-stack item this is exactly quantity 1.
  - For a stack, it keeps the price the old client shows on its Sell button true.
