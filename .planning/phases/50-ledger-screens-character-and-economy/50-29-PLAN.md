## Findings (planner, code read 2026-10-06)

### Why a new reducer, not a new argument
- Reducer arguments are a positional BSATN product (plan 50-26 research 4). An added argument breaks every client built on the old bindings.
- So craft_recipe keeps its six fields (items_crafting.ts:140-150), and a new reducer `craft_recipe_count` takes the count. The client switches to the new one in plan 50-36.

### craft_recipe today (spacetimedb/src/reducers/items_crafting.ts:140-303)
- **Checks, in order:**
  1. owner (requireCharacterOwnedBy throws)
  2. station (an appendPrivateEvent 'system' line and return)
  3. recipe found ('Recipe not found')
  4. discovered ('Recipe not discovered')
  5. planCraft, where 'materials' writes the plan message as a 'system' line and the others go through failItem
- **Writes:**
  1. remove req1, req2 and req3
  2. addItemToInventory(output, outputCount) returns the new row or the merged stack
  3. for gear with an output: remove the catalyst and each reagent, insert suffix affixes, insert the implicit quality affixes (getCraftQualityStatBonus) and update the instance with qualityTier 'common', craftQuality and displayName
  4. the 'reward' line `You craft {name}.`
- **A missing output template:** addItemToInventory throws SenderError and the transaction rolls back. The batch path refuses it up front instead.
- **Capacity:** craft_recipe has no backpack capacity gate (data/inventory_rules.ts header). The batch path keeps that parity and adds none (see the SUMMARY note).
