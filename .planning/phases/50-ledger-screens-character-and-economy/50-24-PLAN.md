<objective>
Give every vendor a rule-based, area-appropriate base stock that restocks on a timer, as the owner decided after the build (CONTEXT "Owner decision after the build: vendor base stock"). Today `vendor_inventory` is filled only by player sales, so every Trade screen opens empty.

Purpose: the owner said "Vendors should sell what players sell to them and they should have a selection of items appropriate to the area."
- Stock comes from item templates that already exist (the starter set and play), chosen by the vendor's role and the area's level band, with rarity weighted toward common.
- It is deterministic per vendor and tick.
- It is replaced by a guarded scheduled tick that never touches player-sold listings.
- It is priced through the shared list price, then `buyPrice` with rapport at purchase.
- There is no LLM call, no prompt change, no Keeper Bible or route change, and no client change.

- The pure rules module `data/vendor_stock.ts` with tests.
- Two private tables, one private scheduled.
- The guarded `restock_vendors` reducer with the first fill on connect.
- Real-handler tests and the scheduled-guard list entry.
- A client render test.
- A local publish (key 108 before and after) and bindings regenerated under an allowlist.

**Area level band.**

- Starter set: `STARTER_ITEM_NAMES` (data/combat_constants.ts:19-33) keeps starter gear out of loot drops only. The owner's decision says stock comes from "play and the starter set", so starter templates stay eligible here.

**Listing shape.**
- `vendor_inventory` (tables.ts:883-896, public, index `by_vendor` on npcId) has the columns id, npcId, itemTemplateId, price and qualityTier. It has no quantity (buy never decrements; items.ts:105-150), no owner and no source.
- Player rows are written by `sellInstanceToVendor` (helpers/vendor_sale.ts:158-175) and typed `sell N` (reducers/intent.ts:1005-1017) at price `vendorValue > 0n ? vendorValue * 2n : 10n`, de-duplicated on template plus quality.
- A marker is therefore truly needed: base and player rows are otherwise identical, and restock must delete only base rows.
- The marker goes in a NEW private table `vendor_base_stock` (listingId primary key, npcId with index by_vendor). There is no new column on vendor_inventory, for three reasons:
  - The public row type and client fixtures stay as they are.
  - The two sell paths that insert vendor_inventory rows need no edit.
  - Clients never see which rows are base stock.
- A sale of a template that is already listed adds no row (existing Phase 50 behavior). If that row is base stock, it rotates at the next restock like any base row. This is the same "accept and document" call as review IN-03 (50-REVIEW-server.md:203-212).

**Scheduled tables.**
- Pattern: `scheduled: () => scheduledReducers['name']`, columns `scheduledId` (u64 primaryKey autoInc) and `scheduledAt` (scheduleAt). Examples: tables.ts:1236-1245 and 1868-1877.
- The reducer is registered as `scheduledReducers['name'] = spacetimedb.reducer(...)`, with the guard `if (ctx.sender.toHexString() !== ctx.databaseIdentity.toHexString()) return;` as the first statement (index.ts:297-305, sweep_inactivity). It reschedules by inserting the next row.
- The "ensure" pattern inserts only when the table is empty (helpers/scheduling.ts:59-66). It is called in init through `initScheduledTables` (index.ts:577) and in clientConnected (index.ts:594-601).
- `init` does not run again on republish, so the first fill must come from clientConnected.
- reducers/scheduled_guard.integration.test.ts:114-121 fails when a scheduled table in tables.ts is missing from its list, so the new reducer must be added there.

**Bindings.**
- Private tables appear in src/module_bindings/types.ts only (for example DayNightTick at types.ts:445 and VendorBuyback at types.ts:1449).
- Scheduled reducers of private tables get no reducer binding: there is no tick_day_night binding anywhere.
- So the only expected binding change is two added types in types.ts.

**Client.**
