# Phase 51.3.1.2: Code Review Report, part A (generation pipeline)

**Reviewed:** 2026-10-09
**Depth:** deep (call chains traced into llm_executor.ts, llm_budget.ts, region_hold.ts, passages.ts, travel.ts and the client's creationSteps.ts where the pipeline's behaviour depends on them)
**Files Reviewed:** 18 (region_hold.ts was read because world_gen.ts and the HELD logic depend on it)
**Status:** issues_found

## Summary

Severity key: **BLOCKER** means incorrect behaviour, a security hole or data loss that must be fixed before shipping. **WARNING** means a real defect or risk that should be fixed. **INFO** means a hardening or cleanliness item.

I checked these invariants and found them holding:

- **2b never reaches FILL_ERROR or reruns 2a.** Every caller of `failWorldFill` is behind a `FILLING` step guard:
  - `applyWorldFillResult` (llm_apply.ts:614)
  - `applyLlmFailure` for world_gen (llm_apply.ts:233)
  - the sweeper's `isStage2a` check (llm_sweeper.ts:332)
  - `restartFailedStage`, which picks the stage from the handed step (world_gen.ts:1204)

  A throw anywhere in `writeRegionPlaces` rolls back the whole 2a transaction, so a later `apply_error` leads to FILL_ERROR only when no place was written. Only `startWorldFamilies` is wrapped in try/catch (llm_apply.ts:655-660). No path writes places twice.
- **Applies are idempotent.** The applies check the step: GENERATING, FILLING and FILLING_FAMILIES. When the sweeper expires a job, a late reply for it is never applied (llm_executor.ts persistAttempt, the `stale` branch). The re-apply after a rollback (applyStored, at most two attempts) runs against rolled-back state, so it is safe.
- **Locks are not left stranded.** `releaseStrandedLocks` now covers FILLING_FAMILIES and sends it to FAMILIES_ERROR, never FILL_ERROR. HELD, COMPLETE and the two error steps are never touched.
- **Determinism.** There is no `Math.random`, `Date` or `performance` in the changed code. The place count, hub count, feud and family seeds all come from `hubSeed` or `familySeed` of the region id. The request and the write re-derive the same numbers (`placeCountFor(region.id)` at llm_apply.ts:646, `familyCountFor(regionChartedPlaces)` at both world_gen.ts:1295 and world_gen.ts:1604).
- **Second-order prompt injection, 2a to 2b.** Every value that 2a's model wrote goes through `w()` / `sanitizeWorldData` (angle-bracket escape, single line) before it enters the 2b prompt: place names, terrain, faction, threats and hub names (llm_layers.ts `buildWorldFamiliesVolatile`). Descriptions are not sent at all.
- **Cap exemption.** `world_gen_families` is cap-exempt, on the no-auto-retry list, and has no truncation retry. That matches D-01.

I found no BLOCKER. The defects below are cost leakage, edge-case strandings and UX regressions. The most important are:

- **WR-01:** the late-family loot jobs inherit the 20000-token region-creation cap.
- **WR-02:** placement side effects run unguarded inside the paid 2b apply.
- **WR-03:** a duplicate starter region can be created during the stage-1 window that the HELD design does not cover.
- **WR-04:** the hold now applies to legacy FILL_ERROR regions.

## Warnings

### WR-01: The late-family loot jobs inherit the 20000-token region-creation cap (each reserves about 40 times what D-11 budgeted)

**File:** `spacetimedb/src/data/llm_tuning.ts:188`, `spacetimedb/src/data/llm_tuning.ts:408`; caller `spacetimedb/src/helpers/region_economy.ts:1361-1366` and `region_economy.ts:1252-1273`

**Issue:** D-19 gives the shared `REGION_CREATION_MAX_TOKENS = 20000` to the `region_economy` route. That route also serves every family-mode late-loot job (`startFamilyLoot` enqueues `route: 'region_economy'`). D-11 says these are about $0.005 each and that a big region gets 5 to 8 of them. `reservationMicroUsd` uses `LLM_ROUTES[route].maxTokens`, so each one now reserves about $0.20 against the phase ledger and the global ceiling.

Failure scenario:
- A 10-place region completes its economy, and `startLateFamilies` enqueues 8 family jobs in one transaction. That is about $1.60 of ceiling headroom reserved at once, for one region.
- With two or three regions finishing near each other, or with the ledger near the default $10 ceiling, `reserveLlmBudget` returns `ceiling`.
- The families silently fall back to rule loot (`started.startsWith('refused:')`), and other players' calls get the resting line.
- The real spend on a runaway late-loot reply is also capped at $0.20 instead of a few cents.

These late jobs are not region creation, and they keep running for quest families and late joiners in every region (existing ones included) for the life of the world.

**Fix:** keep region-mode and family-mode economy calls on different output caps. Either split the route (for example `region_economy_family`, with its own cap of about 2048 and the same schema), or carry a per-request `maxTokens` that `reservationMicroUsd` and the request builder both honour. At minimum, leave `region_economy` at its pre-D-19 value and give the shared cap only to world_gen_start, world_gen and world_gen_families:
```ts
// llm_tuning.ts
region_economy: entry('low', 6144, 90_000, 'insufficient_data'),
```

### WR-02: Placement side effects run unguarded inside the paid 2b apply, so a placement throw rolls back the families and makes every retry fail the same way

**File:** `spacetimedb/src/helpers/world_gen.ts:1082-1085` (`placeWaitingCharacter`, `placeHeldCharacters`), called from `llm_apply.ts` `applyWorldFamiliesResult` (last line)

**Issue:** The economy start inside `finishRegionFill` is in a try/catch so it cannot roll back the paid families (world_gen.ts:1087-1092). Character placement is not. Placement covers `placeWaitingCharacter` and `placeAtHome` for every HELD character: `markLocationVisited`, `ensurePoolsForLocation`, `npcNoticeLine`, `keeperSegments` and the character update.

Failure scenario:
1. One HELD character's row trips a throw, for example a character whose data makes `ensurePoolsForLocation` or `markLocationVisited` throw.
2. The whole 2b transaction rolls back, including the families.
3. applyStored retries once with the same result, then `apply_error` leads to FAMILIES_ERROR.
4. Every `[explore]` buys a new paid 2b call that hits the same deterministic throw.
5. The region stays held forever, and so does every traveller at the crossing.

The same "chain bug never rolls back a paid reply" rule (Pitfall 2) that protected the 2b enqueue applies here.

**Fix:** isolate each placement so one bad character cannot undo the region. Commit COMPLETE and the families first, then place each waiting character inside its own guard:
```ts
for (const held of heldStatesOf(tx, region.id)) {
  try { placeOneHeld(tx, held, region); }
  catch (err) { console.error('Held placement failed for state ' + String(held.id) + ': ' + errorName(err)); }
}
```
The state stays HELD, and `retryHeldStarter` already places a HELD character whose region is whole. Note that SpacetimeDB does not undo writes made before a caught throw, so keep each guarded block small and write the character row last.

### WR-03: The HELD design does not cover the stage-1 window, so a second character of the same race generates a duplicate starter region

**File:** `spacetimedb/src/helpers/world_gen.ts:400-407` (`starterRegionFor`), `world_gen.ts:521-530` (`reuseStarterRegion`)

**Issue:** `reuseStarterRegion` only finds a starter region once its `region` row exists. Stage 1 writes that row in its apply, `writeRegionStart` with `starterForRace`.

Failure scenario:
1. Character A of race R finalizes, and stage 1 is GENERATING for several seconds.
2. Character B of race R finalizes during that window.
3. `starterRegionFor` returns null, so B's state enqueues a whole second world_gen_start, then 2a, 2b and the economy. That is a second paid region (about $0.12-0.14 by the D-12 estimate, plus the reservations).
4. Both regions carry `starterForRace = r`. `starterRegionFor` returns whichever the table iterates first, so later characters of race R are split between them, and the hold check may look at the wrong one.

The milestone-end UAT step 4 ("During the wait, create a second character of the same race") will hit this if it is done early in the wait. This was possible before the phase too, but D-15/D-17 claims a new character waits on a starter region "still being built", and this window breaks that claim.

**Fix:** in `startWorldGeneration`, before enqueueing a starter stage 1, look for a starter state of another character of the same race in PENDING or GENERATING. If one exists, hold the new state on that state, not on a region. Store the build state's id, then resolve it to `generatedRegionId` when stage 1 lands, in `applyWorldStartResult` after line 554, by converting those HELD-by-state rows. A simpler fallback is to answer 'busy' and retry placement at finalize. Also make `starterRegionFor` deterministic (lowest region id) so duplicates that already exist resolve the same way every time.

### WR-04: The hold also applies to legacy FILL_ERROR regions (existing regions are touched)

**File:** `spacetimedb/src/helpers/region_hold.ts:55`, `region_hold.ts:70-77`, `region_hold.ts:90-97`; consumers `world_gen.ts:521-530` and `travel.ts` (`travelHoldRefusal`)

**Issue:** `regionHoldState` treats any state naming the region in FILL_ERROR as `held_failed`, whatever its age. A region whose fill failed before this publish was "playable" under the Phase 43 contract (world_gen.ts header: "the stage-1 region stays playable"). It is now changed in three ways:

- Travel into it from its neighbour is refused with the 7d line.
- Its crossing passage never collapses (passages.ts `crossingHoldState`).
- If it is a starter region, every new character of that race is HELD in creation, with the 7e line followed by the failure line.

Before the phase, such a character was placed at once (`reuseStarterRegion` placed him whenever the region had a charted place). Getting out now needs someone to `[explore]`, which buys a new paid 2a and 2b on that existing region and grows it to 8-10 places. That conflicts with "existing regions are not touched" (CONTEXT domain, D-14).

**Fix:** limit the hold to states created by the new pipeline, for example only when a state carries FILLING_FAMILIES, FAMILIES_ERROR or a 2a job with `placeCount`. Simpler: limit it to states updated after the publish, or add a marker the new `startWorldFill` sets. Alternatively, have `reuseStarterRegion` keep placing new characters in a legacy FILL_ERROR starter region (`regionHoldState === 'held_failed'` with no 51.3.1.2 marker), as before.

### WR-05: Handing a starter build state to a HELD retrier hides it from the creator: a false "first region failed" on his creation console and missing failure lines

**File:** `spacetimedb/src/helpers/world_gen.ts:550-552` (`retryHeldStarter`), `world_gen.ts:992` (`postFillFailure`), `world_gen.ts:1131-1143` (`storedRegionDescription`); client `src/creation/creationSteps.ts:116-130`, `src/creation/queries.ts:23`

**Issue:** `retryHeldStarter` rewrites the generating state's `playerId` to the HELD asker (character B's identity) and keeps `characterId` as the creator A. Three things follow:

1. **False failure shown to A.** A's client subscribes to `world_gen_state` filtered by `playerId = A's identity`, so the row leaves A's subscription. `firstRegionFailed` then sees no row for A's character and returns `true` (`if (newest === null) return true;`). A's creation console shows "first region failed" while B's retry is actually running. A's `[explore]` answers 'busy', which contradicts the UI.
2. **Failure lines go to B instead of A.** If B's retry fails again, `postFillFailure` reaches `if (!char || char.locationId === 0n) tellCreation(genState.playerId)`. `char` is A, still at location 0, but `genState.playerId` is now B. A gets no creation_error line, and B is told twice (deduplicated to once).
3. **A gets the generic region description.** On success, `storedRegionDescription` looks up the stage-1 job by `buildDedupeKey(state.playerId, ...)`, which is now B's identity. The lookup misses, so A's arrival message falls back to "A {biome} region." and loses the model's region description.

**Fix:** do not move ownership of the build state. Charge the retry to the asker by passing `playerId` only to the enqueue. `startWorldFill(tx, state, { chargeTo: playerId })` and `startWorldFamilies` would take an optional payer, and the state's `playerId` would stay the creator's. If the state must be handed, have `postFillFailure` also tell the creator's player (resolve it with `resolveCharacterPlayerId(tx, char)` when `char.locationId === 0n`). Also have `storedRegionDescription` search by `SOURCE_KEYS.worldGen(state.id)` across identities, or store the description on the region row at stage 1.

### WR-06: The NPC count from the 2a reply is not capped (D-06 says 3-5), and D-19 removed the output backstop

**File:** `spacetimedb/src/helpers/world_gen.ts:1534-1544`

**Issue:** `writeRegionPlaces` trims places to the server count (D-03) and `validateFamilies` trims families to `familyCount`. Every object in `reply.npcs`, however, is inserted (only an exact repeat at the same place is skipped). With `max_tokens` now 20000 (D-19: "We could always limit via the prompt"), a reply that ignores the "3-5 more NPCs" wording can insert dozens of NPC rows into a new region. Each row then feeds `npcNoticeLine`, NPC conversation prompts and the look output. That breaks the "AI names, server numbers" rule (D-46) the rest of the pipeline follows.

**Fix:** cap the kept NPCs on the server. Allow the D-06 maximum of additional NPCs, plus the vendor and banker that the model may write for each hub (those are re-typed by `settleRegionServices` anyway):
```ts
const NPC_MAX = DENSITY_RULES.REGION_NPCS_MAX + 2 * hubs.length; // new named constant, 5
let kept = 0;
for (const npc of npcItems) {
  if (kept >= NPC_MAX) break;
  ...
  insertRegionNpc(tx, npc, npcLocation.id);
  kept += 1;
}
```

### WR-07: A throw from the 2b or 2a enqueue on the `[explore]` path is not caught, so the region can be held for good

**File:** `spacetimedb/src/helpers/world_gen.ts:1203-1206` (`restartFailedStage`), `world_gen.ts:1330-1336`; `llm_queue.ts:225-228`

**Issue:** `enqueueLlmJob` throws, rather than refusing, for a request over `LLM_REQUEST_JSON_MAX_CHARS` (64000) and for an invalid identity. In the 2a apply this throw is caught (llm_apply.ts:655-660) and gives FAMILIES_ERROR. On the retry path (`retryWorldFill`, `retryHeldStarter`, `retryStarterWorldGen`, then `restartFailedStage`, then `startWorldFamilies`) nothing catches it. The whole `[explore]` reducer fails with an internal error, no in-voice line is posted, and the state stays FAMILIES_ERROR.

Because the input is rebuilt from the same stored rows every time, every later `[explore]` throws the same way. The region stays held forever, and so do the crossing and any HELD new characters.

The 2b input carries unbounded model-written strings from 2a: threats, faction and place names (see IN-02). D-19's 20000-token 2a cap makes an oversize input possible, though unlikely.

**Fix:** wrap the enqueue in `startWorldFamilies` and `startWorldFill` and treat a throw as a refusal:
```ts
let result;
try {
  result = enqueueLlmJob(tx, { ... });
} catch (err) {
  console.error('World families enqueue failed for state ' + String(genState.id) + ': ' + errorName(err));
  failWorldFamilies(tx, genState, WORLD_FAMILIES_FAILED_MESSAGE);
  return 'refused';
}
```
Also cap the world-data lengths in `buildWorldFamiliesInput` (IN-02) so the input size is bounded.

## Info

### IN-01: `regionFillHint` ignores the new steps

**File:** `spacetimedb/src/helpers/world_gen.ts:376-387`

**Issue:** The hint knows only FILLING and FILL_ERROR. A character inside a region at FILLING_FAMILIES or FAMILIES_ERROR gets no hint and plain "There is nowhere to go from here." That happens only for characters placed by the old pipeline before the publish, or through `placeAtHome`'s no-exits branch.

**Fix:** treat FILLING_FAMILIES like FILLING. For FAMILIES_ERROR, return a line naming `[explore]` (owner wording needed), or return `REGION_FILL_FAILED_HINT` for both error steps.

### IN-02: World data passes from 2a to 2b with no length cap

**File:** `spacetimedb/src/helpers/world_gen.ts:1286-1310`, `spacetimedb/src/data/llm_layers.ts:656` and `llm_layers.ts:1294-1297`

**Issue:** Sanitization is present (angle-bracket escape and whitespace collapse), so a model-written value cannot forge a tag or a new line. Length and count are not bounded, though:

- a place name or threat can be thousands of characters;
- `threats` can have any number of entries;
- `writeRegionPlaces` stores `JSON.stringify(reply.threats)` without validating the elements.

That widens the injection surface of the 2b prompt (an inline "Families: one." inside a threat, for example). It also drives WR-07. The counts the server sends are enforced at write time, so the integrity impact is low.

**Fix:** in `buildWorldFamiliesInput`, `truncateCodePoints` each name to about 80 characters and each threat to about 160, and keep at most about 8 threats. Also cap these values when they are written in `writeRegionPlaces` (location name, dominant faction, threats and landmarks).

### IN-03: A 2b enqueue refusal stores the 2a refusal wording as the public `errorMessage`

**File:** `spacetimedb/src/helpers/world_gen.ts:1339-1343`

**Issue:** A non-resting refusal stores `WORLD_FILL_REFUSED_MESSAGE` ("...cannot finish remembering this region...") on a FAMILIES_ERROR state. The creation and crossing lines ignore it, but `world_gen_state` is public, so a client that shows `errorMessage` gets 2a wording for a 2b failure.

**Fix:** store `WORLD_FAMILIES_FAILED_MESSAGE` for non-resting 2b refusals.

### IN-04: `startWorldFill` and `startWorldFamilies` do not check the incoming step

**File:** `spacetimedb/src/helpers/world_gen.ts:925-931`, `world_gen.ts:1347-1353`

**Issue:** Both functions set FILLING or FILLING_FAMILIES on whatever state they are given. Every current caller checks the step first, but the D-09 invariant ("never re-run 2a after places exist") relies only on caller discipline. A future caller passing a FAMILIES_ERROR state to `startWorldFill` would duplicate the places.

**Fix:** add a guard in `startWorldFill`: refuse unless `current.step` is GENERATING (stage-1 apply) or FILL_ERROR. Likewise for `startWorldFamilies`: refuse unless the step is FILLING or FAMILIES_ERROR.

### IN-05: An orphaned live 2b job remains if `startWorldFamilies` throws after its enqueue

**File:** `spacetimedb/src/helpers/llm_apply.ts:655-660`

**Issue:** SpacetimeDB does not undo writes made before a caught throw. If anything after `enqueueLlmJob` inside `startWorldFamilies` throws (today only the state update), the 2b job and its dispatch stay live while the catch sets FAMILIES_ERROR. The job's paid reply is then discarded by the FILLING_FAMILIES guard, unless an `[explore]` from the same identity first dedupes onto it and moves the state back. The impact is low.

**Fix:** keep the code after the enqueue to a minimum (it is now one update), or check in the catch whether an active 2b job exists for the state and leave the state at FILLING_FAMILIES if so.

### IN-06: The host floor can be silently unmet at the 6-place floor

**File:** `spacetimedb/src/data/region_shape.ts:225-234`, `spacetimedb/src/helpers/world_gen.ts:1521-1525`

**Issue:** Take a 6-place region (D-03 floor) with a safe non-hub arrival point and two hubs. That leaves 3 candidates, and `MIN_HOST_PLACES` is 4. `hostFloorFlips` can then return index 0, which `writeRegionPlaces` skips with `continue`. The SC3 floor is not met and nothing records it. Families still fit (9 families across 3 hosts at up to 5 each), so this is a rule gap, not a crash.

**Fix:** exclude index 0 inside `hostFloorFlips` (pass `arrivalIndex` or filter `n.index !== 0`), and document or log when the floor cannot be reached.

### IN-07: The economy size counts passage places as charted

**File:** `spacetimedb/src/helpers/region_economy.ts:100-102`, `region_economy.ts:320`

**Issue:** `chartedPlaceCount` excludes only `uncharted`. A region whose Edge Beyond place later became a `passage` counts it as a place. At first design this never happens, because the economy starts before any onward passage exists. An admin `retryFailed` on an older 7-place region with a passage would flip it to `medium`.

**Fix:** exclude `passage` as well, or reuse `regionChartedPlaces` semantics.

### IN-08: The proof cost-bound assertion is skipped while the bound exceeds the run cap

**File:** `scripts/llm/proof_rules.test.mjs` (see `51.3.1.2-D19-SUMMARY.md`)

**Issue:** This is outside the strict file scope, but it bears on cost. The worst-case dry-run bound is now $2.6669. That is over the $1.80 stop line and also over the $2.00 run cap. The owner deferred the check (`it.skip`), so the test suite no longer guards against a paid proof that could exceed its cap. This is tracked in deferred-items.md, so it is not a defect of this phase. It is noted here because WR-01 adds reservation pressure from the same cap.

**Fix:** none needed now. Re-enable the assertion when the per-route budgets are set (Phase 52.5).
