### WR-01: The late-family loot jobs inherit the 20000-token region-creation cap

**Files modified:** `spacetimedb/src/data/llm_tuning.ts`, `spacetimedb/src/data/llm_routes.ts`, `spacetimedb/src/helpers/llm_budget.ts`, `spacetimedb/src/helpers/claude_request.ts`, `spacetimedb/src/helpers/llm_executor.ts`, `.planning/phases/51.3.1.2-bigger-regions/51.3.1.2-CONTEXT.md`; tests `spacetimedb/src/helpers/late_family_max_tokens.test.ts` (new, 9 tests) and `spacetimedb/src/helpers/region_economy.test.ts`
**Commit:** 40d0e83e
**Applied fix:**
- There was no per-job budget mechanism, so I added the smallest one.
- New `LATE_FAMILY_MAX_TOKENS = 4096` in llm_tuning.ts.
- New `jobMaxTokens(route, input)` in llm_routes.ts. It returns LATE_FAMILY_MAX_TOKENS for a region_economy job whose input mode is 'family', or 'enemy' (a stored 51.3 late-creature job). Otherwise it returns the route's maxTokens.
- `reservationMicroUsd` reads the stored request input of a region_economy job and reserves at jobMaxTokens. An unreadable request JSON falls back to the route cap.
- `buildClaudeRequest(route, layers, maxTokens?)` takes the job cap. The executor passes `jobMaxTokens(c.route, c.input)`.
- The truncation-retry reservation goes through the same function, so the reservation and the call always agree.
- Region-mode region_economy keeps REGION_CREATION_MAX_TOKENS.
- I added a one-line note under D-19 in CONTEXT.
- **Tests:**
  - the late-family cap is used for both the reservation and the request;
  - region mode and every other route are unchanged;
  - the largest one-family reply (4 members x 4 gear slots, every field at its cap) stays under 80% of the cap;
  - in region_economy.test.ts, real late-family jobs reserve at the late-family cap.

### WR-02: Placement side effects run unguarded inside the paid 2b apply

**Files modified:** `spacetimedb/src/helpers/world_gen.ts`; tests `world_gen_creation_wait.test.ts` and `world_gen_retry.test.ts`
**Commit:** 4d64690d
**Applied fix:**
- In `finishRegionFill`, `placeWaitingCharacter` runs in a try/catch that logs `Waiting character placement failed for state <id>: <ErrorName>`.
- In `placeHeldCharacters`, each HELD placement has its own try/catch (`Held placement failed for state <id>: ...`).
- `placeAtHome` and `placeWaitingCharacter` now write the side rows (visited row, pools) first and the character and state rows last. A throw therefore leaves the character at location 0 with his state unchanged, never half-placed.
- A HELD state that could not be placed stays HELD, and its `[explore]` places it through retryHeldStarter, which already handled this.
- New `placeAfterFailedPlacement`: a COMPLETE starter state whose character still waits at location 0 is placed by his `[explore]` (`retryStarterWorldGen` returns 'reused', with no call).
- **Tests:**
  - a throwing visited insert, for the starter character and then for a HELD character: the families, COMPLETE and the economy stay; the other character is placed; the failed one waits and is placed by his `[explore]`;
  - the retry case "the newest COMPLETE answers none" now places a character who is still waiting. 'none' is kept for an already placed character and for a missing region.

### WR-03: A duplicate starter region during the stage-1 window

**Files modified:** `spacetimedb/src/helpers/world_gen.ts`, `spacetimedb/src/helpers/llm_apply.ts`; tests `world_gen_creation_wait.test.ts` (7 cases)
**Commit:** cd4e6ea4
**Applied fix:**
- **Joining the build:** `reuseStarterRegion` looks for another character's starter build of the same race (case-insensitive) that is still PENDING or GENERATING. If one exists, the new state becomes HELD with no `generatedRegionId` and gets the 7e line. No model call is made and no second region is generated.
- **Stage 1 lands:** `applyWorldStartResult` calls the new `joinStarterHolds(tx, regionId, race)` before the fill starts. It names the region on those HELD states, so placement at COMPLETE and the 2a/2b failure lines reach them through the existing hold machinery.
- **Stage 1 fails:** `failWorldGen` now also posts its existing failure line to those waiting players (`starterBuildWaiters`), once per player. Players still waiting on another same-race build that is in stage 1 are not told.
- **`[explore]` with no region yet (`retryHeldStarter`):**
  - 'busy' while a same-race build is still in stage 1;
  - otherwise the race's region, once it exists;
  - otherwise (the build failed at stage 1) his own region starts on his state, charged to the asker ('started').
- `starterRegionFor` now picks the lowest region id, so duplicates that already exist resolve the same way every time.

### WR-05: Handing a starter build state to a HELD retrier hides it from the creator

### WR-07: A throw from the 2b or 2a enqueue on the [explore] path is not caught

**Files modified:** `spacetimedb/src/helpers/world_gen.ts`; tests `world_gen_retry.test.ts` (2 cases)
**Commit:** 373cd398 (shared with IN-05)
**Applied fix:**
- `startWorldFill` and `startWorldFamilies` catch a throw from `enqueueLlmJob` and log only the error name.
- They then call `settleStageStartThrow`. With no live job, the stage fails with its approved line and the result is 'refused':
  - 2a: failWorldFill with WORLD_FILL_FAILED_MESSAGE;
  - 2b: failWorldFamilies with WORLD_FAMILIES_FAILED_MESSAGE.
- The 7d line at the crossing, or the creation line, is posted. The region is never left stuck behind an internal error.
- **Tests:** an oversized 2b input (huge threats) and an oversized 2a input (huge start description) on the in-game `[explore]` both give 'refused', the error step with the approved message, one 7d line and no job.
- The single `route: 'world_gen'` enqueue site that the world_gen.test.ts source guard counts is preserved.
