# Phase 51.3.1.2: Code Review Report, Part B

**Reviewed:** 2026-10-09T14:30:30Z
**Depth:** deep (call chains traced into helpers/world_gen.ts, helpers/llm_apply.ts, helpers/llm_sweeper.ts, helpers/llm_executor.ts, helpers/character.ts, reducers/characters.ts, reducers/intent.ts, reducers/movement.ts)
**Files Reviewed:** 11
**Status:** issues_found

## Summary

**The server-side hold is sound for the new flow.** I traced every way a character's `locationId` can change:

- `performTravel`, reached from `move_character` and the two typed travel paths in intent.ts;
- the passage sweep;
- the two respawn paths, which use `boundLocationId`;
- `placeAtHome` and `placeWaitingCharacter`.

No quest, teleport, recall or summon reducer moves a character; corpse summon moves corpses only. The results:

- **No path in the new flow enters a held region.**
  - `travelHoldRefusal` runs before the party is gathered, so a leader, the followers he brings along and a member travelling alone are all refused the same way.
  - Nothing is spent on a refusal: no stamina, no cooldown, no leave roll.
  - A bind point can only point inside a region someone has stood in. Placement in creation is gated on `regionHoldState` (reuse) or on COMPLETE (`finishRegionFill`).
  - A held crossing never collapses, and the sweep leaves it alone.
  - An apply that throws rolls back (`withTx`), so no half-written stage-1 region can leave an ERROR state with a `generatedRegionId`.
  - Stranded FILLING and FILLING_FAMILIES locks are released to their error steps by the sweeper, so a hold cannot stick forever without an `[explore]` retry.
- **Travel back is always open.** The crossing (uncharted, then a passage) keeps the source region's `regionId`, so the trip back is same-region and is never held.
- **The four hold lines match the approved draft byte for byte.** I checked them with `prompt_draft.mjs chosen`. Each traveller of a trip gets 7a or 7d once per arrival.

**The defects are elsewhere:**

- **The prompt-draft tool (CR-01)** does not enforce its own contract: it emits and writes text from an unapproved draft, and in one case it returns the markdown bullet itself as the "approved line".
- **Older data (WR-01):** a failed region stays sealed when no crossing is left to retry from.
- **Speed of the hold check (WR-02):** a full scan of `world_gen_state` on every cross-region trip, on a table that grows by one row per character ever created.
- **Tooling that measures the wrong thing:** the sweep's place bounds (WR-03), and the proof's spend guard, which cannot stop the server-chained 2a/2b calls (WR-04).
- **A pinning test that breaks at milestone archive (WR-05).**

No script makes a paid call by default:

- `prove-live` needs `PROVE_LIVE_RUN=run` and the `uwr-verify` database.
- The other scripts in scope are pure rules with no I/O.

## Critical Issues

### CR-01: prompt_draft.mjs emits and writes text from an unapproved draft, and can return the raw owner bullet as the "chosen line"

**File:** `scripts/llm/prompt_draft.mjs:115-166` (ownerChoices), `:145-149` (raw-bullet fallback), `:154-159` (quote check), `:284-286` (`chosen`), `:294-300` (`write`)

**Issue:** The header says the tool "reads an owner-approved PROMPT-DRAFT.md". It does not enforce that. Only `status` looks at `status.approved`. `chosen`, `pins`, `write` and `check` all run on a draft whose status line reads `AWAITING OWNER APPROVAL`. The only remaining gate is a `grep` that each wiring plan must remember to run. There are three ways the tool can ship text the owner did not approve:

1. **Unapproved draft.** `write <heading> <CONST> llm_layers.ts` overwrites a shipped prompt block from a draft that is still awaiting approval. `chosen` prints lines from it and exits 0.
2. **Raw-bullet fallback for any key.** When a section's fences carry no `**Recommended`/`**Alternative` label, `ownerChoices` returns the owner-choices *bullet text* as the chosen line (`choices[key] = bullet`). That fallback exists only for section 6, but it fires for any key, including 7a to 7e. I reproduced this offline with a scratch draft whose 7a label line read `Recommended:` without bold:
   ```
   "7a": "**7a (arrive):** RECOMMENDED, but please say `Edited by owner.`"
   ```
   The command exited 0 and reported `approved: false`. A plan that copies `chosen` output into `region_hold.ts`, as Plan 06 did, would ship that markdown as player text. The pin tests would then pin the wrong text.
3. **Edits on a RECOMMENDED bullet are dropped.** The quote-versus-fence check runs only for ALTERNATIVE. If the owner writes `RECOMMENDED, but say \`...\``, the edit is silently ignored and the original fence text ships.

Smaller gaps in the same function:
- A later bullet for the same key silently overrides an earlier one.
- `parseDraft` takes the *first* line starting `Status: ` anywhere in the file, including inside a fenced example.

The strings shipped in this phase are correct: I verified 5 and 7a to 7e against the draft. The defect is the tool's guarantee, which later phases (52.x) rely on.

**Fix:**
```js
// in main(): refuse every copying mode on an unapproved draft
if (['chosen', 'pins', 'write', 'check'].includes(mode) && !(status.approved && status.date)) {
  throw new Error(`${mode}: draft is not APPROVED (${status.line ?? 'no status line'})`);
}

// in ownerChoices(): the raw-bullet fallback only for section 6, and duplicates are errors
if (key in choices) throw new Error(`owner choice ${key} listed twice`);
if (labelled.length === 0) {
  if (key !== '6') throw new Error(`owner choice ${key}: section has no labelled fences`);
  choices[key] = bullet;
  continue;
}
// quoted text must match the chosen fence whichever label was chosen
if (quote && quote[1] !== chosen[0].text) throw new Error(`owner choice ${key}: quoted text differs ...`);

// in parseDraft(): read the status line from the header only (before the first '## ')
```
Add a test case for each of these, starting with the reproduction above.

## Warnings

### WR-01: A region whose build failed before this publish is sealed from outside, and `[explore]` cannot reopen it once its crossing has collapsed

**File:** `spacetimedb/src/helpers/region_hold.ts:70-77, 90-97`; `spacetimedb/src/helpers/world_gen.ts:1219-1236` (retryWorldFill matching)

**Issue:** `regionHoldState` holds any region with a FILL_ERROR (or FILLING) build state. Under the old D-02, such a region was open: players walked in, bound there, and its passage collapsed into a direct border. After this publish:

- A player inside can leave, because the trip is to an open region.
- That player cannot come back. Travel in gets 7d: "Type [explore] to try again."
- `[explore]` at the border place outside does nothing. `retryWorldFill` matches only states whose `sourceLocationId` is the explorer's place (the collapsed passage, which no longer exists) or whose `generatedRegionId` is the explorer's own region. The explorer gets 'none' and then "There is nothing uncharted to explore here."

The 7d line names a retry that cannot run from where the player stands. Only someone still inside can retry. The local database has no such row (14-SUMMARY), and Plan 06 waved this off because "the owner regenerates the world". Maincloud has not been checked, and the owner publishes it by hand.

**Fix:** Pick one of these:
- In `retryWorldFill`, also match failed states whose `generatedRegionId` is the region of any neighbour of the explorer's place (a border crossing into the held region).
- Have `travelHoldRefusal` return 7d only when `fromLocation.id` is the state's `sourceLocationId`, and otherwise use a line with no `[explore]`.

At minimum, add the "no FILL_ERROR or FILLING rows" check to the maincloud publish checklist, next to the key-108 check.

### WR-02: Every cross-region trip scans all of `world_gen_state`, and the table grows by one row per character ever created

**File:** `spacetimedb/src/helpers/region_hold.ts:70-77` (called from `travel.ts:137`)

**Issue:** `regionHoldState` iterates the whole table, so every cross-region `performTravel` reads every row. The comment's premise ("the table is small") does not hold:

- `reducers/creation.ts:345` inserts a starter state for **every new character**.
- `travel.ts:441` and `intent.ts:1396` insert a row for every crossing attempt, failed ones included.
- Nothing ever deletes these rows.

The cost therefore grows with the total number of characters and attempts. It is paid on the hottest cross-region path, for regions that have been COMPLETE for months. The read also widens the reducer's read set to the entire table.

**Fix:**
- Add an additive btree index on `generatedRegionId`. Check that an index on an optional column is accepted, and publish locally without `--clear-database` first, as `passages.ts:145` asks.
- Or keep a small `region_hold` table, keyed by regionId, written by the step transitions.
- A cheaper interim fix: skip the scan when no in-progress or failed state exists, using a counter row maintained by the step writers.

### WR-03: The sweep's `world_gen` structural check disagrees with the server's place floor and trim

**File:** `scripts/llm/sweep_rules.mjs:334-339`

**Issue:** For a places-only (2a) reply, the check accepts 2 to 9 new places. The server (`writeRegionPlaces`, D-03) works differently:

- It **refuses** a reply with fewer than `REGION_PLACES_FLOOR - 1` = 5 new places (FILL_ERROR).
- It **trims** anything above `placeCount - 1`.

So a sweep marks replies with 2 to 4 places as structurally valid, although every one of them fails the fill in production. It also flags 10 or more places as `locations_count`, although the server accepts them by trimming. The 2a sweep figures therefore misreport exactly the failure mode D-03 introduced. The check also hardcodes the lower bound 2 instead of reading `DENSITY_RULES.REGION_PLACES_FLOOR`.

**Fix:**
```js
const minNew = placesOnly ? DENSITY_RULES.REGION_PLACES_FLOOR - 1 : 2;
if (!isObject(p) || !Array.isArray(p.locations) || p.locations.length < minNew) bad.push('locations_count');
// over-long places-only replies are trimmed by the server: report them separately (e.g. 'locations_trimmed'), not as invalid
if (!placesOnly && Array.isArray(p?.locations) && p.locations.length > 4) bad.push('locations_count');
```

### WR-04: The live proof's spend guard cannot stop the chained 2a/2b calls, and the deferred bound check was skipped in only one of its two places

**File:** `scripts/llm/prove-live.live.ts:241-255` (dry bound assertion), `:668`, `:726`, `:755`, `:790` (paidStep per step); `scripts/llm/proof_rules.mjs:358-360`

**Issue:**
1. **The guard runs too late for the region chain.** `paidStep(step)` checks the run cap once, *before* a step. The server enqueues stage 2a from the stage-1 apply, and stage 2b from the 2a apply, without the harness. When `paidStep('world_gen')` or `paidStep('world_gen_families')` refuses, those calls have already been made, so the per-step guard for them has no effect. `explore_region` likewise passes one check and then triggers three chained calls.

   With D-19's 20000-token cap, each region-creation call reserves about $0.21. A run near the $1.80 stop line can therefore pass the check and still commit about $0.63 more (start, 2a, 2b) per region. That overshoots the $2.00 cap the comment calls "never the harness's only bound".

2. **The bound assertion is half skipped.** D-19 defers the "bound under the stop line" assertion, and `proof_rules.test.mjs` now has it as `it.skip`. The dry run's own `expect(bound.total).toBeLessThan(stop)` at `prove-live.live.ts:254` is still live. The bound is $2.6669 against a $1.80 stop line, so the free dry run now always fails. Meanwhile the paid mode has no preflight bound check at all. The one gate that would warn before a paid run lives only in the mode that spends nothing.

**Fix:**
- Before calling the region-creation steps, check that the remaining run cap covers the whole chain (start + 2a + 2b reservations), for the starter and for `explore_region`.
- Move the bound check into a shared preflight that both modes run. While D-19 is deferred, make it print a loud warning in dry mode and *refuse* paid mode unless an explicit override env var is set, rather than leaving the two modes inconsistent.

### WR-05: The hold-line pin test reads the draft from the live phase folder and will fail when the milestone is archived

**File:** `spacetimedb/src/helpers/region_hold.test.ts:33-36`, and the same pattern in `llm_layers.world_gen.test.ts`, `llm_layers.world_gen_families.test.ts`, `world_gen_families.test.ts` and `scripts/llm/prompt_draft.test.mjs`

**Issue:** The test does `readFileSync(REPO_ROOT + '.planning/phases/51.3.1.2-bigger-regions/51.3.1.2-PROMPT-DRAFT.md')` at module load. Milestone cleanup (`gsd-cleanup`) moves phase folders into `.planning/vX.Y-phases/`; `v2.0-phases/` to `v2.2-phases/` already exist. After that move, the whole file throws ENOENT and every hold-line pin stops running. Its `toContain` check is also weak: it passes when the constant equals *either* variant, Recommended or Alternative, because both appear in the draft.

**Fix:**
- Resolve the draft through a small helper that also searches `.planning/*-phases/51.3.1.2-*/`.
- Or freeze a copy of the approved lines (and their sha256) under `spacetimedb/src/data/approved_copy/`.
- Compare against `ownerChoices(draft, { required })` output, not against `toContain` on the whole file.

## Info

### IN-01: The 7c line HTML-escapes the region name, but the client renders event text as plain text

**File:** `spacetimedb/src/helpers/region_hold.ts:41-44`

**Issue:** `sanitizeWorldData` is the *prompt* sanitizer: it turns `<` and `>` into `&lt;` and `&gt;`. The client never uses `v-html` or `innerHTML`, so a region name containing `<` would show the literal text `&lt;` in 7c. The discovery line posted right after it (`pickDiscoveryMessage`) uses the raw name. The risk is low, because the naming rules make angle brackets unlikely.

**Fix:** Use only `name.replace(/\s+/g, ' ').trim()` for player text, and keep `sanitizeWorldData` for prompt inputs.

### IN-02: Arriving at a failed crossing always posts 7d, even when the failure was a resting refusal

**File:** `spacetimedb/src/helpers/travel.ts:458-466`

**Issue:** `postFillFailure` (`world_gen.ts:1002`) tells people at the crossing `LLM_RESTING_LINE + [explore]` when the kill switch or the ceiling refused the call. Someone who arrives later gets 7d ("the storm does not pass") for the same state. This is not wrong, but the two messages describe the same moment differently.

**Fix:** When `arrivalHold === 'held_failed'` and the newest failed state's `errorMessage === LLM_RESTING_LINE`, post the resting line plus the explore hint instead.

### IN-03: Some people at the crossing never hear why they are held

**File:** `spacetimedb/src/helpers/travel.ts:451-466`; `reducers/intent.ts:1392-1406` (not in scope; noted for the hold)

**Issue:**
- People already standing at an uncharted crossing get nothing when generation starts through someone else's `[explore]` retry. The explorer gets the shimmer line, per the owner's choice. The others only learn about the hold when they try to travel (7b).
- When the trigger trip's `startWorldGeneration` is refused, only the leader gets the refusal line. Followers who arrived with him get no explanation.

D-15 says everyone at the crossing is held, which is true, but they are not told.

**Fix:** After a successful `[explore]` restart, post 7a to `character.by_location(crossing)`, as `crossingAudience` does. Optionally, copy the refusal line to the trip's followers.

### IN-04: The client keeps its own copy of the queue-exempt route list

**File:** `src/console/indicator.ts:44-45`

**Issue:** The file header says every list comes from the server module. `QUEUE_EXEMPT_ROUTES` is a client copy, and it now has to be edited by hand for each new fill stage. That breaks the "server is the source of truth" rule.

**Fix:** Export `LLM_QUEUE_EXEMPT_ROUTES` from `spacetimedb/src/data/llm_indicator_lines.ts` and import it through `@game-data`.

### IN-05: The families call is priced with a 3-place smoke input, and the sweep has no families check

**File:** `scripts/llm/proof_rules.mjs:158-162`; `scripts/llm/sweep_rules.mjs:314-350`

**Issue:** `proofPricingInput('world_gen_families')` falls back to `smokeInputFor`, which has 3 places. A real 2b input has 8 to 10 places and their hub names. The under-count is a few hundred characters (well under a cent), but it contradicts the "never under-count" claim. `structuralCheck('world_gen_families', …)` returns `unknown_route`, so a future families sweep would flag every reply.

**Fix:** Add a realistic `world_gen_families` sweep fixture (10 places) and a `case 'world_gen_families'` structural check (`families` array within `1..FAMILY_COUNT_MAX`).

### IN-06: The golden comment says the re-record covers families, but there is no families item

**File:** `scripts/llm/golden_rules.mjs:59-74`

**Issue:** The comment says `world_gen_families` "is listed so the re-record covers it", yet `GOLDEN_ROUTE_COUNTS` is unchanged with zero families items. The milestone-end paid golden re-record will never exercise the 2b prompt's tone or shape.

**Fix:** Add one or two `world_gen_families` golden items before the re-record, or correct the comment so the gap is visible.
