# Phase 51.3.1.2 Plan 12: [explore] retries only the failed stage Summary

`[explore]` now retries only the stage that failed. At the crossing or inside the region, a FAMILIES_ERROR state gets one world_gen_families job, a FILL_ERROR state gets world_gen as before, and FILLING or FILLING_FAMILIES is busy. A new character waiting in the creation console gets the same 2a or 2b retry on the same state (`'fill_started'`, WORLD_FILL_RETRY_LINE). The fresh-start retry stays only for a stage-1 ERROR.

## What changed

- `helpers/world_gen.ts`
  - `newestFirst` (private) sorts by createdAt descending, then id descending.
  - `restartFailedStage(tx, handed)` (private) calls `startWorldFamilies` for FAMILIES_ERROR and `startWorldFill` otherwise. It returns `'started' | 'refused'`.
  - `retryWorldFill`:
    - busy on FILLING or FILLING_FAMILIES;
    - otherwise picks the newest FILL_ERROR or FAMILIES_ERROR state, hands it to the explorer (playerId, characterId) and calls `restartFailedStage`.
  - `StarterRetryOutcome` gains `'fill_started'`. New private constant `STARTER_RUNNING_STEPS` = PENDING, GENERATING, FILLING, FILLING_FAMILIES.
  - `retryStarterWorldGen` checks in this order:
    1. busy if any starter state is running;
    2. `'none'` if there is no starter state;
    3. the newest FILL_ERROR or FAMILIES_ERROR state is handed to the asker (characterId kept) and only its stage restarts (`'fill_started'` or `'refused'`);
    4. if every starter state is ERROR, today's fresh-state path runs;
    5. anything else is `'none'`.
  - The `startWorldFamilies` doc comment now names the [explore] callers.
- `reducers/intent.ts`: the location-0 branch maps `'fill_started'` to WORLD_FILL_RETRY_LINE. The in-game comment now names the FAMILIES_ERROR/FILLING_FAMILIES retry. In-game behaviour is unchanged.
- `reducers/creation.ts`: `retryStarterFromCreation` maps `'fill_started'` to a `'creation'` WORLD_FILL_RETRY_LINE line.

No new wording. All lines are existing constants: WORLD_FILL_RETRY_LINE, STARTER_RETRY_MESSAGES, and the refusal and resting lines from failWorldFill and failWorldFamilies.

## Deviations from Plan

1. **[Rule 3 - Blocking] The intent.test.ts reducer cases are source-level checks.** `intent.test.ts` mocks `../helpers/location` with only `getWorldState`, so the real `submit_intent` cannot run there. The reducer-level `[explore]` cases are in `explore_retry.integration.test.ts`: in-game families/busy/fill/refused, the creation console, and submit_intent at location 0. intent.test.ts reads the explore branch of intent.ts and checks how each outcome maps to a line.
2. **Newest-state order** is now createdAt, then id, instead of id alone (CLAUDE.md core rule 4). The result is the same for real data.
3. **Starter ERROR rule kept as it is today.** A fresh state is made only when every starter state is ERROR, not whenever the newest one is ERROR. This is stricter than the plan's "newest decides" wording for ERROR, and it means a newest ERROR beside an older COMPLETE stays `'none'`, as before.
