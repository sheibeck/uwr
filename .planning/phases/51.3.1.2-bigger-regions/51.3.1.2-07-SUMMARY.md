# Phase 51.3.1.2 Plan 07: Bigger-region economy Summary

Regions with 8 or more charted places now get the medium economy (5 gatherables, 5 recipes). Each family past the 7-family design cap now gets its own late-family loot job, using the approved B2b wording. Rule loot is written only when that job fails, its reply can't be used, its start is refused, or the AI switch is off.

## What changed

**Task 1 (D-10): medium size by place count**
- `regionEconomySizeFor(placeCount)` in `data/economy_design_rules.ts` returns `'medium'` when the count reaches `DENSITY_RULES.ECONOMY_MEDIUM_MIN_PLACES`; otherwise it returns `REGION_ECONOMY_SIZE` (small).
- `buildRegionEconomyInput` (region mode) counts the region's charted places with the new exported `chartedPlaceCount`, which leaves out locations whose terrain is `uncharted` (trimmed, any case). It sizes `gatherSlots` and the recipe tier slots from that count. Family and enemy modes are unchanged.
- No change was needed in the validator or the prompt builder. Both already read the input's own `gatherSlots` and `recipeSlots`. A test confirms that `buildRegionEconomyVolatile` prints "five gatherables ... and five recipes" for the medium input with no builder change. `REGION_ECONOMY_COUNTS` is unchanged.

**Task 2 (D-11): late-family jobs, rule loot only as the fallback**
- `startRegionEconomy` sends `ruleFamilyIds: []`. `economyDesignFamilies` still picks the 7 designed families.
- `applyFamilyRegion` still writes a stored non-empty `ruleFamilyIds` list by rule, so jobs queued before this change finish unchanged.
- `writeRuleLootForFamily(ctx, regionId, familyId)` writes nothing unless three things hold: the region economy is `complete`, the family and region exist, and a member still lacks loot. When they hold, it builds the family-mode input, opens an apply book that owns the family's drop, trophy and gear slot keys, and calls `writeRuleFamily` over the region's existing gatherables. Because writes check for existing rows first, a second call writes nothing new.
- It is called from five places (the acceptance grep counts 6 including the definition):
  - `failRegionEconomy` for family mode;
  - `applyLateFamilyResult` when the reply is unusable or names another family;
  - `startLateFamilies` when the switch is off, for every family lacking loot (this replaces the early return);
  - `startLateFamilies` when a start returns `refused:*`;
  - `startLateFamilies` when a start throws.
- Existing complete regions are not touched. Nothing loops over existing regions, and a test checks that every path leaves a complete region's rows unchanged.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] Purity test allow-list**
- **Found during:** Task 1
- **Issue:** the `purity > imports only data modules` case in `economy_design_rules.test.ts` allows only a fixed list of data modules. The plan's `DENSITY_RULES` import failed it.
- **Fix:** added `density_rules` (a pure data module) to the allow-list.
- **Commit:** a41b7e91

**2. [Rule 2 - Missing critical] A start that throws also gets rule loot**
- **Found during:** Task 2
- **Issue:** the plan names only a start that returns refused. But `enqueueLlmJob` throws in some cases (for example, a job with no owner identity or a request context that is too large). Before this fix, the family was then left with no loot and no job.
- **Fix:** the `catch` around each family start in `startLateFamilies` also calls `writeRuleLootForFamily`.
- **Commit:** 01832edb

**3. [Expected behaviour change] Existing region_economy tests updated**
- `lateFamilyWorld` and the "reply left out a family" case now run the region apply with the switch on and an owned job. With the switch off, the left-out family now gets rule loot at once, as D-11 requires. A new case covers that switch-off path.
- The "unusable reply writes nothing" check and the "family job ignores a late-creature reply" check now expect rule loot, written once.
- The nine-family "rule families" case is split in two:
  - a new job sends `[]` and queues `family:4` and `family:5`;
  - a stored `['4','5']` context is still written by rule.
