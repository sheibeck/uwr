## Summary

Today a region is built by two chained LLM jobs. Stage 1 (`world_gen_start`) writes the region, the arrival point and the first NPC. Its apply enqueues stage 2 (`world_gen`) in the same transaction, and stage 2's apply writes everything else in one `writeRegionFill` call: 2-4 new places, their connections, hubs, 1-3 NPCs, 3-7 creature families with histories and a feud, then the uncharted boundary, and then chains the region economy job. [VERIFIED: llm_apply.ts:497-586, 593-645; world_gen.ts:914-1073]. The stage-2 reply is capped at 6144 output tokens and the route never retries, so a truncated reply fails the whole fill [VERIFIED: llm_tuning.ts:376; llm_limits.ts:42-50]. The one measured sample set (old reply shape, 3-5 places, 2-3 enemy types) came in at 1,658-1,988 output tokens in 15.7-21.0 s, about 90-100 tokens per second [VERIFIED: llm_measurements.json].

An 8-10 place region does not fit one reply. Scaling the measured shape by the field sizes in the schema, I estimate about 2,700 tokens for the places and people of a 9-place region and 4,000-5,000 tokens for 12-15 families with histories, so one reply would be about 7,000-8,000 tokens and about 80 s long [ASSUMED, see A1]. The split the success criteria describe is therefore required, not optional. The code is already well shaped for it: apply is guarded by the state's `step`, `world_gen_state.step` is a plain string (a new step needs no schema change), the writer already separates the places steps from the families step, and `completeRegionFamilies` already fills a whole region by rule when the AI gives none [VERIFIED: world_gen.ts:1002-1031; llm_apply.ts:597; tables.ts:2103-2120].

**Primary recommendation:** keep `world_gen` as stage 2a ("places and people": region facts, 7-9 new locations, NPCs; budget about 4096) and add one new cap-exempt route `world_gen_families` as stage 2b ("creature families": 12-15 families with histories and feud marks, told the real place count; budget about 7168), chained from the 2a apply exactly the way 2a is chained from stage 1. The region opens to players when 2a lands; 2b failure falls back to the rule family list and completes the region (never FILL_ERROR, which would let `[explore]` re-run 2a and duplicate places). The server rolls the place count (8-10), sets level offsets by a hop gradient, anchors the uncharted edge deliberately, and replaces the `FILL_PLANNED_PLACES` placeholder. The economy job's 7-family design cap (`ECONOMY_DESIGN_FAMILIES_MAX`) starts to bind for the first time, so about half the families of a 10-place region would get rule-made loot; that is the phase's biggest hidden quality cost and needs an owner decision.

```

   |  apply enqueues stage 2a in the same tx
   v
world_gen   = STAGE 2a "places and people"  (route name kept, reshaped)
   input : region, arrival, hub count, PLACE COUNT (server roll 8-10)
   reply : dominantFaction, landmarks, threats, arrival words/hub mark,
           7-9 locations (terrain, safe, hub, connectsTo, place words), NPCs

world_gen_families = STAGE 2b "creature families"  (NEW route, cap-exempt, no auto-retry)
   input : region facts, the real places (name, terrain, safe, hub), hub names,
           FAMILY COUNT = familyCountFor(real places), FEUD count (seeded)
```

### Pattern 1: Chain the next stage inside the apply transaction (existing pattern)
**What:** stage 1's apply ends with `startWorldFill(ctx, ...)`, which enqueues stage 2 in the same transaction; the state step is the lock; a refused enqueue degrades in place. Do the same from the 2a apply.
**When to use:** 2a -> 2b, and 2b -> economy.
**Example (sketch built from the existing code, not new API):**
```typescript
// Source: spacetimedb/src/helpers/llm_apply.ts:593-645 and world_gen.ts:784-818 (pattern)
export function applyWorldFillResult(ctx, job, resultText) {
  const state = ctx.db.world_gen_state.id.find(genStateIdOf(job));
  if (!state || state.step !== 'FILLING') return;          // stale or repeated apply: no-op
  /* parse, writeRegionPlaces(...) in this same transaction */
  ctx.db.world_gen_state.id.update({ ...state, step: 'FILLING_FAMILIES', updatedAt: ctx.timestamp });
  try {
    if (startWorldFamilies(ctx, state) === 'refused') completeFamiliesByRule(ctx, state);
  } catch (err) {                       // a chain bug must not roll back the paid places reply
    completeFamiliesByRule(ctx, state);
  }
}
```
Atomicity: `applyStored` runs apply in one `withTx` and retries it at most `LLM_APPLY_MAX_ATTEMPTS = 2` times from the stored text, never a second billed call [VERIFIED: llm_executor.ts:589-632]. Because the places write and the 2b enqueue share the transaction, either both happen or neither; the step guard makes a repeated apply a no-op.

### Pattern 2: A second-stage failure never reopens the first stage
`failWorldFill` sets FILL_ERROR and `retryWorldFill` (the player's `[explore]`) re-enqueues stage 2 for any FILL_ERROR state at the player's place [VERIFIED: world_gen.ts:826-901; intent.ts:1363-1376]. If 2b used that path, `[explore]` would run 2a again over a region that already has its places and add up to nine more (duplicates are skipped by name only, `world_gen.ts:941`). So 2b has its own terminal handling: complete by rule.

### Pattern 3: Server owns the numbers (D-46)
Place count, level offsets, graph degree, boundary anchor, family count and feud size are server rules in `data/`; the AI writes names, descriptions, terrain, safety, hub marks, connections, fit and histories. Same shape as hubs: the server rolls with a seeded roll that reads no timestamp (`hubSeed(regionId)`), prints the number in the user message, and re-derives it when writing the reply so request and write agree [VERIFIED: density_rules.ts:222-235; world_gen.ts:621, 768-775].

### Anti-Patterns to Avoid
- **A `part` flag on `world_gen` with a union schema:** the route table is one schema per route; unions are limited by `countUnionParams` in `schema_lint` [VERIFIED: PLAN 23 summary].
- **Setting FILL_ERROR for a 2b failure** (Pattern 2).
- **Letting a chain bug throw inside the 2a apply:** it would roll back a paid reply. Wrap the enqueue like the economy chain does (`world_gen` apply already wraps `startRegionEconomy` in try/catch, `llm_apply.ts:633-638`).
- **A new table or migration for stage state:** `step` is a plain string; no schema change is needed, which also removes any publish risk.
- **Keeping `keptFamilyCount = min(asked, familyCountFor(actual))`:** with `asked` fixed at 7 it would silently cap a 10-place region at 7 families (the existing test even pins `keptFamilyCount(9) = 7`, `density_rules.test.ts:865`).

### 3. Connectivity, boundary, level offsets, map

**Reachability.** Already guaranteed by step 4 (`world_gen.ts:978-986`): after `connectsTo`, any new place not reachable from the arrival point is connected directly to the arrival point. With 7-9 new places an AI listing that connects poorly turns the arrival point into a hub-and-spoke star (up to 9 exits at the arrival point). Proposed shape rule (pure, in `region_shape.ts`): repair an orphan component to the reached place with the fewest exits (ties by hop distance, then id), not always the arrival; trim extra edges above `EXIT_DEGREE_CAP` (proposed 4) only when the edge is not a bridge; keep the arrival point's source passage out of the count.

**Map layout with 10 nodes.** I ran the existing invariant suite from `src/map/graphLayout.test.ts` against four synthetic 10-place regions (each with one source-region border place, plus the uncharted boundary as place 10) in three modes (desktop 652x600, mobile 358x320, no canvas): a tree, a chain and a ring-with-chord (with a second border place) passed every invariant (no overlaps of labels, hit boxes, gates or caption; minimum 160 / 112 px gap; region inside the outline, borders outside; edges end on node centres). The star (arrival linked to all nine others) failed exactly one invariant in all three modes ("puts each other region on the side its neighbour faces", off by 3-5 px, for example 460 vs 455); all others passed. Conclusion: the layout copes with 10 nodes; extreme stars are a cosmetic edge case and the degree cap prevents them. The temporary test file was deleted; the planner should add 10-place fixtures to the `FIXTURES` list at `graphLayout.test.ts:112-117` (a tree, a chain, a ring; a star only if the layout is hardened). The test file is documented as timing-sensitive on this machine [CITED: 51.3.1.1-VALIDATION.md].

**Boundary placement.** Today the doorway hangs off "the last non-safe location in the AI's order" (`world_gen.ts:1053-1054`), which is arbitrary and, with 10 places, can sit next to the arrival point. Proposed: the place farthest from the arrival point by hops (prefer non-safe, non-hub; ties by lowest id), so the doorway is the far end and the region reads as a journey. Pure function, deterministic, tested.

**Level offsets.** The AI's `levelOffset` has no guidance in the prompt and a -10..10 clamp; with 9 places an AI could put a place ten levels above a level-1 region. Proposed: the server sets offsets for new locations by hop distance from the arrival point (the arrival keeps its stage-1 offset): `offset = arrivalOffset + min(LEVEL_OFFSET_MAX, floor(hops / LEVEL_HOPS_PER_STEP))`, with proposed `LEVEL_OFFSET_MAX = 2`, `LEVEL_HOPS_PER_STEP = 2`; the AI's offset field is dropped from the 2a schema (smaller reply, one fewer number the AI controls, consistent with D-46). Continuity argument: a new region's danger is the source's plus 50-100 (about half to one level), so a far-edge offset of +1 or +2 meets the next region's base level. Open point for the owner: the starter region (danger 100, level 1) would then have places up to level 3 (Q4).

## Common Pitfalls

### Pitfall 1: 2b failure sets FILL_ERROR
**What goes wrong:** `[explore]` re-enqueues 2a, which writes up to nine more places (dup names skipped, others added), two boundaries or two hub passes.
**Why:** `retryWorldFill` matches any FILL_ERROR state of the region (`world_gen.ts:867-901`).
**How to avoid:** 2b ends in COMPLETE by rule. Test: fail 2b by every path (call failure, truncation, malformed JSON, refused enqueue, apply_error after two attempts, sweeper) and assert COMPLETE, a full family set and unchanged place count.
**Warning signs:** a world_gen_state row in FILL_ERROR whose region already has more than one place.

### Pitfall 2: The chained enqueue throws and rolls back a paid reply
**How to avoid:** wrap `startWorldFamilies` in try/catch and fall back to the rule fill (Pattern 1); test with an enqueue that throws.

### Pitfall 3: The browser holds the player's input during 2b
`QUEUE_EXEMPT_ROUTES = ['world_gen']` in `src/console/indicator.ts:45`. A new route not listed gates narrative sends for the 40-50 s of 2b. Also add the route to `LLM_CREATION_CONSOLE_ROUTES` (the starter world's fill shows in the creation console, `llm_indicator_lines.ts:70-78`), to `LLM_INDICATOR_LINES`, `LLM_INDICATOR_POOLS` and `LLM_INDICATOR_PRIORITY`. The two existing `world_gen` pool lines "deciding who else lives out here" and "placing things that will want to eat you" describe families and could move to the new route's pool; moving existing approved lines still goes through the owner copy review (D-58).

### Pitfall 4: Cap refusal on the second chained job
Add the route to `LLM_CAP_EXEMPT_ROUTES` (`llm_queue.ts:165`) and the no-retry list (`llm_limits.ts:42`). Test the chain with a player holding two other active jobs.

### Pitfall 5: Silent family cap at 7
`keptFamilyCount` = min(asked 7, real). Removing `askedFamilyCount` while leaving `keptFamilyCount` unchanged keeps 10-place regions at 7 families without failing any new test except the one that pins 7. Add an explicit 8/9/10 -> 12/13/15 end-to-end test.

### Pitfall 6: Economy cap now binds
`ECONOMY_DESIGN_FAMILIES_MAX = 7`. See Q8; without a decision, 40-55% of a big region's families get rule loot.

### Pitfall 7: Players enter places before the families land
Between the 2a apply and the 2b apply a place has resource pools (the lazy `ensurePoolsForLocation` seeds them) but no creature pools and no `location_enemy_template` links, so it simply has no creatures [VERIFIED: families.ts:707-750]. When 2b lands `seedRegionPools` is find-or-create and adds the creature pools. Test this exact order (visit, then apply 2b) and the rating "Unknown until pool rows apply, never Safe" text path (`rails/exits.ts` header).

### Pitfall 8: Too few host places
AI-marked safe places plus up to 2 forced-safe hubs can leave fewer than 4 host places; then `assignRegionFamilies` leaves families unplaced (`density_rules.ts:908-917`). Server floor rule plus a grid test (hosts 2-8 x families 12-15).

### Pitfall 9: Star topology and absurd offsets
Covered above: degree cap, least-connected repair, server gradient.

### Pitfall 10: Pins, snapshots and the 64 KB request limit
Both blocks are pinned by sha256 and length; the claude_request and schema snapshots must be refreshed deliberately (inspect, do not blindly `-u`). The 2b input lists places and hub names; at 9 places that is well under `LLM_REQUEST_JSON_MAX_CHARS = 64,000`, but cap the per-place description excerpt in the input and pass every string through the existing `w()` sanitizer (second-order injection: model text from 2a becomes part of the 2b prompt).

### Pitfall 11: Publish-time in-flight jobs
A `world_gen` job queued before the publish will be built with the new block. Its stored input has no place-count line; the builder must print no line (as with `Hubs`) and the apply must use the server's own count. A job already in flight under the old schema returns a `families` array: keep the legacy branch.

### Pitfall 12: Existing regions
Nothing may iterate existing regions to grow or relink them. The only touch points are the world_gen write path and tests. Add a test: apply 2a/2b for a new region in a world that already has a COMPLETE 4-place region and assert the old region's place, family and pool rows are byte-identical.

## Security Domain

`security_enforcement` is absent from config, so it is enabled.

### Applicable ASVS Categories
| ASVS category | Applies | Standard control |
|---------------|---------|------------------|
| V2 Authentication | no | no new entry point; world generation is triggered by existing reducers using `ctx.sender` |
| V3 Session Management | no | n/a |
| V4 Access Control | yes (light) | the chain runs from module-driven applies; the new apply must check the state belongs to the job (genStateId from the stored request) and the step guard; no new reducer should be callable by clients (add none) |
| V5 Input Validation | yes | all model output is untrusted: place count, names, graph, terrain/enums, hub marks, history text, family fields go through validators; server clamps every number |
| V6 Cryptography | no | none; the API key is already redacted in logs (`redactSecrets`) |
| V11 Business logic / abuse | yes | cost: every call reserved against the player day and the global ceiling, kill switch honored, no automatic retry, bounded chain length (2 stages), `LLM_REQUEST_JSON_MAX_CHARS` |

### Known Threat Patterns
| Pattern | STRIDE | Standard mitigation |
|---------|--------|---------------------|
| Second-order prompt injection: model-written place names and descriptions from 2a flow into the 2b prompt | Tampering | pass every value through `w()` / `sanitizeWorldData` on one line, cap lengths, no player text anywhere in the chain; tag test as in 51.3.1.1 (`<player_input>` absent) |
| Oversized or hostile reply (hundreds of locations, huge graph) | DoS | `SCAN` limits, trim to the rolled count, floor rule, schema-level `additionalProperties:false`; truncation fails the stage, never retries |
| Cost amplification (extra billed stage per region, retries) | DoS / EoP | cap-exempt only for these routes; ceiling and daily budget still apply; no retry; one 2b per genState (dedupe key) |
| Forged chain (client causes a 2b apply) | Spoofing | `llm_run` guard (module identity) already protects dispatch (`llm_executor.ts:652-654`); no new reducer |
| Information leak: reply text or prompts in logs | Information disclosure | keep the existing log line (counts only) and in-voice fixed error messages; `world_gen_state` is public so `errorMessage` stays a fixed line |
| Duplicate regions from repeated apply or retry | Tampering | step guards, idempotent writers, Pitfall 1 test |

## Owner Questions (for discuss)

Ordered by how much each shapes the plans. Each has options, a recommendation, and evidence. If the owner says "your call", the recommendations are a coherent set.

**Q1. How is generation split?**
- A) Two stages after stage 1: 2a places and people, 2b creature families (recommended).
- B) Three stages: places, NPCs, families.
- C) Families in two batches of about 7.
- D) Families in parallel with places (fit by terrain only).
- Why A: the measured throughput is about 95 tokens per second and the old single reply already used ~1,800 tokens; scaled estimates give ~2.7k + ~4-5k tokens for 9 places and 12-15 families, so one reply (~7.5k, ~80 s) would exceed the 6144 budget; A keeps both replies under 80% of budget, keeps names exact (families see the real places and hubs), and costs one extra call. B and C add calls without a measured need; D loses fitLocations and the real place count (D-66 wants it).

**Q2. When does the region open to players?**
- A) When the places land (2a); creatures arrive about 40-50 s later (recommended).
- B) Hold the exits shut until the families land (~90 s total wait).
- Why A: players can already act during stage 2 today; a place without families simply has no creatures for under a minute, and the pool code seeds the creature pools when they land. B makes every new region feel slower for a rare cosmetic gap. Needs one new test either way.

**Q3. How many places exactly, and who decides?**
- A) The server rolls 8-10 (seeded), tells the AI "N places in all, arrival included", trims extras, accepts a shortfall down to a floor of 6, fails the fill below it (recommended).
- B) The AI picks within 7-9 more, server only clamps.
- C) Fixed 9.
- Why A: same mechanism as the hub and family counts the owner already approved; deterministic and testable; the count in the message keeps replies from drifting. The 10 includes the arrival point (owner decision recorded in 999.26). The floor and range are named constants for 52.5.

**Q4. Level gradient across the region.**
- A) The server sets each new place's offset by hop distance from the arrival point: +1 per 2 hops, at most +2; the AI no longer writes levelOffset (recommended).
- B) The AI sets offsets, the server clamps to a small range.
- C) Flat (all 0).
- Sub-question: should the starter region be flatter (max +1, so a level-1 start has no level-4 place)?
- Why A: today's -10..10 clamp lets an AI create a place ten levels away; a new region's danger is the source's +50..100 (half to one level), so +1 or +2 at the far edge meets the next region. It also shortens the reply and follows "AI names, server numbers". Needs a one-line removal from the approved wording.

**Q5. Region shape rules.**
- A) Deliberate shape: the uncharted doorway at the farthest place from the arrival, at most 4 exits per place (non-bridge trims only), orphan repair to the least-connected reached place, at least 4 host places (recommended).
- B) Leave as today (AI listing order, repair to the arrival point).
- Why A: today's doorway is "the last non-safe place the AI listed" and the repair makes stars; I verified the map handles tree, chain and ring shapes of 10 nodes but a nine-spoke star breaks one cosmetic invariant by 3-5 px, and with fewer than 4 hosts the 12-15 families cannot all be placed.

**Q6. NPCs in a bigger region.**
- A) Raise the AI count from "1-3 more" (owner wording, D-65) to "3-5 more" besides hub vendors and bankers (recommended).
- B) Keep 1-3.
- Why A: 9 places with 1-3 NPCs leaves most places empty and NPC conversation is a core feature; cost is about +2 NPCs (~460 tokens, still inside the 2a budget). Wording change needs approval.

**Q7. Hubs in bigger regions.**
- A) Leave the D-62 rolls as they are (recommended for this phase).
- B) Raise the second-hub chance (now 10%) when a region has 8+ places.
- Why A: D-62 is the owner's own wording ("more than one hub should be rare"); with 9 places and one hub services can be several hops from the far end, which is a feel judgement best made at the milestone UAT. The constants are already dial-ready (`SECOND_HUB_PCT`).

**Q8. Economy for bigger regions (two decisions).**
- Q8a size: A) keep `small` (3 gatherables, 3 recipes); B) `medium` (5 and 5) for regions of 8+ places with `region_economy` budget raised from 4096 to about 6144 (recommended); C) `large`.
- Q8b the families past the 7-family design cap (now 5-8 per region): A) rule-made loot as the code does today; B) one late-family job each with the already-approved B2b wording, rule loot only if that job fails (recommended if AI-named loot matters); C) raise the cap with a single larger call.
- Why: the cap of 7 was sized when a region had at most 7 families, so this phase makes it bind for the first time (40-55% of families on rule loot). B costs 5-8 extra small calls (about $0.005 each) and reuses approved wording and existing code, but it is the largest single item in the phase and is easy to schedule last; A is the lean path. C risks truncating the whole economy. Size B needs no new wording (the count words exist).

**Q9. What happens if the families call (2b) fails?**
- A) Fill by rule and complete the region; no retry (recommended).
- B) Mark a separate error and let `[explore]` retry only the families call.
- Why A: matches "fails over to rules as today" and the owner's note that the whole world will be regenerated; B needs a second retry state and a retry branch in `retryWorldFill`. In both, 2b must never reuse FILL_ERROR (it would duplicate places).

- A) Ship with estimated budgets, run one owner-approved paid region at milestone-end UAT and set the real budgets then (recommended; matches the defer-UAT rule and the 51.3.1.1 precedent).
- B) Run the paid check inside this phase.
