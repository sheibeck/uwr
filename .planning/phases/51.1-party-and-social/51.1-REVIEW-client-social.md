## Summary

I reviewed every file under `src/social` in the range: the menus (`playerMenu.ts`, `PlayerMenu.vue`, `ActionMenu.vue`, `menuPosition.ts`, `menuRegistry.ts`), the action layer (`partyActions.ts`), the follow rule (`follow.ts`, `FollowIcon.vue`), the cards (`MemberCard.vue`, `CombatMemberCard.vue`), the invites (`InviteCard.vue`, `OutgoingInvites.vue`), the pets (`PetRow.vue`, `PetTag.vue`), `TravelSwitch.vue`, the shared `StatusDot` and `CharacterName`, and the social hub (`socialData.ts`, `socialContext.ts`, `queries.ts`). I read the tests for reliability.

I traced calls into:
- the hosts: `src/rails/PartyBlock.vue`, `src/frame/VitalsRail.vue`, `src/frame/VitalsStrip.vue`, `src/frame/FeedShell.vue`, `src/rails/NearbyList.vue` and `src/screens/SocialScreen.vue`;
- the client helpers: `src/game/keyedBinding.ts`, `src/net/bindTable.ts`, `src/map/secondsTick.ts`, `src/ledger/actionRunner.ts`, `src/ledger/InlineConfirm.vue`, `src/rails/party.ts` and `src/session/useSession.ts`;
- the server: `spacetimedb/src/reducers/groups.ts`, `spacetimedb/src/helpers/group_invites.ts`, `spacetimedb/src/helpers/travel.ts` and `spacetimedb/src/data/group_config.ts`.

**What checks out:**
- **Menu entries by role.** They match the UI-SPEC table:
  - yourself, as leader, member and solo;
  - a party member, seen by the leader and by a member;
  - pending invites, for the leader and the inviter;
  - `Leader invites`, `Party full`, `In another party` and `Offline`.

  The pending rule for `Cancel invite` matches the server's `cancel_group_invite`. The `Party full` cap counts members plus live invites, as `invite_to_group` does. The Leave prompt names the same successor as `nextLeaderAfter`.
- **Follow rule.** `followState` goes through the shared `comesAlongWithLeader`. It reads `online === true` and `locationId` equality, exactly as `performTravel` does.
- **Invite expiry.** It is display-only, with `createdAt + GROUP_INVITE_TTL_MICROS` from `@game-data`. `Expired` shows from exactly the TTL, the same boundary as the server's `isInviteExpired`. Accept and Decline become `aria-disabled`.
- **Subscriptions.** Every query has a WHERE on an indexed column, and every keyed binding filters to its own key (shared-cache rule). Group-keyed bindings swap immediately. `reset()` and `dispose()` clear every binding on logout. A character switch re-keys every binding.
- **Security.**
  - No surface renders an email. Nothing subscribes to `user`.
  - There is no `joinGroup` or `join_group` call, so Accept is the only way in.
  - The only feed line the client writes is the shared `SEND_ERROR_TEXT` client rejection.
  - Names render as text nodes only. There is no `v-html`.
- **Accessibility.**
  - Target buttons contain no interactive descendants, and every `⋯` is a sibling.
  - The menus have `role="menu"`, `menuitem` and `separator`, plus `aria-haspopup`, `aria-expanded` and `aria-controls`.
  - The keyboard works: arrows wrap over disabled items, Home and End jump, Escape is stopped before it reaches a drawer, and Tab closes the popover.
  - Only one menu is open at a time.
  - The mobile sheet is a modal dialog with a focus trap. Mobile controls are at least 44px tall, and menu rows are 48px.
- **Design guard.**
  - Type sizes are 10, 12 and 14 only, and weights are 400 and 500 only.
  - There are no negative margins. The pet elbow's `left: -12px` is a spec Exception.
  - Every icon is Phosphor. There are no literal colours.
- **Reducer calls.** All use object syntax, and all go through `partyActions`.

The `src/social` suites pass: 18 files, 514 tests.

There are no blockers. The defects are:
- three party controls swallow a rejected reducer promise;
- a player left alone in a group has no Leave path and can't be invited;
- focus falls to `body` when the server removes an invite card or an outgoing row;
- the desktop menu popover stays put when its rail scrolls.

## Warnings

### WR-01: The invite card, the outgoing invites and the Travel switch swallow rejected reducer calls

**File:** `src/social/InviteCard.vue:26,92-97`, `src/social/OutgoingInvites.vue:26,67-73`, `src/social/TravelSwitch.vue:20,56-59`
**Issue:** Each of these components builds its own `createActionRunner`. A rejected promise only increments `runner.rejection` and returns `false` (`src/ledger/actionRunner.ts:42-44`), and none of the three ever reads `runner.rejection`. `PlayerMenu.vue:52-57` does read it and prints `SEND_ERROR_TEXT`, but these three do not. The runner is internal, so no host can pass the count to a `NoticeLine`; `SocialScreen.vue` mounts `<NoticeLine :kinds="SHEET_KINDS" />` with no `rejection`. The UI-SPEC Copywriting contract requires `Couldn't send that. Try again.` for a client rejection. This is the same defect as Phase 51 WR-01, now in three new places.
**Failure scenario:** The player taps Accept as the transport drops, or as `requireCharacterOwnedBy` throws `SenderError` after a character switch mid-flight. The buttons turn from inert back to enabled, the card stays, and nothing is written to the feed or to the sheet's `NoticeLine`. The same happens for `Cancel invite` and the switch.
**Fix:** Mirror the `PlayerMenu` pattern in each of the three components:
```ts
import { SEND_ERROR_TEXT, createActionRunner } from '../ledger/actionRunner';
watch(
  () => runner.rejection.value,
  (next, previous) => {
    if (next > previous) game.feed.appendLocal('system', SEND_ERROR_TEXT);
  },
);
```
Better still, hoist one `runner` and the watch into a shared `usePartyActions()` (see IN-01). Add a test per component that rejects the reducer and expects the line.

### WR-02: A player left alone in a group gets no Leave path and can't be invited

**File:** `src/social/playerMenu.ts:104-107` (`selfEntries`: `if (group === null || input.memberCount <= 1) return [];`); hosts `src/frame/VitalsRail.vue:49-53` (`selfMenuShown` requires more than 1 member) and the sheet self card through `MemberCard` → `PlayerMenu`
**Issue:** The client treats a one-member group as solo, so there is no self `⋯` and no `Leave party`. The server does not dissolve such a group after a leave or a kick:
- `leave_group` keeps the group whenever `nextLeaderAfter` finds anyone (`groups.ts:133-145`);
- `kick_group_member` keeps it while at least one member remains (`groups.ts:276-285`);
- `dissolveLoneGroup` is called only from `endInvite` (`helpers/group_invites.ts:79`).

So the last remaining member stays in a persistent `Party · 1` group.
**Failure scenario:**
1. A and B are partied. A (the leader) leaves, and B becomes the leader of a one-member group.
2. B sees `Party · 1` and a self card with no `⋯`. No UI offers Leave.
3. Every other player's menu shows B's `Invite to party` disabled with `In another party`, because `target.groupId !== null`. The server refuses too, with `B is already in a group.`
4. B stays un-invitable until they type `leave` in the console, or send an invite of their own and let it expire.

The playerMenu test at line 119-124 pins this ("A lone group ... is also solo"). It only fits the pending-invite case, not the stranded case.
**Fix:** Show `Leave party` to a member of any group, and hide only the Travel entry when nobody else is in it:
```ts
function selfEntries(input: PlayerMenuInput): MenuGroup[] {
  const { group, self } = input;
  if (group === null) return [];
  const isLeader = group.leaderCharacterId === self.id;
  const entries: MenuEntry[] = [];
  if (!isLeader && input.memberCount > 1) { /* travel entry as today */ }
  entries.push(/* leave entry as today */);
  return nonEmpty([{ key: 'party', entries }]);
}
```
Relax `VitalsRail.selfMenuShown` to match. Alternatively, have the server call `dissolveLoneGroup` at the end of `leave_group` and `kick_group_member` when no invite rows remain. Either way, add a test for "the last member after a leave".

### WR-03: Focus falls to `body` when the server removes the invite card or an outgoing row

**File:** `src/social/InviteCard.vue:39,121-122`; `src/social/OutgoingInvites.vue:40,75-92,99`
**Issue:** Focus handling exists only after the local action. `answered` is emitted after Accept or Decline, and the `cancelled` mark is set after Cancel invite. Server-driven removals have no handling:
- the incoming invite row is deleted by the expiry tick, or ended by the inviter's cancel, or the group dissolves;
- an outgoing row is deleted when the target accepts or declines, or by the expiry tick.

If focus sat on Accept, Decline or a row's `Cancel invite`, the `v-if` removes the focused button and focus drops to `document.body`. When the last outgoing row goes, the whole `section` unmounts. The UI-SPEC Accessibility Contract keeps the Phase 50 rule that focus never falls to `body` after a removal ("focus after removal work as in 50"), and the Phase 51 review treated the same pattern as WR-03.
**Failure scenario:** A keyboard player tabs to Accept and hesitates. The card reads `Expired` (both buttons `aria-disabled`), then the server deletes the row. Focus is now on `body`, and the next Tab starts from the top of the page.
**Fix:** In each component, watch the shown or visible state (or the row list) with `flush: 'pre'`. If `document.activeElement` is inside the component root, move focus after `nextTick` to a stable target:
- emit `answered` from InviteCard, so the host focuses the Party heading or the composer;
- emit `focusHeading` from OutgoingInvites, or focus the next row's `Cancel invite`, reusing the existing index logic.

Add tests that delete the row while the button holds focus.

### WR-04: The desktop menu popover does not follow its opener when a rail scrolls or the window resizes

**File:** `src/social/ActionMenu.vue:104-133`; `src/social/PlayerMenu.vue:144-153`
**Issue:** The popover is `position: fixed`, placed once from the opener's `getBoundingClientRect()` at open. It is re-placed only when the entry groups or the confirm state change. Nothing listens for `scroll` (capture phase, so rail scrolls count) or `resize`, and a wheel or trackpad scroll fires no `pointerdown`, so the outside-click close never runs either.
**Failure scenario:**
1. The player opens `⋯` on a Nearby player in the context rail and scrolls the rail with the wheel.
2. The menu stays fixed in the viewport while its row and opener scroll away. The menu now sits beside a different player's row, and the only cue is the header name.
3. A resize can leave the panel partly off-screen, because the 8px viewport clamp is not re-applied.
**Fix:** While the menu is open on desktop, either close it on any scroll or resize (the simplest, and common for menus), or re-place it from the opener's rectangle:
```ts
// PlayerMenu.openMenu (desktop only)
window.addEventListener('scroll', onScrollOrResize, true);
window.addEventListener('resize', onScrollOrResize);
function onScrollOrResize() { closeMenu(false); }
// and remove both in closeMenu / onBeforeUnmount
```

## Info

### IN-01: The "one action runner" guarantee holds per component, not across surfaces

**File:** `src/social/partyActions.ts:6-11` (header comment), with runners created in `PlayerMenu.vue:44`, `InviteCard.vue:26`, `OutgoingInvites.vue:26` and `TravelSwitch.vue:20`
**Issue:** The module header says every party reducer "goes through one action runner: a second click on the same action and name while it is pending sends nothing". In fact each component instance builds its own runner, so pending and dedupe are per instance. Two examples:
- the Nearby `⋯` → `Cancel invite` and the `Invited · waiting` row's `Cancel invite` for the same player can both send;
- the Travel switch and the self menu's `Stop travelling with leader` can both send.

The second call is refused by the server (`No pending invite to {name}.`) or is a no-op, so the cost is a spurious refusal line and an entry that does not show as pending.
**Fix:** Create one runner in the session (or provide one through a `PARTY_ACTIONS_KEY`) and inject it in all four components. Otherwise, correct the comment so it promises only per-surface dedupe.

### IN-02: InviteCard emits `answered` even when the server refused the answer

**File:** `src/social/InviteCard.vue:92-97`
**Issue:** `ok` is true whenever the reducer promise resolves. `fail()` refusals resolve normally. For example, `joinFromInvite` returns `Group is full.` before it deletes the invite (`groups.ts:49-50`). The card stays, but the host has already moved focus to the Party heading (`PartyBlock`) or to the composer (`FeedShell`). The player's focus leaves a card that still asks for an answer.
**Fix:** Emit `answered` only when the invite row is actually gone. Watch `invite.value?.id` for the answered id, and emit when it disappears. This shares a code path with the WR-03 fix.

### IN-03: The 1-second tick runs while no timer is shown

**File:** `src/social/socialData.ts:201-210`
**Issue:** `tickActive` is true for any outgoing invite of the group, any incoming invite row and any timed pet of any party member. It stays true even where none is displayed:
- in combat, where `Invited · waiting` is hidden;
- for a member who is neither the leader nor the inviter, who never sees those rows;
- on mobile out of combat with the Party sheet closed, where no pet row is mounted;
- while the inviter's name is unresolved and the card is hidden.

The UI-SPEC says timers tick "only while a timer is shown". The cost is small, but it contradicts the contract and the hub's own comment.
**Fix:** Let the surfaces register interest (a ref-counted `useTick()` that each timer component calls while mounted), or narrow `tickActive` to what is visible. Keep the `refresh()` on row changes.

### IN-04: An expired-but-not-yet-deleted pet reads `0:00` and "fades in about 1 minute"

**File:** `src/social/PetRow.vue:32-36,60-64`; `src/social/PetTag.vue:17-24`
**Issue:** `secondsLeft` reaches 0 before the server deletes the pet row, and `aboutMinutes(0)` returns `about 1 minute`. Screen-reader users hear "fades in about 1 minute" for a pet that has already faded, and sighted users see `0:00` on a countdown with no end state. The invite and outgoing rows show `Expired` in the same case.
**Fix:** When `secondsLeft === 0`, hide the clock and the sentence. Alternatively, show a `Fading` state in place of the clock and drop the "fades in" clause.

### IN-05: The Travel switch announces its sub-line twice

**File:** `src/social/TravelSwitch.vue:70-78`
**Issue:** The switch's accessible name comes from its content, which already includes the sub-line: "Travel with leader On · you move when Bram travels". `aria-describedby` then points at the same sub-line, so it is read again as the description. The sub-line also says "On"/"Off", which duplicates `aria-checked`.
**Fix:** Name the switch with only the title: `aria-labelledby` on the title span's id. Keep `aria-describedby` on the sub-line.

### IN-06: Crown icons carry `aria-label` without `role="img"`

**File:** `src/social/InviteCard.vue:144`, `src/social/MemberCard.vue:94`, `src/social/CombatMemberCard.vue:143`
**Issue:** `PhCrownSimple` renders an `<svg>`. An `aria-label` on an `svg` that has no `role="img"` is ignored by several screen-reader and browser pairs, so "Party leader" may never be announced. The out-of-combat member card and the invite chips rely on it to say who leads.
**Fix:** Add `role="img"` next to `aria-label="Party leader"`, or make the crown `aria-hidden` and add an `.sr-only` "leader" twin, as the follow icon does.

### IN-07: The rail's unknown-member card exposes progressbars with a maximum of 0

**File:** `src/social/MemberCard.vue:118-143`
**Issue:** For an unknown member, `partyMembers` returns `hp`, `maxHp`, `resource` and `maxResource` as `0n` (`src/rails/party.ts:150-168`). The rail variant still renders both bars, with `aria-valuemax="0"` and the label `Member health 0 of 0`. That is an invalid progressbar range and misleading text. The combat card already drops the bars for unknown members (UI-SPEC "Unknown member: … no bars").
**Fix:** Render the bars only when `known` (`v-if="known && (!isSheet || !props.self)"`, and likewise for the resource bar).

### IN-08: Small design-contract deviations

**File:** `src/social/TravelSwitch.vue:112,155`; `src/social/PetTag.vue:40-47`; `src/social/InviteCard.vue:223`
**Issue:**
- **TravelSwitch.** Disabled is `opacity: 0.6`. The contract ("Disabled is 45% opacity") and every other surface use 0.45. The 0.6 also flickers on each toggle while the call is pending. The track's radius is the literal `8px` instead of `var(--radius-md)`.
- **PetTag.** It does not override the global `.tag` padding, which is `3px 10px` (`src/styles/nocturne.css:224`). That is off the spacing scale and is not the spec's `0 8px` for the pet tag.
- **InviteCard.** The `Party invite` kicker is weight 500. The contract role is Micro 10 / 400.

**Fix:**
- TravelSwitch: `opacity: 0.45`, and `border-radius: var(--radius-md)`.
- PetTag: add `padding: 0 8px` to `.pet-tag`.
- InviteCard: `font-weight: 400` on `.kicker-label`.

### IN-09: Dead hub fields and a duplicated width constant

**File:** `src/social/socialContext.ts:21,26`, `src/social/socialData.ts:177-178,236-242`; `src/social/menuPosition.ts:7` and `src/social/ActionMenu.vue:304`
**Issue:** `petsApplied` and `outgoingApplied` are built, exported and kept in the inert hub, but no production code reads them. `MENU_WIDTH = 224` is used for placement, while the panel's CSS hard-codes `width: 224px`. If one changes without the other, the left-side clamp misplaces the panel.
**Fix:** Drop the two unused refs, or use them to gate the rows. Bind the width from the constant (`:style="{ width: `${MENU_WIDTH}px`, … }"`), or add a test that pins the two together.
