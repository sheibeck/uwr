## Warnings

### WR-01: The re-invite wait can still be skipped with a second character, because a withdrawal caused by another member starts no wait

**File:** `spacetimedb/src/helpers/group_invites.ts:77-80` (`startsReinviteWait`), `:267-274` (`settleGroupAfterLeave`, `empty`), `:276-284` (the `stays` path keeps the leaver's invite); `spacetimedb/src/reducers/groups.integration.test.ts` ("a withdrawal the inviter did not cause starts no wait")
**Issue:** `startsReinviteWait` starts the wait for `withdrawn` only when `actor.id === invite.fromCharacterId`. An attacker A with a second character M (an alt account, or a friend) can loop as follows:
1. A invites M, and M accepts. The group is {A, M}, and A leads.
2. A invites C. C gets "A invited you to a group…".
3. A leaves. One member is left and a live invite is out, so the outcome is `stays`. M leads alone, and A's invite stays live.
4. M leaves. Nobody is left, so the outcome is `empty`, and the invite ends as `withdrawn` with actor M. M is not the inviter, so no wait starts. C gets "The invite from A is no longer open.".
5. Go back to step 1. A→M was an accepted invite, so it has no wait. At step 2, `liveInvitesTo(C)` is empty and `reinviteWaitActive(A, C)` is false.

Each cycle costs five reducer calls and sends C two lines, with no throttle. That is the spam pattern the WR-02/WR-01 guard exists to stop. The new test "a withdrawal the inviter did not cause starts no wait" pins step 4 as intended behaviour.

The only withdrawal where skipping the wait is right is a deletion. There the deleted character's waits are removed anyway (`characters.ts:175-179`), and a deleted target cannot be invited again.
**Fix:** Start the wait for every `withdrawn` end except one caused by a deletion. Make that explicit, instead of inferring it from the actor:
```ts
// group_invites.ts
function startsReinviteWait(reason: InviteEnd, opts: { deletion?: boolean } = {}): boolean {
  if (reason === 'cancelled' || reason === 'declined') return true;
  return reason === 'withdrawn' && opts.deletion !== true;
}
// characters.ts:173: endInvite(ctx, invite, 'withdrawn', undefined, undefined, { deletion: true });
```
- Leave `settleGroupAfterLeave`'s `empty` branch as it is: it will then start the wait for the original inviter of every invite it withdraws.
- Change the test to expect a wait row for A→C after M's leave.
- Add the two-character loop as a regression test: one invite line for C over ten rounds.

### WR-02: The WR-05 notice skips a lone member who is himself the inviter, so a party that shrank around its leader still vanishes silently

**File:** `spacetimedb/src/helpers/group_invites.ts:125-131` (`loneId !== invite.fromCharacterId`), `:276-284` (`stays` with a live invite); client `src/rails/PartyBlock.vue:52` (`inParty = group !== null`)
**Issue:** The fix uses "the lone member is the inviter" as a stand-in for "this is a solo inviter's own auto-group". It cannot tell that case apart from a real party that shrank:
1. A and B are in a party, and B leads. B invites C.
2. A leaves. B's live invite keeps the group (`stays`). B gets only the group line "A left the group.", with no disband.
3. C declines, or the invite expires. `finishInvite` dissolves B's group. `loneId === invite.fromCharacterId`, so `lone` is null. B gets only "Cole declined your group invite." (or "Your invite to Cole expired.").

On the client, `inParty` is `group !== null`. B's party block, which still showed his party with the Invited row, flips to "Not in a party." without "The group has disbanded.". WR-05 described this same symptom. Had B sent no invite, step 2 would have told him "A left the group. The group has disbanded.", so the notice now depends on who sent the last invite.

The same happens when B invites D after A leaves while A's invite to C is still live: whichever invite ends last decides the notice, and if it is B's, the dissolve is silent.
**Fix:** Drop the inviter exclusion and suffix the lone member's own reason line whenever the end dissolves his group:
```ts
const lone =
  announceDisband && dissolved && loneId !== undefined
    ? ctx.db.character.id.find(loneId) ?? null
    : null;
```
- `say(from, …)` then reads "Cole declined your group invite. The group has disbanded.".
- A solo inviter also sees the suffix. That fits, because his auto-group was announced to him with "Ann formed a group.", and the party block he watched does disband.
- Update the "a solo inviter's own lone group still dissolves without the extra line" test.
- Add the A-leaves-then-C-declines case for leader B.
