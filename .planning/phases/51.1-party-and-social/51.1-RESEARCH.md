## Summary

The reducers for a party and for friends already exist, so most of this phase is **hardening the server plus a new client hub and screen**. Five server gaps matter. (1) `join_group` joins anyone with no invite check. (2) `group_invite` rows never expire, and `invite_to_group` creates a one-member group *before* it checks the pending-invite and full-group rules, so a failed invite leaves a stale group. (3) The `user` table (emails), `friend` and `friend_request` are public tables, and no client code reads them (the client reads nothing from `user`; the only server users are `login_email` and `send_friend_request`). (4) Nothing stores presence: "online" today means "some `player` row has this id as `activeCharacterId`", and `helpers/online.ts` computes it by scanning `player`. (5) `login_email` trusts a client-supplied email (CR-01), so any identity can become any user.

The recommended storage is small and additive: a defaulted public column `character.online` (written only by one helper at the places `player.activeCharacterId` changes), a private singleton `online_count` row read by an anonymous view, a private one-shot scheduled table `group_invite_expiry_tick`, new defaulted columns on `friend_request` and `friend` that record which character a request was made for, and two shaped per-sender friend views. `user`, `friend` and `friend_request` flip from public to private, which SpacetimeDB auto-migration allows without `--clear-database` (it is in the "potentially breaking" class, so the existing `--break-clients` local publish command is the right one). I recommend fixing CR-01 in this phase with a tiny change that needs no bindings change: derive the email from `ctx.senderAuth.jwt.fullPayload` (the same `email ?? preferred_username` the client parses), keep the argument, reject a mismatch, and let admin identities (the CLI identity the live proof scripts use) keep supplying it.

On the client, build a session-owned social hub (`src/social/socialData.ts`, beside the map and ledger hubs), a pure `follow.ts`, `playerMenu.ts` and `partyActions.ts`, the Social screen and menus, and extend `PartyBlock.vue` and `NearbyList.vue`. Two findings change the UI-SPEC's assumptions and need an owner nod (Open Questions 1 and 4): the server does **not** currently skip offline followers when the leader travels, and the Social `NoticeLine` mirrors only `system`, `reward` and `heal` private lines while group and friend refusals are written with kinds `group` and `friend`.

**Primary recommendation:** Do the server first as one wave and one local publish (key length 108 before and after, no clear): the stored `character.online` flag with a single writer helper, private `user`/`friend`/`friend_request`, the CR-01 fix, invite expiry/cancel/`join_group` rules, friend views and the online count. Then regenerate bindings and build the client hub, pure modules, menus, pet rows and the Social screen on top of rows the client already subscribes (`character`, `group_member`, `active_pet`).

### Pattern 1: Single writer for online status
**What:** One helper changes `character.online` and the counter together, only on a real flip, and is called from every place `player.activeCharacterId` changes. Writers found: `reducers/characters.ts` (`set_active_character`, `clear_active_character` fallback, `delete_character`), `reducers/creation.ts:318`, `helpers/character.ts` `campCharacter`, `reducers/auth.ts` `disconnect_logout`, `index.ts` `sweep_inactivity` orphan branch. [VERIFIED: grep of `activeCharacterId`]
**When to use:** always; never write `online` by hand.
**Example:**
```typescript
// Source: pattern from helpers/visited.ts and helpers/online.ts (this repo)
export function setCharacterOnline(ctx: any, characterId: bigint, online: boolean): void {
  const row = ctx.db.character.id.find(characterId); // re-read: never reuse a stale snapshot
  if (!row || (row.online ?? false) === online) return;
  ctx.db.character.id.update({ ...row, online });
  adjustOnlineCount(ctx, online ? 1n : -1n); // singleton row, clamped at 0
}
```
Call it as the **last** character-row write of a reducer, because many reducers do `character.id.update({ ...character, ... })` with a snapshot read earlier, which would overwrite a flag set before it.

### Pattern 2: One-shot guarded scheduled expiry
**What:** `invite_to_group` inserts the invite and one `group_invite_expiry_tick { scheduledId, scheduledAt = createdAt + TTL, inviteId }`. The reducer starts with the module-identity guard, deletes the invite if it still exists and is expired, and dissolves a one-member group that has no other pending invite.
**Example:**
```typescript
// Source: pattern from reducers/auth.ts disconnect_logout and index.ts sweep_passages
scheduledReducers['expire_group_invite'] = spacetimedb.reducer(
  'expire_group_invite',
  { arg: GroupInviteExpiryTick.rowType },
  (ctx, { arg }) => {
    if (ctx.sender.toHexString() !== ctx.databaseIdentity.toHexString()) return; // first statement
    const invite = ctx.db.group_invite.id.find(arg.inviteId);
    if (!invite || !isInviteExpired(invite, ctx.timestamp.microsSinceUnixEpoch)) return;
    endInvite(ctx, invite); // delete, then dissolve a lone group with no other invite
  },
);
```
Add the reducer to the `SCHEDULED` list in `scheduled_guard.integration.test.ts` (forged-call and control cases). A tick whose invite is already gone (accepted, declined, cancelled) is a harmless no-op, so cancel does not need to delete the tick.

### Pattern 3: Shaped per-sender view with a primary key
**What:** `t.row('Name', {...})` with a declared `primaryKey()` so online flips arrive as updates, not delete plus insert. Index lookups only (`player.id.find`, `friend.by_user`, `character.by_owner_user`, `location.id.find`). The row name must differ from the view's generated struct. [VERIFIED: `views/combat.ts` MyCombatAggroEntry; CITED: spacetimedb.com/docs/functions/views/ for the primary-key update behaviour and the no-`iter()` rule]
**Example:**
```typescript
// Source: views/combat.ts pattern
const MyFriendEntry = t.row('MyFriendEntry', {
  friendUserId: t.u64().primaryKey(),
  characterId: t.u64(),
  name: t.string(),

spacetimedb.view({ name: 'my_friend_list', public: true }, t.array(MyFriendEntry), (ctx: any) => myFriendRows(ctx));
```

### Pattern 4: Pure modules shared by menus, rail and Social
`follow.ts` (`followState`, `followSummary`, `staminaWarning`), `playerMenu.ts` (`playerMenuEntries`), and `partyActions.ts` each take rows and return plain data, with no Vue and no connection, so one test file covers the rule for every surface (the 999.22 requirement).

### Anti-Patterns to Avoid
- **Writing `online` outside the helper**, or in the middle of a reducer that updates the character afterwards from an older snapshot.
- **Scanning in a view** (`.iter()`): views are index-lookup only, and the project test pattern throws on any scan.
- **Nesting the `⋯` button inside the ally-target `button`** in `PartyBlock.vue`: the card becomes a wrapper with the target area and the `⋯` as siblings.
- **Subscribing the whole `user`, `friend` or `friend_request` table** or any unfiltered public table; every keyed table carries a WHERE on an indexed column.
- **Client-side invent of rules:** the 5-person cap, the 5-minute TTL and the stamina cost come from `@game-data` (`data/group_config.ts`, `data/travel_config.ts`).

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Invite expiry | A client timer that hides rows, or a polling loop | Scheduled one-shot table plus lazy checks | Server is the source of truth; refusals after expiry must come from the server |

## Findings by Key Question

**Q1. Group, party, friend, invite and chat tables, reducers, views, and what is public.** See "Current State". Summary: everything except the new presence data is already public; the gaps are rules (join check, expiry, cancel, solo-inviter order) not tables.

**Q2. How online status is stored and swapped into `onlineCharacterIds`.**
- Today "online" is `player.activeCharacterId`, set by `set_active_character` and finalize, cleared by camp, `clear_active_character`, the 15-minute inactivity sweep, `delete_character`, and `disconnect_logout` (30 s after disconnect; a reconnect inside 30 s keeps the session because `lastSeenAt` is newer). Character switch replaces the id, so the old character is offline at once. Camp also removes the character from the party; disconnect does not (so a party keeps offline members). [VERIFIED: `characters.ts`, `helpers/character.ts`, `auth.ts`, `index.ts`]
- Recommended: `online: t.bool().default(false)` as the last column of `character` (public), plus the singleton `online_count`. Turn the flag on where `player.activeCharacterId` is set and off where it is cleared. Do **not** flip it in `clientDisconnected`: the 30 s grace already exists for page refreshes and matches the "went offline" presence line.
- `onlineCharacterIds(ctx)` becomes "ids of characters with `online`" (a `character.iter()` filter is fine in a reducer; the sweep runs every 5 minutes). Update the three fixtures that seed `player.activeCharacterId` (`passages.test.ts`, `passage_sweep.integration.test.ts`, `combat_fight_fixture.ts`).
- **Backfill.** After publish every existing character reads `online = false` while two local players are active (user 1 char 1, user 4097 char 4097). `init` does not re-run on republish, so use the repo's pattern (`ensurePassageSweepScheduled`): an `ensureOnlineInitialized(ctx)` called from `clientConnected` that, when the `online_count` singleton is missing, sets the flag for every character that is some player's `activeCharacterId`, clears it elsewhere, and inserts the counter. Add an admin-only `reconcile_online` reducer for drift. [ASSUMED: this backfill shape, see A4]

**Q3. Making `user` private without breaking a client read, and whether it needs `--clear-database`.**
- The client never reads `user`: no `tables.user`, no `db.user`, no SQL string names it. The only `user` import in `src/` is the generated `UserRow` in `module_bindings/index.ts`. Server users: `login_email` and `send_friend_request` only (reducers can read private tables). The live proof scripts subscribe `player` and `character`, not `user`. [VERIFIED: grep over `src`, `scripts`, `spacetimedb/src`]
- **No clear is needed.** SpacetimeDB documents "Changing tables from public to private" as an allowed automatic migration in the "potentially breaking" class (clients subscribed to the newly private table get runtime errors; none do). Adding columns needs a default and must come last. [CITED: spacetimedb.com/docs/databases/automatic-migrations] Phase 46 and 50 shipped last-position defaulted columns with the same local publish command and an empty clear request. [VERIFIED: 46-01, 46.1-09, 50-26 SUMMARYs]
- Do the same flip for `friend` and `friend_request` (also unread by the client). Keep `group_invite` public: it holds ids only, the client needs it for the invite card and "Invited · waiting", and privatising it would remove the only way to know a target already has a pending invite.
- Private tables are not generated into `src/module_bindings`. After `spacetime generate`, `user_table.ts` (and the friend tables) disappear; the `Friend`, `FriendRequest` and `GroupInvite` **types** must still be exported (the old views return them). Run `npx vue-tsc -b` to prove it.

**Q4. Invite expiry through a scheduled table with the module-identity guard.** Pattern 2. Constants: `GROUP_INVITE_TTL_MICROS = 300_000_000n` and `MAX_GROUP_SIZE` move to `data/group_config.ts` (today `MAX_GROUP_SIZE` is a local `const` in `groups.ts`, and the UI-SPEC needs it through `@game-data`). ## Common Pitfalls

### Pitfall 1: Stale-snapshot overwrite of the online flag
**What goes wrong:** `set_active_character` and others read a character, do several writes, and finish with `character.id.update({ ...character, ... })`. A flag written earlier is overwritten with the old value.
**Why:** the codebase passes row snapshots through helpers.
**How to avoid:** `setCharacterOnline` re-reads by id and is the last write; add a source guard test that fails on any `online:` property written outside `helpers/online.ts` and the creation insert.
**Warning signs:** the count drifts from the number of `online = true` rows; a character shows offline while playing.

### Pitfall 2: Two sessions on one character
**What goes wrong:** the same user on two identities can have the same `activeCharacterId`; one logout turns the flag off while the other is playing.
**How to avoid:** the off path checks that no other `player` row still has that `activeCharacterId` (`character_logout` already does this scan) before flipping.

### Pitfall 3: Counter drift on delete or missed path
**What goes wrong:** deleting an online character, or a new code path that clears `activeCharacterId`, leaves the count high.
**How to avoid:** `delete_character` calls the helper before deleting; `reconcile_online` recounts; a test seeds drift and proves the reconcile.

### Pitfall 4: The Social notice line shows nothing for party and friend refusals
**What goes wrong:** `NoticeLine.vue` mirrors only private kinds `system`, `reward`, `heal` (`MIRRORED_KINDS`). Group refusals are written as kind `group` (`failGroup`, `appendPrivateEvent(..., 'group', ...)`) and friend lines as kind `friend`. The Social screen would stay silent.
**How to avoid:** give `NoticeLine` an optional `kinds` prop (default unchanged) and pass `system`, `group`, `friend` from Social. `accept/reject/remove_friend` take no `characterId`, so their `SenderError` becomes the generic "Couldn't send that. Try again." Add a short private `friend` line on success if feedback is wanted.

### Pitfall 5: Party chat shows another party's lines
**What goes wrong:** the feed store is per character, and `source === 'group'` entries carry no group id. After leaving one party and joining another, the old lines stay.
**How to avoid:** filter chat entries to `createdAtMicros >= own groupMember.joinedAt`; clear nothing in the store. Test a leave-and-rejoin.

### Pitfall 6: Offline followers move (and block) trips today
See Q7. Fix the server rule and mirror it in `travelChecks.ts` and `follow.ts`, with a parity test, or the summary line will promise something the server does not do.

### Pitfall 7: Offline party members join fights
`getGroupOrSoloParticipants` (`helpers/group.ts`) includes every member at the leader's place, online or not. Out of scope here; record it as a todo (an offline member can be pulled into a fight). Do not widen this phase.

### Pitfall 8: Existing tests treat missing `online` as offline
Fixtures that seed `character` rows without `online` read as offline once look, who, whisper, invite and Examine filter on it. Update `combat_fight_fixture.ts` and any seed that exercises those paths, and grep the tests first.

### Pitfall 9: `invite_to_group` order
Move the target checks (already in a group, pending invite, full group, offline) **before** the auto-create of the group, then create the group only when the invite will be inserted. Test: a failing invite leaves no group and no member row.

### Pitfall 10: Public event tables
`event_private` and `event_group` are public event tables whose filter is chosen by the client, so any client can subscribe to anyone's private feed or party chat. Event tables cannot be read through views, so there is no cheap additive fix. Out of scope; record a todo. (The decision for this phase is that nothing here makes it worse.)

### Pitfall 11: Generated bindings
Regenerate with `spacetime generate` after the publish; never hand-edit. `user_table.ts`, `friend_table.ts`, `friend_request_table.ts` vanish; the row types must remain exported through the views. Verify with `npx vue-tsc -b`.

## Open Questions

1. **Should the server skip offline followers when the leader travels?**
   - What we know: today it moves them and counts their stamina; the approved UI-SPEC and its summary line assume it does not.
   - What's unclear: whether the owner wants the behaviour change.
   - Recommendation: yes. Add the `online` test in `performTravel`, `travelChecks.ts` and `followState`, with one parity test. It is small and it prevents an offline member from blocking the leader.

2. **Should a party of one dissolve when its last pending invite ends?**
   - What we know: `invite_to_group` auto-creates the leader's group; decline, cancel and expiry leave it.
   - Recommendation: dissolve on invite end only (not on leave or kick). Otherwise the solo "You're travelling alone" state never returns after a failed invite.

3. **How should friend names resolve for offline friends and multi-character users?**
   - What we know: `friend` rows are user-level; a user can have several characters.

4. **Where do Social refusals show?**

5. **Is the CR-01 fix in scope?**

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2 Authentication | yes (CR-01) | Derive the user from the verified JWT claim in `login_email`; admin identities only for the proof tooling |

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Impersonation by `login_email` with someone else's email | Spoofing, Elevation | Claim-derived email, mismatch rejected (Q10) |
| Passive email harvest through a public table | Information Disclosure | `user` private |
| Email-existence oracle through `send_friend_request` | Information Disclosure | Reducer neutralised |
| Social graph read from public `friend` rows | Information Disclosure | `friend`, `friend_request` private, per-sender views |
| Forged call to the expiry reducer | Tampering, Denial of Service | Module-identity guard as the first statement; guard test |
| Joining a party without an invite | Elevation | `join_group` invite rule, lazy expiry |
| Invite spam or a blocked target | Denial of Service | Expired invites do not block; one pending invite per target; leader only |
| XSS through character, pet, chat or place text | Tampering | Text nodes only; escape test |
| Subscribing anyone's `event_private` or `event_group` | Information Disclosure | Pre-existing; out of scope, record a todo (Pitfall 10) |
| A friend's location leaking to non-friends | Information Disclosure | The view returns place only for the sender's friends; `character.locationId` is public regardless, so this adds no exposure |

## Project Constraints (from CLAUDE.md)

Extracted from `C:\projects\uwr\CLAUDE.md` and the owner's memory; they carry the authority of locked decisions.
- SpacetimeDB: reducers are transactional and deterministic; read data through tables, views and subscriptions, never reducer returns; `ctx.sender` is the principal, never trust identity arguments (this is exactly CR-01).
- TypeScript module rules: `table(OPTIONS, COLUMNS)` with `indexes` in the first argument (each with `accessor` and `algorithm: 'btree'`); `insert` needs a `0n` placeholder for auto-inc and returns the row; use `.find()` on unique and `.filter(value)` on indexes; **views use index lookups only, never `.iter()`**; scheduled tables use `scheduledId`/`scheduledAt` and the function form `scheduled: () => reducer`; reducers take object arguments on the client (`conn.reducers.x({ ... })`); `useTable` returns `[rows, isLoading]` (the project hubs use `bindTable`); memoize the connection builder; do not edit generated bindings.
- Do not invent SpacetimeDB APIs. Everything used here exists in the 2.10.1 type definitions or this repo (`ctx.senderAuth.jwt.fullPayload` verified in `node_modules/spacetimedb/dist/lib/reducers.d.ts`; `anonymousView` is in the CLAUDE.md rules and the schema recorder).
- Smallest change necessary; do not touch unrelated files.
- Owner memory: prefer `fail(ctx, character, message)` over `SenderError` where a character exists (the friend accept, reject and remove reducers have none); server is the source of truth (constants from `spacetimedb/src/data` through `@game-data`); local publish only, never maincloud, never `--clear-database` unless schema changes require it (they do not here); every change unit-tested; Keeper and NPC pronouns and voice rules are unaffected (no prompt text changes); never "ripple".
- Publish: `spacetime publish uwr -p spacetimedb --server local --break-clients < /dev/null`; check `admin_llm_status` `key_length` 108 before and after; regenerate bindings after.
