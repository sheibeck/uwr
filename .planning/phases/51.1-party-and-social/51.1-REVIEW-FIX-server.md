## Fixed Issues

### CR-01: login_email trusts the email claim of a token from any issuer

**Files modified:** `spacetimedb/src/data/auth_config.ts` (new), `spacetimedb/src/helpers/login_identity.ts`, `spacetimedb/src/reducers/auth.ts`, `spacetimedb/src/helpers/login_identity.test.ts`, `spacetimedb/src/reducers/auth_login.test.ts`
**Commit:** 2d3ea13f
**Applied fix:**
- `readTokenEmail(senderAuth)` returns the email, or the reason there is none (`no_token`, `issuer`, `audience`, `no_email`).
- The token's `iss` must equal the pinned issuer (a trailing slash is ignored). Its `aud`, a string or a list, must name a pinned client id.
- `login_email` logs the reason to the server log on a refusal (`spacetime logs uwr`). It never logs an email.
- The user-facing refusal is unchanged: 'Sign-in token carries no email.'.
- Tests cover: a foreign issuer, a missing or near-miss issuer, a wrong or missing audience, an audience list, a trailing slash, and the attack (a foreign token carrying the victim's email) through the real handler.
- **Status: fixed, requires human verification.** The owner must sign in once on the local build (see the checkpoint in the hand-off).

### WR-01: The email claim fell back to preferred_username and ignored email_verified

**Files modified:** `spacetimedb/src/helpers/login_identity.ts`, `spacetimedb/src/helpers/login_identity.test.ts`, `spacetimedb/src/reducers/auth_login.test.ts`
**Commit:** 84bab513
**Applied fix:**
- Only the `email` claim counts. `preferred_username` is never used: no claim in the token shows that the provider verified it.
- An email with `email_verified` present and not `true` (or the string `'true'`) is refused (`unverified`).
- A token without `email_verified` is still accepted. The owner's earlier sign-in proved the email claim is there, but not whether `email_verified` is.
- **Status: fixed, requires human verification** (the same sign-in check as CR-01). If the owner's token carries only `preferred_username`, sign-in is refused with 'Sign-in token carries no email.', and the server log says `(no_email)`.

### WR-02: Invite spam and a scheduled tick row per invite

**Files modified:** `spacetimedb/src/data/group_config.ts`, `spacetimedb/src/schema/tables.ts`, `spacetimedb/src/helpers/group_invites.ts`, `spacetimedb/src/reducers/groups.ts`, `spacetimedb/src/reducers/groups.integration.test.ts`
**Commit:** 4f3c98b7 (the group_config unit tests landed in 7e080a83)
**Applied fix:**
- The re-invite wait (see the rules table) is stored in a new private table, `group_invite_cooldown` { id, fromCharacterId, toCharacterId, untilMicros }, with a `by_to_character` btree. The schema change is additive and has no view. There is one row per inviter and target pair. Finished waits are pruned when that target is next invited, and `delete_character` drops the character's rows.
- The check runs after the pending-invite check, before the cap and before any group is created, so a refused re-invite creates nothing.
- New `cancelInviteExpiry` deletes an invite's expiry tick whenever the invite ends early: accept, decline, cancel, a lazy expiry, or a withdraw. The tick that is running (`expire_group_invite`) is left for the platform to delete.
- It finds the tick by scanning the private tick table, which holds one row per open invite. No index was added, so no index migration is needed.
- Tests:
  - decline and cancel, each followed by a re-invite at wait - 1 µs (refused, nothing created) and at the end of the wait (allowed, the old row pruned);
  - the wait is per inviter;
  - expiry starts no wait;
  - no tick is left after accept, decline, cancel or a lazy expiry;
  - the running tick is untouched;
  - a ten-round decline loop sends the target one invite line and leaves no tick.

### WR-05: Invites deleted silently; stray lone groups (with the client review's WR-02)

**Files modified:** `spacetimedb/src/helpers/group_invites.ts`, `spacetimedb/src/reducers/groups.ts`, `spacetimedb/src/helpers/character.ts`, `spacetimedb/src/reducers/characters.ts`, `spacetimedb/src/reducers/groups.integration.test.ts`
**Commit:** a4fb4027
**Applied fix:**
- New invite end reason `withdrawn`. The target is told 'The invite from {name} is no longer open.' and the inviter 'Your invite to {name} is no longer open.' (private, kind 'group'). It starts no re-invite wait.
- New `settleGroupAfterLeave(ctx, groupId, leavingCharacterId, departureLine)` runs after every leave, kick, camp and delete:
  - Nobody is left: each invite ends as withdrawn, then the group row is deleted.
  - One member is left: the group's expired invites end first, with their expiry lines. With no live invite left, the group dissolves through `dissolveLoneGroup`, and the member, now solo, is told '{departure line} The group has disbanded.'. Without that line the member would get no notice, because the group line goes with the group. A live invite keeps the group, and that member leads it.
  - Otherwise `handOnLeadership` runs.
- `delete_character` first ends every invite to or from the character as withdrawn, while the names still resolve, and drops its re-invite waits. It then settles its group once. This covers the reviewer's case: a solo inviter is told and his lone group dissolves.
- `kick_group_member` dropped its own puller and remaining-member code in favour of the shared helper.
- **Mid-fight (IN-05 question):** a dissolve during a fight is safe. No combat rule reads the group row, and a member leaving mid-fight was already allowed. See IN-05.
- Tests:
  - each of leave (member), leave (leader), kick, camp and delete leaves the last member solo with the disbanded line and no 'is now the group leader' line;
  - each path keeps the group when a live invite is out;
  - an expired invite does not keep the group;
  - a dissolve with an active group fight leaves the fight alone;
  - the last member leaving or camping withdraws every invite with lines;
  - deleting an invited character tells the solo inviter and dissolves his group;
  - deleting an inviter tells the target and dissolves the remaining one-member group once.
