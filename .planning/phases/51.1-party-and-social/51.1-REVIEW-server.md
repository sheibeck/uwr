## Summary

The scope was the Phase 51.1 server diff (`fde53f6e~1..HEAD -- spacetimedb/src`). It covers:
- the stored online flag and its single writer (`helpers/online.ts`);
- the private `user` table;
- offline members being left behind in travel and in fight pulls;
- the online gates on who, look, look at and whisper;
- the invite rules: consent, lazy expiry, the guarded expiry tick, cancel, the lone-group dissolve and the size cap;
- the leave successor;
- the CR-01 login fix.

I traced these call chains:
- `performTravel` through `moveOne`;
- every `startCombatForSpawn` caller (combat, gathering, quests and the intent route);
- `campCharacter`, `delete_character`, `disconnect_logout`, `clientConnected` and `sweep_inactivity`;
- the `my_group_invites` and `my_group_events` views;
- the `AuthCtx`/`JwtClaims` types in `node_modules/spacetimedb/dist/lib/reducers.d.ts`.

The targeted suites pass (5 files, 92 tests).

These parts are sound:
- **Online writer.** Every place that changes `player.activeCharacterId` either syncs after its last character-row write or deletes the row. These are `set_active_character`, `campCharacter` (clear and AFK), creation finalize, `disconnect_logout` and `delete_character`. `reconcileOnline` collects the rows before it writes and runs after the guarded sweep's camp loop. It is idempotent.
- **Expiry tick guard.** `expire_group_invite` checks the module identity in its first statement. It is a no-op for a missing or still-live invite, and it is pinned in `scheduled_guard.integration.test.ts`.
- **Consent.** `join_group` and `accept_group_invite` both need an invite addressed to the caller's own character. An expired match is ended and refused. `joinFromInvite` re-reads the character before it writes.
- **Cancel authority.** Only the group's leader, or the inviter while still in the group, can cancel, and only a live invite to that target.
- **Size cap.** Members plus live invites must stay below `MAX_GROUP_SIZE`, and the check runs before the solo inviter's group is created.
- **Private `user`.** Only `login_email` reads it. No view exposes it, and the email oracle in `send_friend_request` is closed.
- **Determinism.** The diff adds no `Date`, `Math.random`, timers or crypto. Every time comes from `ctx.timestamp`.

Two blockers:
1. **The CR-01 fix is incomplete.** The token's email is trusted without checking who issued it. SpacetimeDB accepts JWTs from any OIDC issuer, so an attacker can still mint a token that carries a victim's email.
2. **Three fight-start paths ignore the owner's "offline members are never pulled into a fight" rule:** the gathering ambush, the quest-item aggro and `pull_named_enemy`.

The warnings:
- the leader is moved twice on group travel;
- nothing limits invite spam;
- the successor rules are inconsistent and ignore online status;
- several paths delete invites silently and leave stray lone groups.

## Critical Issues

### CR-01: login_email trusts the email claim of a token from any issuer, so account takeover is still possible

**File:** `spacetimedb/src/helpers/login_identity.ts:37-52`, `spacetimedb/src/reducers/auth.ts:35-40`
**Issue:** `verifiedEmailFromAuth` reads `senderAuth.jwt.fullPayload.email` (or `preferred_username`). It never checks `jwt.issuer` or `jwt.audience`. SpacetimeDB validates a token's signature against the JWKS of whatever issuer the token names. It does not limit which OIDC issuers it accepts, and the module has to enforce that itself. `JwtClaims` exposes `issuer` and `audience` for exactly this (`reducers.d.ts:62-72`), but nothing in `spacetimedb/src` reads them (a grep for `issuer|audience` finds only comments).

Attack:
1. The attacker runs any OIDC provider they control (for example a self-hosted Keycloak or a dev tenant) and mints an id token with `email: "victim@example.com"`.
2. They connect to the database with that token. SpacetimeDB derives a fresh identity from (iss, sub).
3. They call `login_email({ email: "victim@example.com" })`. `resolveLoginEmail` sees the claim equal to the argument and returns `ok`. `login_email` then links the attacker's player row to the victim's `user` row (`auth.ts:48-62`), and `requireCharacterOwnedBy` gives the attacker every one of the victim's characters.

This is the same impact as the original CR-01; it only needs one extra step. The tests (`auth_login.test.ts`) build `senderAuth` without an issuer, so they cannot catch this.

**Fix:** Pin the issuer and the audience, and require a verified email:
```ts
// helpers/login_identity.ts
export const SPACETIMEAUTH_ISSUER = 'https://auth.spacetimedb.com/oidc'; // read the real `iss` from one live token
export const SPACETIMEAUTH_CLIENT_ID = '<the VITE_SPACETIMEAUTH_CLIENT_ID value>';

export function verifiedEmailFromAuth(senderAuth: unknown): string | null {
  ...
  const jwt = (senderAuth as any).jwt;
  if (!jwt || jwt.issuer !== SPACETIMEAUTH_ISSUER) return null;
  if (!Array.isArray(jwt.audience) || !jwt.audience.includes(SPACETIMEAUTH_CLIENT_ID)) return null;
  const claims = jwt.fullPayload as Record<string, unknown>;
  if (claims.email_verified !== true) return null;      // see WR-01
  return claimString(claims.email);
}
```
Add tests: a foreign issuer is refused, a wrong audience is refused, and `email_verified: false` is refused. Keep the `TOKEN_EMAIL_CHECK` rollback.

### CR-02: Gathering ambushes, quest-item aggro and pull_named_enemy still pull offline members into fights

**File:** `spacetimedb/src/reducers/items_gathering.ts:82`, `spacetimedb/src/reducers/quests.ts:444-449`, `spacetimedb/src/reducers/quests.ts:518-523`, `spacetimedb/src/helpers/character.ts:21-35`
**Issue:** The owner's decision (51.1-CONTEXT, "Owner decisions after research") says offline members are skipped when a fight starts. Only `getGroupOrSoloParticipants` (`helpers/group.ts:18`) applies it. The 51.1-02 summary calls `getGroupParticipants` "not a fight pull", but it is one:
- `start_gather_resource`'s aggro roll builds the fight from `getGroupParticipants(ctx, character, true)` and passes that list to `startCombatForSpawn`. That helper has no online check, so an offline member left behind at the same place is inserted as an `active` `combat_participant`.
- `pickUpQuestItem`'s 30 % aggro (reached from the typed `pick up` intent and the quest reducer) and `pull_named_enemy` build the list from every `group_member` row. They check neither online status nor location. An offline member anywhere in the world joins the fight.

Combat outlives a disconnect, and an offline character cannot act, so the member can die while away. This is the case the owner ruled out. None of the 51.1 tests cover these three paths.

**Fix:** Route all three through the same participant rule:
```ts
// items_gathering.ts:82
const participants = getGroupOrSoloParticipants(ctx, character);
// quests.ts:444 and :518
const participants = aggro.getGroupOrSoloParticipants(ctx, character); // pass it in the deps
```
Or add `if (memberChar.online !== true && memberChar.id !== character.id) continue;` to `getGroupParticipants` and use it in quests.ts. Add tests for each path with an offline member at the same place.

## Warnings

### WR-01: The email claim falls back to preferred_username and ignores email_verified

**File:** `spacetimedb/src/helpers/login_identity.ts:47`
**Issue:** `claims.email ?? claims.preferred_username` accepts `preferred_username` as an email whenever `email` is missing. In most OIDC providers `preferred_username` is chosen by the user and never verified. `email_verified` is never read either. Even with the issuer pinned (CR-01), a SpacetimeAuth account that can set a username such as `victim@example.com`, or that has an unverified email, can link to someone else's `user` row. Copying the client's `parseJwtEmail` order is fine for display, but it is not a basis for authentication.
**Fix:** Accept only `email` with `email_verified === true`. If some sign-in methods carry only `preferred_username`, confirm with the provider that it is verified before trusting it, and record that in the comment.

### WR-02: Invites can be spammed without limit (cancel or decline, then re-invite), and every invite leaves a scheduled tick row

**File:** `spacetimedb/src/reducers/groups.ts:291-398`, `spacetimedb/src/helpers/group_invites.ts:121-127`
**Issue:** The only throttles are one live invite per target and the group cap. A leader can run `invite_to_group` → `cancel_group_invite` → `invite_to_group` in a loop, or re-invite right after each decline. Each cycle writes "{name} invited you…" and "{name} cancelled the invite." to the target. The target can be any online character on the server, found by name, with no location requirement. The target has no block or mute.

Each `invite_to_group` also inserts a `group_invite_expiry_tick` row. Cancel, decline and accept do not delete it ("no tick cleanup on early ends"), so a scripted loop leaves an unbounded number of scheduled rows, each living for 5 minutes. This was the "invite spam" focus area, and the size cap does not address it.
**Fix:**
- Throttle per inviter and target: keep the last invite time (for example a `lastInviteAtMicros` on `group_invite`, or a small private table keyed by from and to) and refuse with `failGroup(ctx, inviter, 'Wait a moment before inviting {name} again.')` inside a cooldown such as 30 s.
- When an invite ends early, delete its tick. This needs a btree index on `group_invite_expiry_tick.inviteId`.

### WR-03: On group travel the leader is pushed twice, so moveOne runs twice for him

**File:** `spacetimedb/src/helpers/travel.ts:91-107`, `:215-217`
**Issue:** The leader is pushed explicitly (`travelingCharacters.push(character)`). The loop then reaches the leader's own `group_member` row: `followLeader` is true (both `create_group` and `invite_to_group` insert it that way), he is online, he is at the origin and not at the destination, so `comesAlongWithLeader` passes and he is pushed again.

The 51.1-02 summary says "the result is identical". That holds for the stamina deduction (both writes come from one snapshot), but not for `moveOne`, which runs twice for the leader. He gets two "You travel to X." lines and two auto-look blocks. The origin and the destination each get two "departs" / "arrives" lines. Passive search and the world-event auto-register run twice. This rewrite was the moment to fix it.
**Fix:**
```ts
for (const member of ctx.db.group_member.by_group.filter(group.id)) {
  if (member.characterId === character.id) continue; // the leader is already in the list
  ...
}
```
Add a test that asserts exactly one "You travel to" line for the leader on a group move.

### WR-04: The successor rule ignores online status and differs between leave, camp and delete

**File:** `spacetimedb/src/helpers/group_invites.ts:107-118`, `spacetimedb/src/helpers/character.ts:181-192`, `spacetimedb/src/reducers/characters.ts:184-207`
**Issue:**
- `nextLeaderAfter` picks the earliest `joinedAt`, even when that member is offline and others are online. An offline leader cannot travel (and under the new rule nobody follows him), invite, kick or promote, so the online members are stuck. They can only leave.
- `disconnect_logout` never hands leadership on, and `sweep_inactivity` skips player rows whose `activeCharacterId` is already cleared. So a leader who disconnects stays leader indefinitely.
- `campCharacter` (camp and the AFK sweep) and `delete_character` still choose `remaining[0]` / the first `by_group` row. That is a different successor from the one `leave_group` uses and the client's Leave prompt names.
**Fix:**
- Use `nextLeaderAfter` in `campCharacter` and `delete_character`.
- Have it prefer online members: sort by `online === true` first, then `joinedAt`, then id. Keep the client prompt in step.
- Consider handing leadership on in `disconnect_logout` when an online member exists, or record this as an owner decision.

### WR-05: Several paths delete invites silently, leaving stray lone groups and invitees who are never told

**File:** `spacetimedb/src/reducers/characters.ts:211-215`, `spacetimedb/src/helpers/character.ts:176-179`, `spacetimedb/src/reducers/groups.ts:139-144`, `spacetimedb/src/reducers/groups.ts:282-287`
**Issue:** The phase rule is that when an invite ends, a one-member group with no other invite dissolves (`endInvite` → `dissolveLoneGroup`). The other invite deleters bypass `endInvite`:
- `delete_character` deletes every invite to or from the character with a bare `group_invite.id.delete`. Suppose A, solo, invites B, which creates A's auto-group, and B then deletes the character. The invite disappears, A gets no message, and A's one-member group stays forever. That is exactly the stray group the rule was meant to prevent.
- `campCharacter`, `leave_group` (no members left) and `kick_group_member` (remaining 0) also delete invites silently. The invitee's card vanishes with no line.
**Fix:**
- In `delete_character`, end each invite with `endInvite(ctx, invite, 'cancelled', character)`. Do this before the character row is deleted, so the names still resolve.
- In the other three paths, use a reason with copy for the target, for example "The invite from {name} is no longer open.".

## Info

### IN-01: Declining an expired invite reports "declined" instead of ending it as expired

**File:** `spacetimedb/src/reducers/groups.ts:432-439`
**Issue:** `reject_group_invite` uses `pickInvite`, which returns an expired invite when no live one exists. It then calls `endInvite(..., 'declined')`. `join_group`, `accept_group_invite` and `cancel_group_invite` all end an expired match as `'expired'`.
**Fix:** `if (!inviteIsLive(invite, now)) return endInvite(ctx, invite, 'expired');` before the decline.

### IN-02: lastOnlineAtMicros publishes every character's exact login and logout times

**File:** `spacetimedb/src/schema/tables.ts:351-353`
**Issue:** `character` is public, so every client can read the exact moment of each character's last online or offline flip, not only the `online` flag the design calls for. That is presence tracking of strangers to the microsecond.
**Fix:** If no client needs the stamp, keep it in a private table, or expose only a coarse "last seen" through a per-sender friend view (52.2).

### IN-03: The single-writer source guard cannot see shorthand writes

**File:** `spacetimedb/src/helpers/online.test.ts:163-173`
**Issue:** The regex `/\b(online|lastOnlineAtMicros)\s*:/` matches only `key:` forms. A stray `ctx.db.character.id.update({ ...row, online })` passes the guard. That shorthand is the very form the 51.1-01 summary tells callers to use.
**Fix:** Also flag `\bonline\b\s*[,}]` inside `character.id.update(` / `character.insert(` calls. Alternatively, scan for `character\.(id\.update|insert)\([^)]*\bonline\b` across files.

### IN-04: Refusals in invite_to_group bypass fail(), and a comparator is duplicated

**File:** `spacetimedb/src/reducers/groups.ts:313-355`, `spacetimedb/src/reducers/groups.ts:34`, `spacetimedb/src/helpers/group_invites.ts:11`
**Issue:**
- Four player refusals still call `appendPrivateEvent` directly instead of `failGroup`: leader only, already in a group, pending invite, and full. The kind is the same, so this is only a convention drift (memory rule: prefer `fail()`).
- The new SenderErrors in `login_email` and `send_friend_request` are justified, because those reducers have no character context.
- `pickInvite` re-implements `byId` from `group_invites.ts`.
**Fix:** Use `failGroup` for the four refusals (the bytes stay the same), and export and reuse `byId`.

### IN-05: The lone-group dissolve can run while the leader is in a group fight

**File:** `spacetimedb/src/helpers/group_invites.ts:86-101`
**Issue:** Scenario: a solo inviter gets an auto-group, pulls, and the invite expires mid-fight. The guarded tick then deletes the group and clears `groupId`. `combat_encounter.groupId` still points at the deleted group, so the `logGroupEvent` reward lines (`combat.ts:2136-2204`) go to a group that `my_group_events` no longer returns. They duplicate private lines, so the loss is cosmetic.
**Fix:** Skip the dissolve while `activeCombatIdForCharacter(ctx, lone.characterId)` is set; the next invite end or the fight's end can retry. Alternatively, accept this and document it.

### IN-06: Invites can be sent from an owned character that is not active (offline)

**File:** `spacetimedb/src/reducers/groups.ts:297`
**Issue:** `requireCharacterOwnedBy` checks only ownership. A user can invite, accept or cancel with an alt that is offline and invisible to `look` and `who`. The target-online gate does not apply to the inviter. The same pattern exists in other reducers.
**Fix:** In the party reducers, require `character.online === true` (or that it is the caller's active character), refusing with `failGroup`.

### IN-07: The admin bypass in login_email works as a master key to every account

**File:** `spacetimedb/src/helpers/login_identity.ts:67`, `spacetimedb/src/data/admin.ts:5-11`
**Issue:** Any identity in `ADMIN_IDENTITIES` can link to any email. That includes the CLI owner identity, whose token sits on the dev machine. This is intended for the proof scripts, but it makes that token as sensitive as every player's account.
**Fix:** Restrict the bypass to the proof accounts' email domain or an explicit allow-list of emails, or log each admin link with `console.warn` so it is auditable.
