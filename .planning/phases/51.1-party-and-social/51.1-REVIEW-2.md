## Critical Issues

### CR-01: The desktop player menu closes whenever any feed line arrives, because the scroll listener catches the feed's own auto-scroll

**File:** `src/social/PlayerMenu.vue:151-157`, `:174-177`; `src/console/FeedView.vue:115-126`, `:145-156`
**Issue:**
- **The listener.** `openMenu` adds `window.addEventListener('scroll', onScrollOrResize, true)`. A capture listener on `window` receives the `scroll` event of every scrolling element in the document, not only the rail that holds the opener. `onScrollOrResize` ignores only scrolls inside the menu itself.
- **The feed.** `FeedView` keeps the feed pinned to the bottom. On every new entry (`watch(lastKey)`) it calls `scrollToBottom`, which sets `scrollTop` or calls `scrollTo` on the feed scroller, and that fires a `scroll` event. The pinned state is the default.
- **The result.** On desktop the menu closes as soon as any line lands in the feed: another player's chat or arrival, a world event, the server's own result line for the action just taken, or the `reportRejections` line. In combat, lines arrive every round.

The two-step entries are hit hardest. `Leave party` and `Remove from party` open an inline confirm, so a line arriving between the first click and `Leave` / `Remove` closes the menu and drops the confirm. The ally ⋯ in combat is close to unusable. The WR-04 test only dispatches a scroll on a rail element, so it cannot catch this.
**Fix:** Close only when the scrolled element actually moves the opener, meaning the document or an ancestor of the opener:
```ts
function onScrollOrResize(event: Event): void {
  const target = event.target;
  if (event.type === 'scroll') {
    const moved =
      target === document || target === window ||
      (target instanceof Node && opener.value !== null && target.contains(opener.value));
    if (!moved) return; // the feed or another unrelated scroller
  }
  const inside = focusInside();
  closeMenu(false);
  if (inside) opener.value?.focus({ preventScroll: true });
}
```
Add a component test that opens the menu, dispatches `scroll` on an unrelated sibling scroller (the feed), and expects the menu to stay open. Keep the existing rail-scroll test.

## Warnings

### WR-01: The re-invite wait is bypassed by leaving the lone group: invite → leave → invite repeats with no wait

**File:** `spacetimedb/src/helpers/group_invites.ts:196-205` (`settleGroupAfterLeave`, nobody left), `:86-88` (`endInvite` starts the wait only for `cancelled` / `declined`); `spacetimedb/src/reducers/groups.ts:131-149`, `:282-285`
**Issue:**
1. A solo inviter A calls `invite_to_group(C)`. This creates A's auto-group and sends C "A invited you to a group…".
2. A calls `leave_group`. Nobody is left, so `settleGroupAfterLeave` ends every invite as `withdrawn`, and C gets "The invite from A is no longer open.". `withdrawn` starts no wait.
3. A calls `invite_to_group(C)` again straight away. `liveInvitesTo(C)` is empty, `reinviteWaitActive(A, C)` finds no row, and the invite goes out.

The loop costs two reducer calls per cycle and sends the target two lines per cycle with no throttle. That is the spam pattern WR-02 meant to close. Camping out and back in, or `kick` + re-invite in a two-member group, gives the same result more slowly. No test covers a withdrawn end followed by a re-invite.
**Fix:**
- Start the wait for a `withdrawn` end too, when the inviter caused it (the inviter leaving or camping out of his own group). The simplest version: call `startReinviteWait` for every reason except `expired` and an accept.
- Alternatively, have `settleGroupAfterLeave` pass the leaving character and start the wait when `invite.fromCharacterId === leavingCharacterId`.
- Add a test: invite, leave, re-invite at T + 1 is refused with the wait line.

### WR-02: In a 2-member party the leader's Leave prompt says "Leadership passes to {name}", but the server now dissolves the group

**File:** `src/social/playerMenu.ts:113-133` (`selfEntries`), `src/social/playerMenu.ts:228-249` (`nextLeaderName`); server `spacetimedb/src/helpers/group_invites.ts:206-214`
**Issue:**
- Since WR-05, when one member is left after a leave and the group has no live invite, `settleGroupAfterLeave` dissolves the group. It does not hand on leadership. The remaining member gets "{Ann} left the group. The group has disbanded." and never "is now the group leader".
- The client prompt still appends ` Leadership passes to ${nextLeaderName}.` whenever the leader leaves and `nextLeaderName` is non-null, and for two members it always is.
- The "successorOrder parity" fix (8fd4f94b) matched the sort order but not the outcome. Every client test uses a 3-member party (`memberCount: 3`, Bram and Cy), so this case is not covered.

**Fix:**
- Mirror the server's branch. When `memberCount === 2` and the group has no live outgoing invite (`input.liveOutgoing.length === 0`, which the leader can see), say ` The party disbands.`. Otherwise name the successor.
- Better: export a pure `leaveOutcome({ remaining, liveInvites })` from `@game-data/group_config`, and use it in both `settleGroupAfterLeave` and `selfEntries`, so the two cannot drift.
- Add a 2-member test with and without a live invite.

### WR-03: A mid-fight dissolve sends the survivor's dismiss_combat_results down the solo path, which deletes every participant's loot for that fight

**File:** `spacetimedb/src/helpers/group_invites.ts:183-187` (the "Dissolving during a fight is safe" claim), `spacetimedb/src/reducers/combat.ts:1262-1297`
**Issue:**
- `dismiss_combat_results` branches on `effectiveGroupId(character)`. In a group it deletes only the caller's own loot. Solo, it deletes `combat_loot.by_combat.filter(combatId)` for every combat in the caller's results, and that includes the other participants' loot rows.
- Before WR-05, a member who left mid-fight was already solo. The member who stayed was not: he kept a one-member group and took the group branch.
- Now the leave dissolves the group in the same transaction, so both former members are solo when the fight ends. Leaving the group does not remove anyone from `combat_participant`. Either dismiss now wipes the other player's unclaimed loot.

No client code calls the reducer today (a grep for `dismissCombatResults` finds no callers), which keeps this at WARNING. It is a data-loss path reachable by any SDK call, and the fix report's "safe" claim is wrong.
**Fix:** Make the solo branch delete only the caller's own loot, as the group branch does:
```ts
for (const combatId of combatIds) {
  for (const loot of ctx.db.combat_loot.by_character.filter(character.id)) {
    if (loot.combatId === combatId) ctx.db.combat_loot.id.delete(loot.id);
  }
}
```
Alternatively, skip the lone-group dissolve while `activeCombatIdForCharacter(ctx, lone.characterId)` is set. Also correct the comment on `settleGroupAfterLeave` and `dissolveLoneGroup`.

### WR-04: email_verified is enforced only when the claim is present, so a token without the claim passes

**File:** `spacetimedb/src/helpers/login_identity.ts:84-86`
**Issue:** `if ('email_verified' in claims && !emailVerified(...))` accepts any email when the provider omits `email_verified`. The issuer and audience pins limit this to tokens SpacetimeAuth issues for our own client. The open question is whether every sign-in method enabled on that client verifies the address before putting it in `email`. If any method (for example a password sign-up before confirmation, or a social provider that passes through an unverified address) issues a token with `email` and without `email_verified`, the CR-01 account takeover is open again for that method. The fix report leaves this open ("A token without `email_verified` is still accepted") pending the owner's sign-in.
**Fix:**
- As part of the owner's sign-in checkpoint, record whether SpacetimeAuth's id token carries `email_verified`.
- If it does, require it (`if (!emailVerified(claims.email_verified)) return { email: null, refusal: 'unverified' }`) and add a test for the absent claim.
- If it does not, record in `auth_config.ts` which sign-in methods the client allows and confirm with the provider that each one verifies the address.

Until then, treat this as a blocker for any maincloud publish.

### WR-05: A group kept alive by a live invite later dissolves without telling its remaining member

**File:** `spacetimedb/src/helpers/group_invites.ts:94-108` (`endInvite`), `:116-131` (`dissolveLoneGroup`), `:206-216` (`settleGroupAfterLeave` keeps the group for a live invite)
**Issue:**
1. Leader A invites C, then A leaves a two-member group. A live invite is out, so the group stays and B leads it alone.
2. C later declines, or the invite expires. `endInvite` writes only to `from` (A, who is no longer in the group) and to C. It then calls `dissolveLoneGroup`, which deletes B's membership and the group without a line.
3. B's party block and self ⋯ just vanish. There is no "The group has disbanded." of the kind `settleGroupAfterLeave` writes for the same outcome.

The same silent dissolve happens on a cancel by B, though there B at least gets "You cancelled the invite…".
**Fix:** In `endInvite`, check whether `dissolveLoneGroup` returned true and whether the lone member is not the inviter. If so, tell him `"{reason line} The group has disbanded."` (for example "Cole declined the invite. The group has disbanded."). Alternatively, return the lone character from `dissolveLoneGroup` and write the line there. Add a test for leave-with-live-invite → decline.

### IN-04: fightRoster is "the one fight rule" but does not refuse members already in another fight
