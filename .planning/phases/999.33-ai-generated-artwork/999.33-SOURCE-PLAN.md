# Unwritten Realms — AI-Generated Artwork Implementation Plan

## Purpose

Add AI-generated artwork to Unwritten Realms in a way that enriches the existing narrative-first MMORPG experience without blocking gameplay, changing the core text-driven identity, or requiring images to exist before content can be played.

The system should gradually fill in artwork over time for:

- Locations
- Enemy definitions / creature types
- Named NPCs

Later extensions may include:

- Bosses
- Items
- Factions
- Quest/event scenes
- Player/character portraits
- Location state variants
- Day/night/weather variants

The core rule is:

> If artwork exists, show it.  
> If artwork does not exist, gameplay continues normally and generation is queued asynchronously.

Artwork is optional presentation data, not authoritative gameplay state.

---

# Existing Project Context

Repository:

`https://github.com/sheibeck/uwr`

Current architecture:

- Vue 3
- TypeScript
- Vite
- SpacetimeDB backend
- Existing LLM integration through SpacetimeDB procedures
- Narrative-first gameplay UI
- Left player/party sidebar
- Large center narrative log
- Right contextual panel with:
  - current location
  - exits / nearby places
  - nearby creatures
  - resources
- Bottom hotbar + text command input

Important SpacetimeDB rule:

- Reducers must remain deterministic.
- Reducers must not make outbound network/API calls.
- Image generation should therefore happen through:
  - a SpacetimeDB procedure, or
  - a separate external worker later if needed.

For MVP, prefer a SpacetimeDB procedure because UWR already uses procedures as its outbound AI boundary.

# Core Product Direction

Generated artwork should feel like:

> an illustration in a living game book

and not like:

> a graphical MMO viewport bolted onto a text game.

The narrative remains primary.

Artwork should support atmosphere, recognition, and discovery.

# Visual Integration Decisions

## Locations

Location artwork should appear **inside the narrative flow**, not as a permanent hero image.

Good moments to display location art:

- entering a location
- first discovery
- `look`
- major world-state change

Do not show it for:

- ordinary combat messages
- gathering
- movement chatter
- ambient one-line events
- every repeated `look`
- chat

Recommended narrative structure:

```text
> look

The Drowned Bell

[ LOCATION ART ]

A great bronze bell stands upright in the cracked lakebed...

It is currently daytime...

Safety...
Creatures...
Resources...
Exits...
```

The image belongs directly under the location title and before the descriptive prose.

---

## Missing Location Art

If artwork does not exist:

```text
The Drowned Bell

A great bronze bell stands upright...
```

Do not show:

- broken image icon
- giant blank box
- spinner
- "image pending"
- warning

The current text-only UI already works well.

Missing artwork should simply preserve the text-only experience.

---

## Repeated Location Art

Do not stack the same giant image repeatedly in narrative history.

Recommended rule:

- show location art on first `look` after entering
- show again after leaving and returning
- optionally show again after a significant location state change

Repeated `look` commands while remaining in the same place should usually omit the image.

Alternative implementation:

- suppress duplicate image if the same asset appeared within the last 10–20 narrative entries

The first approach is probably cleaner.

# Recommended Image Sizes

## Location Art

Generate/store master at:

```text
1536 × 1024
3:2 aspect ratio
```

Generate a normal gameplay derivative at:

```text
1024 × 683 WebP
```

Why 3:2 instead of 16:9:

- better vertical room for landmarks
- still works naturally in the center narrative column
- looks like an illustration rather than a cinematic banner
- supports scenes such as The Drowned Bell where the main landmark is tall

Recommended display behavior:

```css
width: 100%;
height: auto;
max-height: 420px;
object-fit: cover;
```

Use a responsive 3:2 wrapper to avoid layout shift.

---

## NPC Art

Recommended:

```text
4:5 portrait
```

Suggested master:

```text
1024 × 1280
```

Gameplay derivative can be smaller.

NPC art should appear beside dialogue/interactions rather than as a wide narrative image.

---

## Enemy Art

Recommended:

```text
4:5 portrait
```

or possibly:

```text
1:1
```

depending on final card treatment.

Enemy art is especially well suited to the right sidebar because nearby creatures are already listed there.

Recommended interaction:

- click creature name/card
- selected creature expands
- portrait appears
- description appears
- encounter expectations remain visible
- existing actions such as Pull remain available

Do not replace the center narrative panel just because an enemy is examined.

# Data Architecture

Artwork should be stored separately from gameplay entities.

Do not add image binary data directly to:

- location rows
- enemy rows
- NPC rows

Use a generic artwork table.

Suggested model:

```ts
ArtAsset {
  id

  entityType
  entityId

  artType
  variant

  status

  masterUrl
  displayUrl
  storageKey

  width
  height
  aspectRatio

  prompt
  promptVersion

  provider
  model

  attemptCount
  lastAttemptAt
  generatedAt

  errorMessage

  createdAt
  updatedAt
}
```

Suggested values:

```text
entityType:
  location
  enemy
  npc

artType:
  landscape
  creature
  portrait

variant:
  default

status:
  missing
  queued
  generating
  ready
  failed
  deferred
```

Use enums/constants in application code instead of scattering string literals.

---

# Stable Entity Keys

Artwork belongs to stable entity definitions.

Examples:

```text
location:drowned_bell
enemy:brine_sentinel
npc:orrin_sill
```

Do not generate art for transient spawned enemy instances.

Twenty Brine Sentinels should all reuse the same creature image unless the game intentionally introduces visual variants later.

---

# Generation Job Queue

Use a separate job table.

Suggested model:

```ts
ArtGenerationJob {
  id

  entityType
  entityId
  artType
  variant

  status
  priority

  attempts
  promptVersion

  createdAt
  startedAt
  completedAt
  retryAfter

  lastError
}
```

Suggested statuses:

```text
queued
processing
complete
failed
deferred
```

---

# Idempotency

There must never be duplicate active jobs for the same artwork.

Logical uniqueness:

```text
entityType + entityId + artType + variant
```

Examples:

```text
location:drowned_bell:landscape:default
enemy:brine_sentinel:creature:default
```

Queue behavior:

```text
ready      -> do nothing
queued     -> do nothing
processing -> do nothing
missing    -> enqueue
failed     -> retry only if allowed
deferred   -> wait until retryAfter
```

---

# Generation Triggers

Eventually support all three.

## 1. Creation-Time Enqueue

When new content is created:

```text
new location
new enemy definition
new named NPC
```

create its ArtAsset and enqueue generation.

This becomes the normal long-term path.

---

## 2. Player Encounter Enqueue

If a player encounters an entity with no art:

```text
missing art
-> ensure one generation job exists
-> gameplay continues immediately
```

Examples:

- entering a new location
- examining an enemy
- interacting with a named NPC

This should not block gameplay.

---

## 3. Backfill

Run a gradual scan for existing entities without art.

Example:

```text
find locations with no art
enqueue up to N

find enemy definitions with no art
enqueue up to N

find named NPCs with no art
enqueue up to N
```

Recommended batch:

```text
20 per backfill pass
```

Do not repeatedly full-scan the entire database.

The goal is eventual completeness.

---

# Priority

Suggested priorities:

```text
100 current player encountered missing location
95  current player examined missing enemy/NPC
90  starting areas
85  high-traffic / discovered locations
70  undiscovered locations
60  common enemies
50  named NPCs
```

# Generation Execution

## MVP Recommendation

Use a SpacetimeDB procedure.

Conceptual flow:

```text
claim job
-> transaction marks processing
-> leave transaction
-> build prompt
-> call image provider
-> store image
-> create derivative
-> enter transaction
-> update ArtAsset
-> mark job complete
```

Do not keep a DB transaction open while waiting on external HTTP.

If handling binaries, storage SDKs, or image conversion becomes awkward inside SpacetimeDB procedures, move image-generation execution to a small Node/TypeScript worker later.

Do not add another service until it is actually useful.

---

# Object Storage

Do not store large image blobs directly in SpacetimeDB rows.

Use:

- Cloudflare R2
- S3
- Azure Blob Storage
- another S3-compatible service

Development may temporarily use local filesystem storage.

Example paths:

```text
art/locations/drowned-bell/v1/master.webp
art/locations/drowned-bell/v1/display.webp

art/enemies/brine-sentinel/v1/master.webp
art/enemies/brine-sentinel/v1/display.webp
```

Prefer immutable/versioned paths.

Do not overwrite the exact same URL every time an image is regenerated.

This avoids CDN/browser cache issues.

---

# Prompt Generation

Prompt construction must be centralized.

Create functions such as:

```text
buildLocationArtPrompt(...)
buildEnemyArtPrompt(...)
buildNpcArtPrompt(...)
```

Do not embed giant prompt strings in HTTP call code.

---

# UWR House Art Style

Every image should include a shared style block.

Suggested initial direction:

```text
Atmospheric high-fantasy LitRPG illustration.

Semi-realistic painterly fantasy artwork.
Grounded materials and believable environments.
Dramatic but natural lighting.
Rich environmental storytelling.
Serious fantasy world with occasional dark wit,
but not cartoonish artwork.

No text.
No logos.
No UI elements.
No decorative border.
No watermark.
No modern objects unless explicitly described.
```

Add two important narrative-safety rules:

```text
Do not visually answer mysteries that the source text leaves unexplained.

Do not reveal hidden information the player would not reasonably know.
```

These rules matter especially for Unwritten Realms.

Artwork should illustrate known fiction, not spoil secrets.

# Prompt Versioning

Every asset must record:

```text
promptVersion
```

Start with:

```text
1
```

Example global constant:

```text
UWR_ART_PROMPT_VERSION = 1
```

Later:

```text
assets where promptVersion < current
```

can be candidates for regeneration.

Do not automatically regenerate everything when prompt version changes.

---

# Store Final Prompt

Store the actual prompt used.

Also store where practical:

```text
provider
model
generation settings
```

This helps:

- debugging
- reproducing assets
- comparing good/bad outputs
- future admin tools
- tracking provider changes

---

# Quota / Cost Handling

The generator must treat rate limits and budget exhaustion as normal.

Configurable limits:

```text
ART_GENERATION_ENABLED
ART_MAX_DAILY_GENERATIONS
ART_MAX_ATTEMPTS
ART_PROVIDER
ART_MODEL
ART_PROMPT_VERSION
```

Potential later:

```text
ART_MAX_DAILY_COST
```

If the provider returns:

- 429
- quota exceeded
- budget reached
- temporary outage

then:

```text
status = deferred
retryAfter = future time
```

Do not continuously retry.

Do not break gameplay.

---

# Retry Policy

Suggested:

```text
attempt 1 -> retry
attempt 2 -> retry later
attempt 3 -> failed
```

Possible backoff:

```text
5 minutes
30 minutes
2 hours
next day
```

If a provider exposes an explicit quota reset time, use it.

---

# Atomic Job Claiming

Multiple workers/procedures must not process one job simultaneously.

Conceptual transition:

```text
queued
-> atomic transaction
-> processing
```

Only one process may succeed.

Later add stale-job recovery:

```text
processing for > 30 minutes
-> eligible for requeue
```

This can be Phase 2.

# Location Artwork Loading Behavior

Use:

```html
loading="lazy"
decoding="async"
```

Reserve size only after the UI knows a ready asset exists.

Example:

```css
.location-art-frame {
  aspect-ratio: 3 / 2;
  width: 100%;
  overflow: hidden;
}
```

If the asset itself is loading:

- show subtle skeleton/blank art frame

If no ready asset exists:

- render nothing

This prevents giant empty placeholders.

# Live Art Completion

SpacetimeDB subscriptions can update ArtAsset status live.

However:

Do not insert a newly generated giant image into an old narrative entry while the player is reading/fighting.

Recommended behavior:

- narrative entry snapshots whether art was available when rendered
- if art completes later, future eligible `look` / arrival renders may show it
- right-side examine cards may update more safely because they are current context

This avoids unexpected scroll jumps.

# Provider Abstraction

Avoid tightly coupling UWR to one image-generation service.

Use a small abstraction such as:

```ts
interface ImageGenerator {
  generate(request): Promise<ImageGenerationResult>
}
```

MVP may have only one implementation.

Future possibilities:

- OpenAI
- Imagen
- Stability
- Flux provider
- local model

The rest of the code should not care.

# Final Design Principle

The entire feature should follow this rule:

> AI-generated artwork enriches the world asynchronously but never becomes a dependency of gameplay.

And visually:

> Generated artwork should feel like an illustration in a living game book, not a graphical MMO viewport bolted onto a text game.

Locations belong in the narrative stream.

Enemies belong naturally in the right-side examine context.

NPC portraits belong beside interaction/dialogue.

The text remains the game; the art makes the world easier to see.
