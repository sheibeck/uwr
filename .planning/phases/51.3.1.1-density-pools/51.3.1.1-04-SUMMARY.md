# Phase 51.3.1.1 Plan 04: Enemy roles and enemy-side abilities Summary

Support and caster family members now work from the enemy side (D-53). Every role word maps to a real stat profile, including a new frail, hard-hitting caster profile. An enemy heal or shield lands on an ally enemy. An enemy drain or execute hits the player, and drain heals the caster. Enemy taunt and cc do nothing. An enemy damage shield absorbs player ability damage through one function, `absorbEnemyShield`.

## What was built

### Task 1: Caster profile and role normalization
- `ENEMY_ROLE_CONFIG.caster` is new.
- `getEnemyRole(role)` looks up `ENEMY_ROLE_CONFIG[normalizeEnemyRole(role)]` and falls back to damage:
  - melee, ranged and dps read the damage profile;
  - support reads the healer profile;
  - caster reads its own profile;
  - anything unknown reads damage.
- The legacy `support` and `dps` keys stay in the config. They are no longer looked up.
- Pinned ordering:
  - armour: tank > damage > caster (base and per level);
  - damage per level: caster > damage;
  - a level 5 caster has less HP and armour and more damage than the same template as damage.
- No boss bonus (D-52).

### Task 2: Enemy-side branches in `resolveAbility`
- **Signature:** `resolveAbility(ctx, combatId, actor, ability, targetCharacterId?, targetPetId?, targetEnemyId?)`. The new 7th parameter is the ally the round engine chose for an enemy heal or shield. Existing callers are unchanged.
- **heal (enemy actor):** the ally is `targetEnemyId` if it is alive, else the living enemy of this fight with the lowest HP fraction below full. The caster counts, and ties go to the lower id.
  - The heal uses the existing power path and is capped at maxHp.
  - No ally below full: nothing happens. No character row is ever touched.
  - Log to active participants: `{caster} mends {ally}.`, or `{caster} recovers.` when the caster heals itself (PROPOSED).
- **shield (enemy actor):** the ally is `targetEnemyId` if alive, else the caster. It gets `damage_shield` (value1, or the scaled power if value1 is 0) as a `combat_enemy_effect`. No `character_effect` is written. Log: `{ally} is shielded by {ability}.`
- **drain (enemy actor):** damages `targetCharacterId` through `applyEnemyAbilityDamage`, the same path the enemy damage branch uses. Then it heals the caster `combat_enemy` by `value2 ?? 30`% of the damage dealt, capped at maxHp. No other enemy changes. With no target, nothing happens.
- **execute (enemy actor):** damages the player target, doubled when the target's hp is at or below 30% of maxHp. No enemy changes.
- **taunt and cc (enemy actor):** a `console.log` line, then return before any write. This also stops `findEnemyTarget()`'s 'No target' throw for enemies.
- **`absorbEnemyShield(ctx, combatId, enemy, damage): bigint`:**
  - It reads the enemy's `damage_shield` rows for this fight in id order.
  - Each row absorbs what it can; a used-up row is deleted and a partly used row is updated.
  - It returns the damage left.
  - `applyDamageToEnemy` calls it before `nextHp`. A character actor gets `A ward on {enemy} absorbs N damage.` (PROPOSED).

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] The enemy shield row has no `ownerCharacterId`**
- **Found during:** Task 2
- **Issue:** The plan's call passed `actor.id` (an enemy id) as `addEnemyEffect`'s `ownerCharacterId`. That column holds a character id; the DoT tick heals `ownerCharacterId` as a character. Putting an enemy id there is the same wrong-key hazard as T-51.3.1.1-12.
- **Fix:** The argument is left out (undefined). The test asserts it.
- **Commit:** d28089e8

**2. [Rule 1 - Bug] `applyDamageToEnemy` returns the damage that reached HP**
- **Found during:** Task 2
- **Issue:** With a shield in place, returning the raw hit would make the "hits X for N" lines and a player drain's heal count damage the shield absorbed.
- **Fix:** The function returns the damage left after the shield. Threat still counts the whole hit. A character actor gets one absorb line, phrased like the player-side ward line.
- **Commit:** d28089e8

**3. [Cleanup] Dead enemy log lines removed**
- **Issue:** The `else if (actor.type === 'enemy' && targetCharacterId)` log tails in cc, drain and execute could no longer run once the explicit enemy branches return first.
- **Fix:** Removed them. The drain and execute player lines moved into the new branches with the same wording.
- **Commit:** d28089e8

**4. [Test pin in my own file] getEnemyRole test**
- **Issue:** The old test looped over every config key and expected each key to return its own entry. With normalization, `support` now resolves to healer.
- **Fix:** The test now loops over the four server roles. A second test pins that the legacy keys still exist.
- **Commit:** d6ff4444

### Notes, not changes
- **Character shield and enemy ability damage:** the plan described the enemy damage path as handling "armour, character shield consumption". In fact `applyEnemyAbilityDamage` applies armour and magic resist but does not consume a character's `damage_shield`; only auto-attacks in `reducers/combat.ts` do. Drain and execute reuse that path unchanged, as the plan asked, so enemy ability damage still ignores a player's shield, as it did before this plan.
- **Out-of-scope enemy kinds:** enemy-actor `fear` still stuns the first living enemy, which is the caster's own side. Enemy `hot` and a non-debuff `buff` still land on `targetCharacterId` when one is passed. No member ability uses these kinds (`memberAbilities` only gives damage, dot, shield, heal and drain), but AI-written enemy abilities could. These are left for Plan 05 or a todo.
