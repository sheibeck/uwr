# Phase 51.3.1.1 Plan 25: Economy apply per family and migration of economy rows Summary

The region economy is now written per creature family (D-47). Each family gets one drop and one trophy, each member gets one piece of gear, and each member's loot table draws from the family drop and trophy plus its own gear. Late economy work is one job per family; an invented quest kill target's family of one uses the same job. Existing 51.3 per-type rows move to families with no paid call (D-49). The AI job designs at most seven families per region; the rest are written by rule (coordinator addition for D-66).

## What was built

### Task 1: apply a family reply and the late family result (5eb898f0 RED, eb922276 GREEN)

- **`economy_rules.ts`**
  - `aiLootTable` leaves the gear entry out when `gearId === 0n`. Such a table has 3 to 5 entries: the same drop, trophy and gatherables as before.
  - `ECONOMY_DESIGN_FAMILIES_MAX = 7`, with a `DesignFamilyCandidate { id, feud, places }` type.
  - `pickDesignFamilies(candidates, max = 7)` picks feud families first, then families at more places, then id order. It returns the chosen ids in id order, with no duplicates.
- **`region_economy.ts`**
  - **`economyDesignFamilies(tx, regionId)`** returns `{ designed, ruleFamilyIds }`.
    - Places = the distinct places of the family's creature pools (`place_pool.by_region`). Feud = a `family_relation` row whose kind is `FAMILY_FEUD_KIND`.
    - Region mode lists only `designed`. `startRegionEconomy` stores `ruleFamilyIds` (decimal strings) in the request, and `readEconomyJobContext` reads them back into `EconomyJobContext.ruleFamilyIds`; a job stored without them reads `[]`.
  - **No more 51.3 enemies.** `buildRegionEconomyInput` region mode lists no `enemies`.
  - **`writeFamily(book, entry, memberIds, familyLevel, gatherableIds)`**
    - Writes the family drop (`drop:family:<id>`) and trophy (`trophy:family:<id>`), both with `familyId` set and `enemyTemplateId` 0n.
    - Writes gear per covered member (`gear:<templateId>`, with `enemyTemplateId` and `familyId`).
    - Every member without `enemy_loot_entry` rows gets an `aiLootTable` (its gear, or gearId 0n).
    - The members are the input family's members plus any member row that joined since the input was built.
    - A family of one read from a 51.3 input (familyId 0n) keeps the per-template keys (`drop:<templateId>`).
  - **`applyRegionEconomyResult` branches on the reply shape.**
    - `region.creatures` (and no `families`) goes down the 51.3 path (`writeCreature`, `gather:<rarity>`).
    - Anything else goes through `validateFamilyEconomyReply`:
      - gatherables are keyed `gather:G<n>`;
      - each family goes through `writeFamily`, and `D:E<n>` resolves to family n's drop;
      - then the rule families (`writeRuleFamily`), then the recipes;
      - a left-out recipe slot is filled by rule.
    - The recipe loop moved into a shared `writeRecipes`.
  - **`writeRuleFamily`** builds the rule fallback through `validateLateFamily` with an entry that names nothing. That gives fallback names ("<Region> Hide", "<Region> Trophy", "<Region> Blade", numbered on a clash) and the repaired default gear (a sword). It then calls `writeFamily`.
  - **`applyLateFamilyResult`** handles family-mode jobs. It writes only when:
    - the region is complete;
    - the family row exists;
    - a member lacks loot.
    A second apply changes nothing.
  - **51.3 enemy-mode jobs** still go to `applyLateCreatureResult`. That function also accepts a `lateFamily`-shaped answer: since Plan 24 the route schema produces that shape even for a stored 51.3 job.
  - **`repairRegionEconomyOutputs`** also reads a family design: handles by `gather:G<n>`, family drops by their family slotKey.

### Task 2: one late job per family; quest families use it (a6356801 RED, 9fe0a562 GREEN)

- **`startFamilyLoot(tx, family, regionId, who)`** checks its gates in this order:
  1. `aiEnabled`, else 'off';
  2. a family row, else 'no_region';
  3. the region economy complete, else 'not_ready';
  4. a member lacking loot, else 'exists';
  5. the region row.

  It enqueues route `region_economy` with budget `phase_only` and sourceKey `SOURCE_KEYS.familyLoot(id)` = `family:<id>`. The request is `{ regionId, mode: 'family', familyId, characterId, input }`. An active job for the same family is reused ('duplicate'). The kill switch and the ceiling apply inside `enqueueLlmJob`.
- **`startLateFamilies`** replaces `startLateEnemies`. After a region apply with the switch on, every family of the region (id order) with a member lacking loot gets ONE job.
- **`llm_apply.ts`.** For an invented `kill` / `kill_loot` target, the old `startEnemyLoot` call is gone; the code calls `startFamilyLoot(ctx, family, family.regionId, ...)` on the row `familyOfOne` returns. `boss_kill` gets no family and no job.
- **Deleted:** `startEnemyLoot`, `startLateEnemies` and `regionEnemyTemplates`, together with its filler exclusion. Nothing calls them any more. `SOURCE_KEYS.enemyLoot` is kept as a documented key that nothing enqueues now.
- `enemyEntry` and the `'enemy'` mode of `buildRegionEconomyInput` remain, for stored jobs and the 51.3 tests.

### Task 3: migrate 51.3 economy rows to families (127d8cc9 RED, d66f78e9 GREEN)

- **`migrateEconomyToFamilies(ctx, regionId)`** returns `{ tagged, tables }`. For each family of the region:
  - it tags every member's `economy_item` rows (`by_enemy`) with `familyId`;
  - it takes the family's drop and trophy from the lowest template id member that has both;
  - every member without loot gets an `aiLootTable` with that drop and trophy, its own 51.3 gear row if any (else gearId 0n) and the region gatherables (common, uncommon, rare, then id).
- A family with no rows is left alone. A member's existing table is kept. No job is enqueued.
- It runs as step 7 at the end of `migrateRegion`.
- `POOL_MIGRATION_VERSION = 2n`. A version-1 world (the live local world after Plan 17) re-runs the whole region pass once. The test shows that rerun is idempotent for pools, families and members, adds the filler loot tables, and then the version reads 2n.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] `data/economy_phase_contract.test.ts` named `startEnemyLoot`**
- **Found during:** Task 2
- **Issue:** The spend-safety source test checks that every enqueuing function reads `aiEnabled` first, and it listed `startEnemyLoot`, which the plan deletes.
- **Fix:** The list now names `startFamilyLoot`. The same check applies: `aiEnabled` is read before `enqueueLlmJob`.
- **Files modified:** `spacetimedb/src/data/economy_phase_contract.test.ts`. This is a server test outside files_modified, and no running plan (18, 26, 28, 29, 30) lists it.
- **Commit:** 9fe0a562

**2. [Rule 3 - Blocking] The 12-line window in the same contract test**
- **Issue:** The test looks for `budget: 'phase_only'` within 12 lines of the route literal. The extra `ruleFamilyIds` request line pushed it out of that window.
- **Fix:** The `budget` key now comes before `request` in both enqueues.
- **Commit:** eb922276

**3. [Rule 2 - Missing critical] A 51.3 enemy-mode job answered in the family shape**
- **Issue:** Since Plan 24 the route schema only produces `lateFamily`, so a stored enemy job run after publish would never apply.
- **Fix:** `applyLateCreatureResult` falls back to `validateLateFamily`, reading the stored enemy as a family of one, and writes the same per-template rows. The family-shape region reply does the same for a 51.3 stored region input.
- **Commit:** eb922276

**4. [Rule 2 - Missing critical] Rule fill for left-out recipes; gear for members that already have loot**
- **Recipes:** A recipe slot the reply left out is filled by rule, as the Plan 24 hand-off asked.
- **Gear:** `writeFamily` writes no gear for a member that already has a loot table, because nothing would drop it.
- **Commit:** eb922276

**5. [Coordinator addition] The design cap.**
- **What:** `ECONOMY_DESIGN_FAMILIES_MAX` lives in `data/economy_rules.ts`, which is in files_modified.
- **Rule families:** The families past the cap are carried in the request (`ruleFamilyIds`), so that a family joining while the job is pending still gets a late AI job, not the rule.
- **"Rule fallback":** I took this to mean rule-named rows written at the apply: drop, trophy, one gear per member, and the loot tables. With rows in place those families start no late job, so the cap also bounds the paid follow-ups.

**6. Repair.** `repairRegionEconomyOutputs` also reads a family design (a small additive branch). Its test is in region_economy.test.ts.

No other deviation. No production file outside files_modified was touched.
