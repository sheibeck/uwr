# Phase 51.3.1.1 Plan 11: Pull a Family, Encounter Rolls Summary

Every pool encounter now goes through one seeded module, `helpers/encounters.ts`. The new `pull_family` reducer draws a family group sized by density, with roles by rule and the trim set by the lowest party member. Picking up a quest item can now draw an ambush from the place's pools. The careful pull and the `start_combat` spawn fallback are retired.

## What was built

- **`helpers/encounters.ts`** (deterministic, with no run-time import of `reducers/combat.ts`):
  - `creaturePoolsHere(ctx, locationId, now)` returns `PoolHere[]` (`{ pool, family, level, lvLo, lvHi, members: { templateId, role, level }[] }`). Each pool is settled through `poolsAt`. Each member is listed at its place level.
  - `rosterLevel(characters)` returns the lowest level (D-56).
  - `rollEncounter(ctx, { locationId, isSafe, partyLevel, phase, leaderId, now, factorPct? })` returns `EncounterHit | null`. The seed is `encounterSeed(now, leader, place, phase)`. It then runs `encounterChanceBp`, `encounterHit` and `pickEncounterPool`.
  - `drawGroup(ctx, { pool, family, partyLevel, seed })` returns `DrawnEnemy[]`:
    - the size comes from `groupSizeFor` (gap = family top level here minus party level);
    - the roles come from `composeGroupRoles`;
    - each slot's member is picked with `rollBelow(seed, MEMBER_BASE + slot, n)`;
    - every enemy has `spawnId 0n` and `poolId = pool.id`.
  - `drawForPull(ctx, pool, family, partyLevel, leaderId, now)` is drawGroup with the 'pull' seed.
  - `startPoolFight(deps, ctx, { leader, candidates, groupId, pool, family, drawn, originKind, line })` writes the line to the `fightRoster` (kind 'combat' or 'ambush'), then calls `deps.startCombat(ctx, leader, candidates, groupId, drawn, { kind, familyId, level, name, plural })`. It returns null for an empty draw.
- **`reducers/pools.ts`** `registerPoolReducers(deps)` adds `pull_family({ characterId, poolId })`, registered in `reducers/index.ts`. The checks run in this order:
  1. `requireCharacterOwnedBy`;
  2. refuse if the character is fighting or gathering;
  3. refuse a missing, foreign or resource pool;
  4. refuse at a safe place;
  5. settle the pool; refuse at level 0 with `pullRefusal`;
  6. take the roster through fightRoster and its lowest level;
  7. call `drawForPull`, then `startPoolFight` with origin 'pull' and the `pullLeadIn` line.
- **`pickUpQuestItem`**:
  - The `(id ^ timestamp) % 100n` roll and the spawn search are gone.
  - The ambush now uses `rollEncounter` (phase 'aggro', `QUEST_ITEM_AMBUSH_FACTOR_PCT`), then `drawGroup`, then `startPoolFight` with origin 'ambush_other' and `ambushLine({ phase: 'other', ... })`.
  - A safe place, a wiped-out place, a fighting character, or a call without `aggro.startCombat` never ambushes.
  - The aggro bag type is `{ ensurePoolsForLocation; effectiveGroupId; startCombat?; startCombatForSpawn? }`. `loot_quest_item` passes `startCombat`.
- **`reducers/combat.ts`**:
  - `start_combat` serves individual spawns only. A missing, busy or distant spawn gets `fail()` 'That enemy is not here to fight.', and no `ensureAvailableSpawn` runs.
  - `start_pull` validates, then calls `startCombatForSpawn` at once. It writes no `pull_state` or `pull_tick` and applies no WIS or `pull_veil` math.
  - `resolve_pull` runs the guard, deletes its `pull_state` row and releases a 'pulling' spawn.
  - `schedulePullResolve` was removed (dead code).
  - The `PULL_*` constants and the `WIS_PULL_BONUS_PER_POINT` import stay, with a comment pointing to 999.4.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] resolve_pull releases a stranded 'pulling' spawn**
- **Found during:** Task 3
- **Issue:** An old pending pull leaves its spawn in state 'pulling'. Draining only the row would strand that enemy forever.
- **Fix:** If the spawn is still 'pulling', resolve_pull sets it back to 'available'. This is tested.
- **Commit:** e3f3c191

**2. [Rule 1 - Bug] start_pull and the quest-item ambush never start a second fight**
- **Found during:** Tasks 2 and 3
- **Issue:** The old start_pull allowed a pull during combat, because resolve_pull added the enemy to the running fight. An immediate `startCombatForSpawn` would instead give the leader a second fight. The quest-item ambush had the same risk.
- **Fix:** start_pull refuses with 'Already in combat' (existing copy). The quest-item ambush skips a fighting character. Both are tested.
- **Commits:** f7764982, e3f3c191

**3. [Rule 3 - Blocking] Tests outside files_modified (neither Plan 09 nor Plan 14 lists them)**
- `reducers/fight_start_online.integration.test.ts` (part of this plan's own verify command):
  - Its world's only creature (Cave Rat) is Old Greymaw's named template, so it never forms a family and the quest-item ambush could never fire.
  - I added an ordinary Reed Wolf (template 2) linked at the place.
  - The two quest-item cases now scan for a hitting timestamp (`questAggroTs()`) instead of relying on the old modulo.
- `reducers/combat_actors.integration.test.ts`: the "partial pull stores adds" case became the drain case.

**4. Bindings not regenerated (rules.md overrides the plan)**
- rules.md allows binding regeneration only in a publish plan. Plan 17 (publish B) regenerates, and its artifact list already names pull_family.
- The plan's acceptance check `ls src/module_bindings | grep -ci pull_family` therefore prints 0 until Plan 17.
- `npx vue-tsc -b` exits 0.

**5. deps.startCombat call shape**
- The plan wrote `deps.startCombat(deps, ctx, ...)`.
- `index.ts` binds it as `deps.startCombat(ctx, leader, candidates, groupId, drawn, origin)`, so startPoolFight uses the bound form.

## Known gap (for Plan 13 or 16)

`reducers/intent.ts` is outside this plan's files. Its "loot <item>" call to `pickUpQuestItem` (about L645) still passes `{ ensurePoolsForLocation, effectiveGroupId, startCombatForSpawn }`, so the intent path picks the item up but draws no ambush. That is no regression: since Plan 08 there are no ordinary spawns, so it never fired anyway.

The fix is one line, `startCombat: deps.startCombat`. `quest_item_pickup.test.ts` pins the gap in "KNOWN GAP: on a hit the intent path ... draws no ambush yet": flip its expectation to 1 combat when the line is added.
