## Warnings

### WR-01: The client copies the server's place target-level formula instead of importing it (breaks "server is the source of truth")

**File:** `src/rails/levelRange.ts:25-33` (`placeTargetLevel`), also `src/rails/levelRange.ts:41-42` (`routeLevel` band)
**Issue:**
- The C-WR-03 fix added `placeTargetLevel`, a hand-written copy of the server's `computeLocationTargetLevel(ctx, id, 1n)` in `spacetimedb/src/helpers/location.ts:14-23`. The copy computes floor(dangerMultiplier / 100) + levelOffset, clamped to at least 1, and reads an unknown region as 100. The fix report names the deviation and calls this "the single client copy". It is still a copy of a server rule.
- The project rule says the client imports rules through `@game-data` and never duplicates constants or formulas.
- `routeLevel` also re-derives the place band in its own words: `lo = max(1, level - 1), hi = level + 1` when the offset is not 0. That duplicates `placeLevelBand` in `spacetimedb/src/data/enemy_rules.ts:78-84`, which the same fix already imports (`placeSpawnLevel`) a few files away.
- No parity test ties `placeTargetLevel` to `computeLocationTargetLevel`. A change to the server's scaling, for example a non-1 `baseLevel` or a different clamp, would silently put the named card level, the exit labels and the Map out of step with the look text and the fight level. That breaks UI-SPEC P2 again.

**Fix:** Move the pure formula into a data module and import it on both sides:
```ts
// spacetimedb/src/data/enemy_rules.ts
/** A place's target level (D-..): base scaled by the region's danger multiplier, plus the place's offset, never below 1. */
export function placeTargetLevelFor(dangerMultiplier: bigint | undefined, levelOffset: bigint | undefined, baseLevel = 1n): bigint {
  const scaled = (baseLevel * (dangerMultiplier ?? 100n)) / 100n;
  const level = scaled + (levelOffset ?? 0n);
  return level > 1n ? level : 1n;
}

// spacetimedb/src/helpers/location.ts
export function computeLocationTargetLevel(ctx: any, locationId: bigint, baseLevel: bigint) {
  const location = ctx.db.location.id.find(locationId);
  if (!location) return baseLevel;
  const region = ctx.db.region.id.find(location.regionId);
  return placeTargetLevelFor(region?.dangerMultiplier, location.levelOffset, baseLevel);
}

// src/rails/levelRange.ts
import { placeLevelBand, placeTargetLevelFor } from '@game-data/enemy_rules';
export function placeTargetLevel(place, regions) {
  return placeTargetLevelFor(regions.find((r) => r.id === place.regionId)?.dangerMultiplier, place.levelOffset);
}
export function routeLevel(dest, regions): RouteLevel {
  if (dest.isSafe) return { safe: true };
  const band = placeLevelBand(placeTargetLevel(dest, regions), dest.levelOffset);
  return { safe: false, lo: Number(band.min), hi: Number(band.max) };
}
```
Keep the `levelRange.test.ts` cases. They then test the shared rule.

### WR-02: `boss_kill` still resolves and links its target at the player's place when the reply lands (the B-WR-02 defect, left in the sibling branch)

**File:** `spacetimedb/src/helpers/llm_apply.ts:984` (`searchLocIds = [character.locationId]`), `:1027` (`location_enemy_template.insert({ locationId: character.locationId })`) and the fallback loop after it
**Issue:**
- B-WR-02 moved kill and kill_loot resolution to `npc.locationId`, because the player can move, even to another region, between `talk_to_npc` and the apply.
- The `boss_kill` branch of the same `offer_quest` loop was edited by the B-CR-01 fix commit (`4bcb8264`), yet it still does all of the following from `character.locationId` at apply time:
  - searches the player's current place and its neighbours;
  - links an invented boss template there;
  - falls back to "the first enemy at the location".
- So a boss quest from an NPC in region 1 can bind to a template, or create and link a new one, at whatever place the player reached in region 2, possibly a hub. The quest goal then disagrees with what the NPC said. This is the same incorrect behaviour B-WR-02 reported, and the fix now handles it two different ways in one loop.

**Fix:** Use the same `questPlaceId` for `boss_kill`. Hoist it above the questType branches and skip the quest when the giver's place is gone:
```ts
const questPlaceId: bigint = npc.locationId;
if (!ctx.db.location.id.find(questPlaceId)) { console.log(`offer_quest "${questName}": the quest giver's place is gone; quest skipped`); continue; }
// boss_kill:
const searchLocIds: bigint[] = [questPlaceId];
for (const conn of ctx.db.location_connection.by_from.filter(questPlaceId)) searchLocIds.push(conn.toLocationId);
// ... ctx.db.location_enemy_template.insert({ id: 0n, locationId: questPlaceId, enemyTemplateId: newEt.id });
// fallback: ctx.db.location_enemy_template.by_location.filter(questPlaceId)
```
Add a test to the `movedAway` block in `llm_apply.test.ts`: a `boss_kill` reply after the player moved to region 2 links nothing at 200n.

### IN-01: `settlePoolKills` unlinks every kill before any pool is written, so one failing pool loses the depletion of the others

**File:** `spacetimedb/src/helpers/pools.ts:419`, with the swallowing catch at `spacetimedb/src/reducers/combat.ts:487-494`
**Issue:** The B-WR-03 fix zeroes `poolId` on all counted rows first, then calls `applyDepletion` pool by pool. Suppose `applyDepletion` throws for an earlier pool, for example inside `runVacuum`. The catch in `clearCombatArtifacts` logs the error and keeps the writes. Every later pool of the same fight is then never depleted, and a retry cannot recover it because the links are gone. Under-depleting is safer than depleting twice, so this is not a blocker, but the loss is wider than it needs to be.
**Fix:** Unlink per pool, right before that pool is written. Wrap each pool in its own try, so one bad pool neither double-counts nor drops the others:
```ts
for (const poolId of poolIds) {
  for (const enemy of countedByPool.get(poolId) ?? []) ctx.db.combat_enemy.id.update({ ...enemy, poolId: 0n });
  try { /* applyDepletion */ } catch (e) { console.error(`settlePoolKills: pool ${poolId}: ${redactSecrets(String(e))}`); }
}
```

### IN-02: A renamed invented target no longer matches what the NPC said, keeps the model's casing, and can pass 40 characters

**File:** `spacetimedb/src/helpers/llm_apply.ts:837`, `:1002`; `spacetimedb/src/helpers/family_validate.ts:221-249`
**Issue:**
- `freeCreatureName` checks names against every enemy template and family in the world, across all regions. When the model's name, say "Ash Wolf", already exists in another region, the quest target becomes something like "Old Ash Wolf". The NPC's dialogue and the stored `questDescription` still say "Ash Wolf".
- `cleanName` does not title-case, so a lowercase model name is stored as-is. The test pins `endsWith('gloomfang')`, which gives public family and pool names like "Old gloomfang".
- The 40-character cap is applied before `withPrefix`. A renamed long name can therefore exceed it.

**Fix:**
- Title-case the cleaned name, as `titleCase` already does for family names.
- Re-apply the length cap after `take`.
- Consider limiting the uniqueness check to the quest's region. Alternatively, put the actual target name in the "New quest" line, so the player sees the creature the server will count.

### IN-03: A wind-up whose ally name has not loaded still reads "→ the party"

**File:** `src/combat/windup.ts:56-59`
**Issue:** When `targetEnemyId > 0n` but `enemyNames` has no entry, for example during a key swap or before the enemy rows apply, `windupTarget` falls through to the player and pet checks. A support cast has neither, so the result is `'the party'`. That is the misleading text C-WR-01 removed.
**Fix:** When an ally id is set, never fall through to the party:
```ts
if (targetEnemyId != null && targetEnemyId > 0n) {
  const ally = enemyNames?.get(targetEnemyId);
  return ally !== undefined && ally !== '' ? ally : 'an ally';
}
```
"an ally" is new copy and would go to the D-58 copy review. An empty target that hides the arrow avoids new copy.
