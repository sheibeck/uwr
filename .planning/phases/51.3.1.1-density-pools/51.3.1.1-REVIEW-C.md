## Summary

**Scope.** I read every production file in the list in full, or as its full phase diff where the file predates the phase. Every call chain that crosses into the server was traced to its source:
- the reducers `pull_family`, `gather_pool`, `pull_named_enemy` and `start_combat`;
- `placeRating` and `ratingLevelRange`;
- the `my_harvest_caps` view;
- `fightRoster` and `getGroupOrSoloParticipants`;
- `individualsHere` and `placeSpawnLevel`;
- the `combat_enemy_cast` insert;
- `startCombatForSpawn`'s origin rule.

The tests touch 122 files and pass: `npx vitest run src/rails src/combat src/console src/game src/map src/frame src/action src/poolBindings.test.ts src/styles` gave 2916 passed, 0 failed.

**What holds up:**
- **Subscriptions.**
  - `pool_level` is keyed by the region ids of here, the exits and the visited places. Its filter matches the query (the shared-cache rule).
  - The fight's pets come through the `combat_participant -> active_pet` semijoin. No query compares the optional `active_pet.combat_id` with a literal, and `queries.test.ts` pins that rule for every query.
  - `combat_encounter` is keyed by the combat id, and `combat.encounter` only returns the row of the current id.
  - The named-enemy templates are their own id-list binding.
  - Every new keyed binding is in `keyedAll`, so `reset()` disposes it.
- **Readiness.**
  - `poolsAppliedFor` is true only once the shown binding has applied and covers the place's region. It is false while loading, after a failure and for an unknown place.
  - `ratingForPlace` turns a not-ready place or a null level into Unknown with no word.
  - Safe comes only from `location.isSafe`, so no surface flashes Safe while loading.
- **Reducer calls.** Every call uses object syntax with the generated argument names (`pullFamily({ characterId, poolId })`, `gatherPool`, `pullNamedEnemy({ characterId, namedEnemyId })`, `startCombat({ characterId, enemySpawnId })`).
  - `send()` passes a rejection on, so the action runner prints `Couldn't send that. Try again.`.
  - Keyword clicks catch the rejection.
  - `fire()` keeps its never-reject rule.
- **XSS.** There is no `v-html` or `innerHTML` in `src/`. All names reach the DOM as text nodes or bound attributes. `familyIcons` uses own-key lookup only.
- **Design guards.** The new styles use tokens and `color-mix` recipes only. Sizes are 10/12/14/16, weights 400/500 and spacing 4/8/16. There are no negative margins, and `<svg>` appears only under `src/map`. Card and enemy-card actions are buttons with no nested buttons, and the mobile targets are 44px (cards, eye buttons, chips).
- **Time of day (D-55).** The resource time-of-day filter is wired through `FrameControls.timeOfDay` from `world_state`. While the value is unknown, every pool is listed.
- **Feed kinds.** The four density kinds are classified after `cleanServerText`, are never keyword-eligible, and render as text nodes.

**What is wrong:** none of the findings is a blocker.
- **Wind-up wording.** An enemy heal or shield wind-up reads "→ the party".
- **Rating level.** The rating level counts offline party members, so the client and the server's look text disagree.
- **Named card level.** Named cards show the template's level, not the place-scaled level the fight uses.
- **Hidden named group.** The named and World event Fight cards are hidden behind the pool readiness gate, and a failed pool subscription shows no error at all.
- **Named chip.** The chip is matched by template id, which can mark ordinary family members as Named.
- **Dead subscription.** The threat view subscription has no reader since the threat block was removed.

## Warnings

### WR-01: An enemy heal or shield wind-up says "→ the party" when it is aimed at an enemy ally

**Files:**
- `src/combat/hostiles.ts:58-66` (`HostileCastRow` has no `targetEnemyId`)
- `src/combat/hostiles.ts:245-263` (the wind-ups are built with `windupTarget`)

**Issue:** Since Plan 05, a support or caster member's heal or shield wind-up is inserted with `targetEnemyId: allyId` and no player or pet target (`spacetimedb/src/reducers/combat.ts:2216-2227`). `windupTarget` (`src/combat/windup.ts:39-56`) falls through to `'the party'`. The card therefore reads, for example:

`Hexer winds up Mending Light → the party · lands in 2 rounds`

That says the party is about to be hit, while the same card's target line correctly says `Healing Goblin Brute`. The feed's wind-up warning (`combatFeed.ts`, same helper) has the same fault. A player would defend against a heal. No test covers a cast with `targetEnemyId`.

**Fix:** Carry the ally on the cast row and name it before the player and pet fallbacks:
```ts
// hostiles.ts
export interface HostileCastRow { /* ... */ targetEnemyId?: bigint | null; }
// in hostileViews, inside the windups map:
const allyId = cast.targetEnemyId;
const ally = isSet(allyId) ? enemyById.get(allyId) : undefined;
const target = ally
  ? ally.displayName
  : windupTarget({ targetCharacterId: cast.targetCharacterId, targetPetId: cast.targetPetId, selfId: input.selfId,
                   characterNames: input.characterNames, petNames: input.petNames });
```
Apply the same branch in `combatFeed.ts`. Add a test: a cast with `targetEnemyId = 2n` reads `→ {ally name}`, never `the party`.

### WR-02: The rating level counts offline party members, so the client rating disagrees with the server (D-14, D-56, P2)

**Files:**
- `src/rails/rating.ts:101-116` (`viewerRatingLevel`)
- every caller: `useRatingLevel` in `src/rails/useExits.ts:58-63`, then the header, Here card, exits, chips, Map, legend and encounter foot

**Issue:** `viewerRatingLevel` takes the lowest level of every group member who stands at the viewer's place, online or not. The server rates the place for `rosterLevel(getGroupOrSoloParticipants(...))` (`helpers/look.ts:95-102`). That roster goes through `fightRoster`, which skips `row.online !== true` (`helpers/group.ts:29`). Encounter rolls, draws and the look text all use that roster.

So a level-2 party member who logged off at the place makes every client surface read Risky or Deadly, while the look text says Quiet. The creatures also roll against the online roster only. This breaks UI-SPEC P2 ("no two surfaces ever disagree") and the D-14 rule that offline members never count. The rating tests and the Map tests have no offline case.

**Fix:**
```ts
export function viewerRatingLevel(
  self: { id: bigint; level: bigint; locationId: bigint } | null,
  groupMembers: readonly { characterId: bigint }[],
  characters: readonly { id: bigint; level: bigint; locationId: bigint; online?: boolean }[],
): bigint | null {
  // ...
  for (const other of characters) {
    if (other.id === self.id || !inParty.has(other.id) || other.locationId !== self.locationId) continue;
    if (other.online !== true) continue; // the server's fightRoster rule (D-14)
    if (other.level < lowest) lowest = other.level;
  }
```
Add a test: an offline level-1 member at the place does not lower the level.

### WR-03: Named cards show the template's level and con colour, not the level the named enemy has at this place

**File:** `src/rails/pools.ts:260-273` (`namedRows`: `level: template?.level`)

**Issue:** The server's level for a named enemy is `placeSpawnLevel(template.level, computeLocationTargetLevel(...), location.levelOffset)` (`helpers/encounters.ts:410-418`). Both the look text (`Enemies nearby: [Name] (Lv X)`) and `pull_named_enemy`'s spawn use that level. When the template's level falls outside the place's band, the server uses the place target instead.

The card shows `Lv {template.level}`, colours the name with `conFor(template.level, ...)`, and sorts by that level. A level-12 named template at a level-4 place reads as a red Lv 12 card, then fights at level 4 (or the reverse). Event spawns are correct, because they use `effectiveEnemyLevel(spawn.level, ...)`.

**Fix:** Mirror the shared rule on the client. Import `placeSpawnLevel` and `placeLevelBand` from `@game-data/enemy_rules`, plus the place target the Map already derives (the region `dangerMultiplier` / location `levelOffset`). Compute `level` for named rows the way the server does. Alternatively, have the server publish the place level on `named_enemy`, which is an additive column. Until then, omit `Lv n` and the con class for named rows rather than show a wrong number. Add a test with a template level outside the place band.

### WR-04: Named and World event Fight cards wait on the pool rows, and a failed pool subscription hides them with no error

**Files:**
- `src/rails/pools.ts:387-389` (`nearbyGroups` returns `named: null` when `!ready`)
- `src/rails/NearbyList.vue:112`, `196-207`
- `src/game/gameData.ts:631-639`

**Issue:** Named enemies come from `named_enemy`, and event spawns come from `enemy_spawn`. Neither depends on `pool_level`, yet the whole Named & quest targets group is gated on `poolsAppliedFor(place)`.

`createKeyed` promotes a failed binding. In that case `poolRegionsApplied` is the empty set until a reconnect, and with it:
- every pool group and the named group stay hidden;
- `nothingAtAll` stays false, so no empty line shows either;
- every rating reads Unknown;
- the player gets no message.

A World event boss here is invisible in Nearby while its feed keyword still works. The test at `pools.test.ts:359-365` pins this behaviour as intended, so the gap is in the contract, not only in the code.

**Fix:** Gate only the pool groups on `ready`, and add a visible state for a failure:
```ts
// nearbyGroups
const named = input.named.length === 0 ? null : [...input.named];   // not gated on ready
if (!input.ready) return { creatures: null, named, resources: null, alsoHereLabel: named !== null && input.others > 0,
                           nothingAtAll: false, loadFailed: input.failed };
```
Expose `poolsFailed` on GameData (`pools.failed`). Have NearbyList print one quiet line (for example `Couldn't load what lives here. Reconnecting will retry.`, PROPOSED for D-58) when it is true.

### WR-05: The Named role chip is matched by template id, so ordinary family members can read Named

**Files:**
- `src/combat/EncounterPanel.vue:40`
- `src/combat/EncounterStrip.vue:30`
- `src/combat/hostiles.ts:238-241`

**Issue:** `namedTemplateIds` holds the `enemyTemplateId` of every own `named_enemy` row, alive or slain. Any combat enemy of such a template reads `Named` with the crown. `named_enemy.enemyTemplateId` is the quest template's `targetEnemyTemplateId` (`helpers/search.ts:114-123`). When that is an ordinary creature template that is also a family member, every member of that template drawn in a pool pull or an ambush is labelled Named. Slain named rows keep their template in the set, so the false label persists.

The template rule is also redundant. `startCombatForSpawn` already records origin `'named'` for every named or boss spawn (`reducers/combat.ts:234-256`), and `namedFight` covers exactly those fights.

**Fix:** Drop the template rule and rely on the origin:
```ts
const role = roleView(template?.role, { boss: isBoss, named: input.namedFight === true });
```
Then remove `namedTemplateIds` from both components and from `HostileViewsInput`. If a legacy fight with no origin must still show Named, restrict the set to living named rows whose template has no family member. The client cannot know that, which is another reason to rely on the origin.

### IN-08: Feed keyword edge cases

**Files:**
- `src/console/FeedView.vue:31-46`
- `src/rails/pullTargets.ts:59-67`
- `src/console/keywordLabel.ts:6-14`

**Issue:**
- **Gather keywords.** The look text writes `[Gather {Resource}]` (`helpers/look.ts:147`). The keyword inside it is a `node` entry, so a click examines the resource instead of gathering it.

**Fix:** Pass the time-of-day filter into `gatherTargets`. Decide in the copy review whether a resource keyword gathers. Give family entries priority over event entries of the same name, or skip the duplicate.

### IN-10: After a flee, a named enemy shows both "Slain" and a Fight card (cross-part)

**File:** `src/rails/pools.ts:260-292`

**Issue:** `pull_named_enemy` marks the named row `isAlive: false` when the fight starts and spawns an individual `enemy_spawn` (`reducers/quests.ts:551-563`). ### IN-11: The header pill's rating line is reachable only by hover

**Issue:** The rating line is only a `title` on a non-focusable span. Keyboard, touch and screen-reader users never get it in the header. The Here card shows it as text, so this is a minor gap on desktop only.

**Fix:** Add a `.sr-only` span with the line inside the pill, or `aria-describedby` to the Here card's rating line.
