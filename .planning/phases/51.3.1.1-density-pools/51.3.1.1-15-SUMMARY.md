# Phase 51.3.1.1 Plan 15: Migration of Existing Worlds Summary

An existing world now moves to families and pools on its own. After publish, `tick_pools` migrates one region per run, with a cursor on the tick row. For each region it:
- groups today's ordinary enemy types into rule families, pooled where their real members stood;
- gives each AI-invented kill target a family of one;
- seeds resource pools;
- retires the standing ordinary spawns and personal nodes;
- marks the old start location as the hub, changing only `isHub`.

It makes no paid call and can safely run again.

## What was built

### `helpers/pool_migration.ts`
- **`POOL_MIGRATION_VERSION = 1n`** is a data version, not a tunable. Plan 25 raises it.
- **`isInventedQuestKillTarget(ctx, template)`** is true when:
  - the template has terrainTypes `any` and socialGroup `loner`;
  - a kill or kill_loot quest targets it (a missing questType reads as kill);
  - no boss_kill quest targets it.
- **`markLegacyHub(ctx, regionId)`** applies D-61 and D-63.
  - It acts only when no place in the region is a hub and the `findRegionStart` place has an NPC whose type is vendor or banker. That place then gets `isHub: true`.
  - Nothing else changes: isSafe, craftingAvailable, bindStone and the NPCs stay as they were.
  - It returns whether it marked a hub.
- **`retireStandingState(ctx, locationIds)`** returns `{ spawns, members, nodes }`. It deletes:
  - `enemy_spawn` rows that are `available`, have no `event_spawn_enemy` link and have an ordinary template, together with their `enemy_spawn_member` rows;
  - `resource_node` rows that are `available` and have no `lockedByCharacterId`.
  - Every other row is left alone.
- **`migrateRegion(ctx, regionId, now)`** runs these steps in order:
  1. Mark the legacy hub.
  2. Delete orphan creature pools (pools whose family row is missing) and their `pool_level` rows.
  3. Group ordinary templates that are in no family yet and are linked to a host place, using `familiesFromTemplates` and `createFamily` at `regionBaseLevel`. Invented quest kill targets are set aside for step 5.
  4. Make every rule family of the region (key `<regionId>:...`) a rival of the others, using `ruleRelations` and `createRelations`.
  5. At each host place, link the families of the ordinary templates linked there, then run `seedCreaturePools`. Existing placement is kept; terrain is not used.
  6. Call `familyOfOne` for each quest target, at its lowest-id linked host place, or else its lowest-id linked place.
  7. Run `seedResourcePools` at every charted place, then `addResourcePoolsForRegion` (D-48).
  8. Run `retireStandingState` on every place in the region.
- **`planMigrationStep(ctx, arg, now?)`** returns a `MigrationStep`: `{ migrating, batch, more, afterRegionId, nextAt, nextAfterRegionId }`.
  - Below the version, it calls `planRestockBatch(sortedRegionIds, cursor, MIGRATION_REGIONS_PER_RUN)`. The next tick is `now + MIGRATION_CONTINUE_MICROS` while regions remain, or `now + POOL_TICK_MICROS` with the cursor at 0n once they are done.
  - At the version, it plans the normal tick.
  - If a state read fails, it plans no work and tries again from the same cursor one tick later.
- **`runMigrationStep(ctx, step, next, now)`** migrates each region of the batch inside its own try/catch.
  - **On a failure:** it logs `tick_pools: migrating region N failed`. It then deletes `next` and inserts a retry row due `now + MIGRATION_CONTINUE_MICROS`, with the cursor at the last region that succeeded.
  - **On success of the last batch:** it sets `pool_state.version = POOL_MIGRATION_VERSION`.

### `index.ts` `tick_pools`
The order is:
1. the guard;
2. `planMigrationStep`;
3. the single `ctx.db.pool_tick.insert(` built from the step;
4. inside try/catch, either `runMigrationStep` (while migrating) or `runPoolTick`.

While the migration runs, settle, hunters and trends do not run. The unused `DENSITY_RULES` import was removed.

### `helpers/pool_tick.ts`
`updatePoolState` is now exported, and the header comment explains the migration branch.

## Deviations from Plan

### Auto-fixed Issues
1. **[Rule 2 - Safety, T-51.3.1.1-48 / D-07] Retirement keeps individual spawns.** `retireStandingState` also requires the spawn's template to be ordinary. Without this, the available spawns of boss_kill targets and named enemies would have been deleted. The test checks that the boss_kill spawn stays.
2. **[Rule 1 - Ordering] Hub first, quest targets after families.**
   - The hub is now step 1 rather than the last step, so a start place that is not safe can never get creature pools before it becomes a hub.
   - Quest targets now run after the region's families. Otherwise `familyOfOne`'s internal `ensurePoolsForLocation` would group one place's templates on their own, and the family name would then depend on that place rather than on the whole region.
3. **[Rule 2] Region AI gatherables.** `addResourcePoolsForRegion` runs after `seedResourcePools`. Without it, an existing region's AI gatherables could miss a pool once nodes are retired (D-48). It is safe to rerun.
4. **[Rule 2] Orphan creature pools are deleted,** together with their `pool_level` rows, as the Plan 14 hand-off suggested.
5. **Relations over every rule family of the region,** not only the new ones. A run that crashes between `createFamily` and `createRelations` therefore still gets its relations on the next run. Quest (`quest:`) and AI (`ai:`) families are never touched.
6. **Retry row.** The plan offered either computing the cursor after success or rescheduling with the previous cursor. I chose the second: a failing run deletes its new row and inserts the retry row inside `pool_migration.ts`.
   - Deleting a row is the documented way to cancel a scheduled job, so this avoids relying on updating a scheduled row.
   - The 700-character window in `index.ts` still has exactly one `pool_tick.insert(`, so the Plan 14 pin passes.
   - A failing run makes two inserts but always leaves one pending row.
7. **planMigrationStep fallback.** If a state read fails, the step returns no work, plus a reschedule from the same cursor. This keeps the chain alive even though the plan runs before the insert.
8. **Existing tick tests:** `quietWorld()` in `pool_tick.integration.test.ts` now seeds `version: POOL_MIGRATION_VERSION`, so those tests exercise the normal tick.
9. **Acceptance grep:** a header comment mentioned the clear flag. It was reworded so `grep -c "clear-database"` prints 0 (commit 09fde9c0).

No file outside files_modified was touched.
