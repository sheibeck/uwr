# Phase 51.3.1.1 Plan 10: Generalised fight start and kill depletion Summary

Every fight now starts through one `startCombat` that takes a drawn group (pool enemies with spawnId 0n and their poolId) and records the origin on the fight row. Kills are settled against their pools exactly once, first thing in `clearCombatArtifacts`, for victory, defeat, `end_combat` and the failure close.

## What was built

### Task 1: startCombat with drawn enemies and the recorded origin
- `reducers/combat.ts` exports:
  - `DrawnEnemy = { enemyTemplateId, level, spawnId, poolId, roleTemplateId? }`
  - `CombatOriginKind`: the `COMBAT_ORIGINS` value type.
  - `CombatOrigin = { kind, familyId?, level?: number, name, plural? }`
- `addEnemyToCombat` is still the only `combat_enemy.insert`. It:
  - takes either a spawn row or a DrawnEnemy;
  - writes `spawnId` and `poolId`;
  - never calls `takeSpawnMember` or marks a spawn engaged when spawnId is 0n;
  - takes a new `index` parameter for the role-template seed.
- `startCombat(deps, ctx, leader, candidates, groupId, drawn, origin)` runs the steps below and returns the combat:
  - `fightRoster`;
  - the encounter insert with `origin`, `originFamilyId`, `originLevel`, `originName` and `originPlural`;
  - one add per drawn enemy;
  - participants and cooldowns;
  - `Combat begins against {origin.name}.`;
  - the summoner pet aggro on the first enemy added;
  - the intro lines and `startRound`.
- `startCombatForSpawn` is now a wrapper: it builds one DrawnEnemy from the spawn and sets origin 'named' for a named or boss spawn, '' otherwise.
- `index.ts`: `reducerDeps.startCombat(ctx, leader, candidates, groupId, drawn, origin)`.

### Task 2: settlePoolKills at the single fight-end point
- `helpers/pools.ts` `settlePoolKills(ctx, combatId, now): PoolCountShift[]`. It:
  - sums `DEPLETION_BY_ROLE[normalizeEnemyRole(template.role)]` per pool, over enemies with poolId > 0n and currentHp 0n;
  - calls `applyDepletion(..., 'kill')` once per pool, in pool id order;
  - skips a missing pool.
- `clearCombatArtifacts` calls it as the first statement, in a try/catch. A failure logs `clearCombatArtifacts: pool kills failed in combat N: ...` (redacted) and the cleanup continues.
- `helpers/combat_rewards.ts` `resetSpawnAfterCombat(ctx, enemies, reinsertSurvivors)`:
  - skips spawnId 0n before any lookup;
  - no longer inserts `enemy_respawn_tick` rows (the Plan 08 hand-off item).

## Deviations from Plan

### Auto-fixed / in-scope additions

**1. [Rule 2 / hand-off item] Stopped the enemy_respawn_tick inserts in resetSpawnAfterCombat**
- **Found during:** Task 2. The coordinator and Plan 08 hand-off asked for this if the file was in scope.
- **Issue:** after a kill, a spawn left empty still scheduled an `enemy_respawn_tick`, but `respawn_enemy` only drains now.
- **Fix:**
  - removed both inserts;
  - dropped the `ScheduleAt` and `ENEMY_RESPAWN_MICROS` parameters and the now-unused `ENEMY_RESPAWN_MICROS` constant in combat.ts;
  - added a small `deleteSpawnAndMembers` helper.
- **Commit:** 1dd4d4da

**2. Role-template seed only for drawn enemies**
- The plan says to seed `pickRoleTemplate` with `poolSeed(ts, combat.id, index)`. That seed is used only for pool enemies (spawnId 0n).
- Spawn-based adds and named spawns keep `ts + spawnId`, so no existing role pick changes.
- Family members have one role template each, so the seed rarely matters for them.

**3. Function order kept for an existing source pin**
- `group_participants.test.ts` slices from `export const startCombatForSpawn` to the next `combat_encounter.insert`.
- `startCombat` is defined right after the wrapper, so that slice still contains the `fightRoster` call. The pin passes unchanged, and no test file outside my list was edited.
