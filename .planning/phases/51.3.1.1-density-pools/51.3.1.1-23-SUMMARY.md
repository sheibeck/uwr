## Task 3: writeRegionFill AI families, arrival isSafe, hub count

- **writeRegionStart:** the arrival point is now `isSafe: isStarter || start.isSafe !== false`:
  - the starter region is still a safe hub with a station and a bind stone;
  - a non-starter arrival point takes the model's false.
- **buildWorldFillInput:** `hubCount = regionHubCount(region, genState.sourceRegionId === 0n)`, and `arrivalIsHub = start.isHub === true`.
- **writeRegionFill, steps in order:**
  1. **Place words:** `validatePlaceWords` runs on each new location insert. Then `writeArrivalPlaceWords` runs after the hub step (step 4c) and writes the arrival point's words when they are usable.
  2. **Hubs:** step 4b (Plan 09, unchanged) reads the reply's marks.
  3. **Families:** step 5 re-reads `[arrival, ...new]` after the hub step and runs `validateFamilies(fill, { regionId, places, isTaken })`. `isTaken` checks the names of existing enemy templates and families with `nameKey`.
     - **Validated families:** `buildAiFamilies` runs. It creates each family with `createFamily` at the region's base level, links it to its fit places with `linkFamilyToPlaces`, stores relations both ways (the inverse kind for the other family), then runs `seedRegionPools`.
     - **Otherwise:** an old-shape reply or an empty or unusable families array takes the rule path. `insertReplyEnemyTemplates` (the old step 5, moved unchanged into a helper) runs, then `buildRegionFamilies`.
- No enqueue site was added: the `git diff` of world_gen.ts has no `enqueueLlmJob`.

**2. [Rule 3 - Blocking] The canned fill reply in llm_cutover.test.ts used the old shape**
- **Found during:** Task 3, in the wider check.
- **Issue:** the executor checks the top-level required keys of the route schema (claude_request.ts `schema_mismatch`). Its old-shape `REGION_FILL_JSON` therefore failed two staged world-gen tests. Neither test calls a paid API: both use the scripted `http.fetch`.
- **Fix:** the canned reply now has `arrival`, place words, `isHub` and one family, and no longer has `enemies`. The assertions are unchanged; for example, `enemy_template` is still above 0 through the family members.
- **Files modified:** `spacetimedb/src/reducers/llm_cutover.test.ts`. This is a server test file that Plan 18 does not list.
- **Commit:** 698b2ed3.

**3. [Rule 2 - Correctness] A stage-1 reply with no isSafe reads as safe**
- **Issue:** the plan says `start.isSafe === true`. A stage-1 reply written under the older wording was asked for a safe place and has no isSafe. Plan 09's tests rely on that.
- **Fix:** I used `isStarter || start.isSafe !== false`. A new reply always carries the boolean, because the schema requires it. Tests cover false, true, missing and the string 'false'.
- **Commit:** 698b2ed3.

**4. [Rule 2 - Correctness] Relations are stored with their inverse**
- **Issue:** the plan says "the relation stored both ways".
- **Fix:** the other family gets the inverse kind: rival becomes rival, prey becomes predator, predator becomes prey. That keeps Plan 06's vacuum candidates consistent. Both kinds are tested.
- **Commit:** 698b2ed3.

**5. [Rule 3 - Refactor] The old enemy-template loop moved into a helper**
- **Issue:** the AI path and the rule path needed a clean branch.
- **Fix:** I moved the old step 5 loop, byte-identical apart from indentation, into `insertReplyEnemyTemplates(tx, fill, dangerMultiplier)`. Only the rule path calls it, so a reply with families never inserts stray enemies.

**Total deviations:** 5 auto-fixed (2 blocking test fixtures, 2 correctness choices, 1 refactor). No production file outside files_modified was changed.
