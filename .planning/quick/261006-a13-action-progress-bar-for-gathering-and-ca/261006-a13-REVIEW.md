## Summary

Reviewed the action progress row: the pure math module, the first-seen and ticker composable, the ActionRow component, its FeedShell mount, and the per-character `resource_gather` and `character_cast` bindings. I cross-checked them against the server code that writes these rows (`items_gathering.ts`, `items.ts`, `corpse.ts`, the `tick_casts` reducer in `combat.ts`, and `abilityCastMicros` in `helpers/combat.ts`) and against `serverClock.ts`, `useCooldownTicker.ts`, `bindTable.ts` and `keyedBinding.ts`.

What holds up:
- **Subscriptions.** They filter on `character_id` with a WHERE clause and a matching filter. They are in `keyedAll`, so reset and scope-stop dispose them; the existing reset tests count every binding.
- **Character swap.** During a keyed swap, rows from the previous character are filtered out by `characterId`.
- **Text safety.** Names render only through interpolation and attribute bindings. There is no `v-html`, and the design guard walks `src/action`.
- **Tokens.** Every token the component uses exists in `nocturne.css`.
- **Ticker.** There is one ticker. It stops when the action clears and on unmount. FeedShell renders once through `v-if` / `v-else`, so only one ActionRow exists at a time.
- **Composer slot.** The row hides on the same `combat.active` flag that RoundRow uses, so the two never show together.
- **Tests.** `pnpm exec vitest run src/action` passes: 3 files, 43 tests.

The main weakness is how the bar's start time is anchored:
- It is a single server-clock estimate taken when a row first appears, then frozen.
- A later clock-skew sample therefore distorts the fraction for the rest of the action (WR-01).
- The anchor lives in component state, so a remount resets it (WR-02).
- The mixed time sources can briefly show more seconds than the action's total (WR-04).
- The tests cannot catch any of these (WR-03).

No blockers.

## Warnings

### WR-01: First-seen is frozen under the clock skew at row arrival; a later skew sample distorts the bar for the whole action

**File:** `src/action/useActionProgress.ts:57`, with `src/action/actionProgress.ts:120-136` and `src/game/serverClock.ts:20-25`

**Issue:** `next.set(key, input.clock.nowMicros())` stores the first-seen time as an *estimated server time*, using whatever skew exists at that moment. Each later read of `now` uses the *current* skew. The bar computes `fraction = (now - start) / (end - start)`. If the skew changes after first-seen, the error never cancels: `now` moves while `start` stays put.

The skew is only sampled from live event rows (`gameData.ts:157-163`), so this happens in two realistic cases:

1. **Reload or remount mid-action before any event row arrives.** The subscription snapshot runs the sync watch with skew 0, so first-seen is raw client time.
   - If the client clock is ahead of the server by more than the time left, `remaining <= 0`. The row reads "Finishing…" with a full bar for the whole remaining gather.
   - Once any event row is sampled, the bar jumps by `skew / total` and stays wrong.
2. **First action of a session.** The "You begin gathering" / "Casting X..." event row comes in the same transaction as the gather or cast row. Which callback runs first depends on the SDK's query-set and table order (`#applyTableUpdates` dispatches in that order). If the gather row's `refresh` runs first, first-seen uses the stale skew.
   - Client behind the server by `e`: the bar jumps to `e/(8+e)` at once (50% for `e = 8 s`).
   - Client ahead by `e >= 8 s`: `start >= end`, so the fraction stays 0 for the whole gather while the seconds count down.

The only skew test (`actionProgress.test.ts:193-200`) passes a fixed `start`, so it cannot detect this.

**Fix:** Store first-seen in client time and re-base it with the *current* skew on every read. Both ends of the subtraction then use the same estimate:

```ts
// useActionProgress.ts — record the raw client time and the skew at that moment
next.set(key, input.clock.nowMicros() - input.clock.skewMicros.value); // client micros
// ...
const seenClient = firstSeen.value.get(view.key);
const seen = seenClient === undefined ? now : seenClient + input.clock.skewMicros.value;
```

Widen `ActionProgressInput.clock` to `Pick<ServerClock, 'nowMicros' | 'skewMicros'>`. Add a composable test: create the row, then call `clock.sample()` with +5 s, tick, and assert the fraction has not jumped.

### WR-02: First-seen state lives in the component, so a FeedShell remount restarts the bar at 0 mid-action

**File:** `src/action/useActionProgress.ts:44`, `src/frame/AppFrame.vue:99,172`

**Issue:** The first-seen map is created inside `useActionProgress`, which is scoped to ActionRow. AppFrame renders FeedShell in two branches (`<template v-if="isDesktop">` … `<template v-else>`). Crossing the desktop breakpoint (resizing the window, rotating a tablet) unmounts one FeedShell and mounts the other.

The new ActionRow records first-seen as *now*. For a gather (no known total), the bar snaps back to 0% while the seconds keep counting down from the true value, so the bar and the number disagree for the rest of the action. A character switch A to B and back to A loses it the same way.

**Fix:** Keep the first-seen map at the data layer, next to the bindings: create it in `createGameData`, watch the `ownGathers` / `ownCasts` rows there, and expose it as `GameData.actionFirstSeen` with an inert empty default. `useActionProgress` then reads it instead of owning it. The map survives component remounts and still clears on `reset()`.

### WR-03: The tests cannot detect the time-anchoring failure modes

**File:** `src/action/actionProgress.test.ts:193-200`, `src/action/useActionProgress.test.ts`, `src/action/ActionRow.test.ts`

**Issue:** Lifecycle and labels are well covered, but the bookkeeping the brief asks about has gaps:
- **Skew.** The skew test feeds a precomputed `start`, so it cannot fail for WR-01. No test changes the skew between first-seen and a tick.
- **Character switch and logout.** No composable test changes `characterId`, sets it to null, or keeps the previous character's rows during a keyed swap. Only the pure `currentAction` covers that.
- **Combat toggle.** No test shows that first-seen survives a combat toggle. The `inCombat` test sets combat before the first flush and never checks the fraction afterwards.
- **Mid-cast cast.** No composable test covers a cast seen mid-cast (the `knownTotalMicros` path), where the bar should start above 0 at once.
- **Action appearing after mount.** No component test mounts with no rows, moves the clock, then adds a row. Every ActionRow test passes the rows at mount, so the ticker's catch-up before the first render is never checked. It currently works only because of Vue's pre-flush ordering.
- **Replacing a shown action.** No test replaces the shown action while the ticker is already running (WR-04).
- **Reduced motion.** The component's reduced-motion test is only a regex over the source text.

**Fix:** Add composable tests for each case above. Under fake timers, assert `fraction` and `seconds` right after the change and after one tick.

### WR-04: `progress` mixes a fresh first-seen with the ticker's stale `now`, so a newly shown action can read more seconds than its total

**File:** `src/action/useActionProgress.ts:57,79-81`

**Issue:** First-seen is read straight from the clock at row arrival. `progress` uses `ticker.nowMicros`, which can lag by up to 250 ms, or 1 s under reduced motion. If the ticker is already running when a new action becomes the shown one, the lag shows up:
- A cast inserted over a running gather.
- A cast row replaced by a new cast in one transaction (`items.ts:833-841`, `corpse.ts:294,314`).

In that case `now < start`, so the fraction is clamped to 0, and `seconds = ceil((end - staleNow)/1 s)`. Under reduced motion a 3 s cast can read "4s" for up to a second, which is more than the action's total. The ticker only catches up when `active` flips false to true, not when the shown key changes.

**Fix:** Clamp `now` to the anchor in `progress`, or restart the ticker when the key changes:

```ts
const now = Math.max(ticker.nowMicros.value, seen);
```

### IN-02: "Finishing…" can show indefinitely while disconnected

**File:** `src/action/useActionProgress.ts:68-74` (with `src/net/bindTable.ts:50-53`)

**Issue:** `bindTable` keeps rows through a disconnect. If the connection drops mid-action, the row passes `endsAt` and reads "Finishing…" with the ticker still running until the resubscription applies. The reconnect notice bar mitigates this.

**Fix:** Optional: hide the row, or show a different time text, while `game.connected` is false.

### IN-03: Screen readers hear the label three times

**File:** `src/action/ActionRow.vue:46-54`

**Issue:** `span.action-label` is exposed to screen readers. The progressbar repeats the label in `aria-label`, and `aria-valuetext` contains it again (`'Gathering Ironwood · 5s'`).

**Fix:** Give `.action-label` `aria-hidden="true"`, or make `aria-valuetext` only the time text.

### IN-04: The tick rate for reduced motion is fixed when the ticker starts

**Issue:** `prefersReducedMotion()` is read once per `start()`. The CSS media block updates live, but the 250 ms / 1 s interval does not change until the next action. This matches the existing cooldown ticker.

**Fix:** None needed for this task. A shared `matchMedia` change listener could fix it for both consumers.

### IN-05: The ticker keeps running while the mobile composer is hidden

**File:** `src/frame/AppFrame.vue:172`

### IN-06: A mana-floored cast seen mid-cast measures from first-seen

**File:** `src/action/actionProgress.ts:115-118`

**Issue:** Example: a mana ability with `castSeconds` 1 that the server raised to `MANA_MIN_CAST_SECONDS` (3 s), loaded with 2 s left. Here `endsAt - castSeconds` is later than first-seen, so the bar starts at 0 instead of about 33%. With `castSeconds` 0, `knownTotal` is 0 and the bar always starts at first-seen.

This is the documented trade-off of not importing `spacetimedb/src/data/combat_scaling.ts`. MEMORY.md's rule is to import mirrored constants from `spacetimedb/src/data/`.

**Fix:** Optional: add `resourceType` to `AbilityRow` and import the floor from the data module once its `.js` relative import is type-check-safe.

### IN-07: The composer grows by 40 px whenever the row appears or disappears

**File:** `src/action/ActionRow.vue:63-69`, `src/frame/FeedShell.vue:37-44`
