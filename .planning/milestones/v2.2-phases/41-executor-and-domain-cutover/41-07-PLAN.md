Hard rules for this plan:
- The sweeper is a reducer: a caught exception does NOT roll back writes already made in that reducer. So the sweeper never runs `applyLlmResult` itself (a multi-table apply must run in the executor's own transaction, which rolls back cleanly); it re-dispatches received jobs instead. For each job it writes status and money first, then calls `applyLlmFailure` inside try/catch.
- Insert the next sweep tick FIRST in the reducer, then sweep (RESEARCH Pitfall 1).
- Use `onSchedule` on the procedure and reducer options (non-deprecated form, `procedures.d.ts`/`reducers.d.ts`); the procedure uses the named 4-argument form so the export collector in `index.ts` finds it (RESEARCH section 1). Import `LlmDispatch` and `LlmSweepTick` straight from `../schema/tables`, as `reducers/combat.ts` does.
- No publish in this plan (first local publish is Plan 41-10).
- Tests: `pnpm --dir spacetimedb exec vitest run --maxWorkers=1 <files>`; loading `index.ts` under the recorder needs a 120 s `beforeAll` timeout. Stage by explicit path; every commit ends with the two attribution lines.
</context>

## Flagged assumptions

- Spec-less probe item 4 (PIPE-02, unclassified): survival across a tab close is structural (no client in the path; results are applied for the stored player). Survival across a module publish or crash in the middle of a call relies on Phase 39's observation that a publish waits for the in-flight call, and otherwise on the sweeper expiring the stranded in_flight job after the route timeout plus 30 s. The runtime behaviour is a backstop truth, not unit-testable.
- Partial writes: a caught exception inside a reducer does not roll back writes already made in it. The sweeper therefore writes status and money first and calls the failure message last, and never runs a success apply itself.
